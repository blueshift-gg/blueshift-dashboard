# Приклад програми

Тепер давайте розглянемо, як регістри (r0-r10), області пам'яті та інструкції працюють разом у реальній програмі. Ми почнемо з найпростішої програми sBPF, щоб зрозуміти основний процес виконання.

<ArticleSection name="NoOp-програма" id="noop-program" level="h2" />

Програма "NoOp" (без операцій) ідеально підходить для навчання, оскільки вона демонструє основну структуру програми без будь-якої складності:
- Як програми отримують вхідні дані (у регістрі r1)
- Як вони повертають результати (у регістрі r0)
- Базовий потік входу/виходу, який виконує кожна sBPF-програма
- Як Rust компілюється в асемблер sBPF

Навіть якщо вона "нічого не робить", вона показує вам основу, на якій побудована кожна програма Solana.

Тепер, коли ми знаємо основні sBPF-операції, давайте подивимося, як вони виглядають у реальній (навіть якщо крихітній) програмі.

<ArticleSection name="Pinocchio NoOp" id="pinocchio-noop" level="h2" />

Нижче наведено високопродуктивний "noop", написаний за допомогою Pinocchio. Все, що він робить, це повертає успіх:

```rust
#![no_std]
use pinocchio::{entrypoint::InstructionContext, lazy_program_entrypoint, no_allocator, nostd_panic_handler, ProgramResult};

lazy_program_entrypoint!(process_instruction);

nostd_panic_handler!();
no_allocator!();

fn process_instruction(
    _context: InstructionContext, // обгортка навколо вхідного буфера
 ) -> ProgramResult {
    Ok(())
}
```

Якщо ми зберемо цей код за допомогою `cargo build-sbf --dump`, ми отримаємо дамп ELF, який надасть нам інформацію про наш бінарний файл у каталозі `/target/deploy/`.

Потім нам потрібно буде знайти розділ `.text`; частину нашого бінарного файлу, де зберігається виконуваний код.

```pinocchio_noop-dump.txt
Disassembly of section .text
0000000000000120 <entrypoint>
     120 b7 00 00 00 00 00 00 00      	mov64 r0, 0x0
     128 95 00 00 00 00 00 00 00      	exit
```

Давайте розберемо, що насправді означають ці шістнадцяткові байти, використовуючи вивчений нами формат інструкцій:

Це перша інструкція: `120 b7 00 00 00 00 00 00 00`
- Адреса: `0x120` (у текстовій області, що починається з 0x100000000)
- Код операції: `0xb7` = `mov64` з негайним значенням
- dst: `0x00` = регістр `r0`
- src: `0x00` = невикористано (негайна операція)
- offset: `0x0000` = невикористано
- imm: `0x0000000` = негайне значення 0

А це друга інструкція: `128 95 00 00 00 00 00 00 00`
- Адреса: `0x128` (8 байтів після першої інструкції)
- Код операції: `0x95` = вихід/повернення
- Усі інші поля: `0x00` = не використовується для виходу

> Зсув `0x120` – це місце, де лінкер вирішив розмістити функцію точки входу в розділі `.text` файлу ELF. Файл ELF починається із заголовків, таблиць розділів та інших метаданих, які займають перші ~`0x120` байти (288 байт). Фактичний виконуваний код знаходиться після всієї цієї бухгалтерської інформації.

<ArticleSection name="NoOp на Асемблері" id="assembly-noop" level="h2" />

Якби ми дизасемблювали бінарний файл, щоб перетворити його назад на компільований sBPF Assembly, код виглядав би так:

```sbpf
.globl entrypoint:
    mov64 r0, 0x00   ; r0 <- success
    exit             ; finish, return r0
```

Давайте розберемо код:
- `.globl entrypoint`: Це директива асемблера, яка вказує компонувальнику зробити символ точки входу глобально видимим. Виконання Solana шукає цей символ, щоб знати, звідки почати виконання вашої програми.
- `entrypoint`:: Це мітка, яка позначає адресу пам'яті, з якої починається виконання програми. Коли виконання завантажує вашу програму, вона переходить на цю адресу.
- `mov64 r0, 0x00`: Переміщує безпосереднє значення 0 у регістр r0. Оскільки r0 є регістром повернення, це встановлює код повернення успішного виконання.
- `exit`: Завершує виконання програми та повертає значення в r0 до середовища виконання.

> повернення 0 означає, що ми повертаємо успішне виконання програми.

Це надзвичайно мала програма, лише з 2 інструкціями, що споживають лише 2 обчислювальні одиниці (CU) для виконання, що ідеально відповідає нашому коду Rust:
- Ми визначили функцію точки входу
- Ми повертаємо Ok(()), яка обчислюється як 0
- Компілятор згенерував відповідні інструкції `mov64` та `exit`

<ArticleSection name="NoOp на Оптиміщованому Асемблері" id="optimized-assembly-noop" level="h2" />

Однак, ми можемо оптимізувати це далі. Оскільки середовище виконання Solana за замовчуванням ініціалізує `r0` рівним 0, ми можемо виключити зайву інструкцію `mov64`:

```sbpf
.globl entrypoint:
    exit
```

Ця оптимізована версія:
- Витрачає лише 1 обчислювальний блок (зниження на 50%!)
- Дає ідентичні результати (`r0` все ще містить 0)

> Ось чому розуміння асемблерного коду допомагає з оптимізацією!

Ця оптимізація можлива, оскільки ми знаємо початкові стани регістрів; це те, чим компілятор Rust не завжди користується. Розуміння асемблерного коду sBPF дозволяє виявляти та усувати такі неефективності в критично важливому для продуктивності коді.

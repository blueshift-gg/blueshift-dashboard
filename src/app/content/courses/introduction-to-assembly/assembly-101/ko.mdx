# sBPF Assembly 101

![Introduction to Assembly](/graphics/course-banners/introduction-to-assembly.png)

sBPF Assembly와 Solana 프로그램에서의 그 역할을 이해하려면 먼저 어셈블리 언어와 그것이 고수준 코드와 머신 실행을 어떻게 연결하는지 이해해야 합니다.

<ArticleSection name="어셈블리 언어" id="the-assembly-language" level="h2" />

어셈블리는 머신 코드의 사람이 읽을 수 있는 형태입니다. 즉, 프로세서가 실제로 실행하는 명령어입니다. 이는 고수준 프로그래밍 언어와 컴퓨터가 이해하는 이진 코드 사이의 다리 역할을 합니다.

다음과 같은 Rust 코드를 작성할 때:

```rust
let result = a + b;
```

컴파일러는 이를 여러 단계를 거쳐 번역합니다:
1. Rust 소스 → 구문 분석 및 분석됨
2. 중간 표현 → 최적화됨
3. 어셈블리 코드 → 사람이 읽을 수 있는 명령어
4. 머신 코드 → 프로세서가 실행하는 이진 코드

어셈블리는 3단계를 차지합니다: 이진 코드로 변환되기 전의 최종 사람이 읽을 수 있는 형태입니다. 각 어셈블리 명령어는 정확히 하나의 프로세서 연산에 해당합니다: 숫자 추가, 메모리 로드 또는 다른 코드 섹션으로의 점프.

<ArticleSection name="sBPF 가상 머신" id="the-sbpf-virtual-machine" level="h2" />

Solana sBPF는 확장 Berkeley Packet Filter (eBPF) 명령어 집합의 Solana 맞춤형 변형이자 모든 온체인 프로그램을 실행하는 가상 머신입니다. 이는 특수화된 실행 환경을 생성합니다: 프로그램과 validator의 네이티브 CPU 사이에 위치하는 64비트 레지스터 머신입니다.

sBPF를 블록체인 실행을 위해 특별히 제작된 컴퓨터라고 생각해보십시오. 고처리량 transaction에 충분히 빠르면서도 수천 개의 validator에 걸쳐 보안 및 결정론을 보장할 수 있을 만큼 충분히 제약적입니다.

CPU에서 직접 실행되는 네이티브 어셈블리와 달리, sBPF 코드는 제어된 가상 머신 환경 내에서 실행됩니다. 이 가상 머신은 실행 전에 모든 명령어를 검증하여 크래시, 무한 루프 및 무단 메모리 접근을 방지함으로써 안전을 보장합니다.

이러한 안전 제약에도 불구하고 sBPF는 `just-in-time` 컴파일을 통해 높은 성능을 유지하며, 거의 네이티브에 가까운 실행 속도를 달성합니다.

가상 머신은 또한 결정론적 실행을 보장합니다: 동일한 입력으로 동일한 프로그램이 전 세계 모든 validator에서 동일한 결과를 생성합니다. 이러한 일관성은 블록체인 consensus에 매우 중요합니다.

또한 sBPF는 account 접근, 크로스-프로그램 호출, runtime 상호작용을 위한 syscall을 포함합니다.

### sBPF Assembly 이해가 중요한 이유

Rust 컴파일러가 고수준 코드를 sBPF 명령어로 효율적으로 번역하지만, 어셈블리를 이해하는 것은 여러 이점을 제공합니다:
- **연산 비용(Compute Costs) 이해**: 모든 sBPF 명령어는 compute units(CU)를 소모합니다. Rust 코드 한 줄이 수백 개의 명령어로 컴파일될 수 있습니다. 어셈블리는 특정 연산이 왜 비싼지 보여줍니다.
- **더 작은 프로그램 크기**: sBPF 어셈블리로 직접 작성된 프로그램은 컴파일된 Rust 프로그램보다 훨씬 작아서 배포 비용을 줄이고 로드 시간을 단축합니다.
- **최적화 기회**: Rust 컴파일러는 안전하고 올바른 코드를 생성하지만 항상 가장 효율적인 코드는 아닙니다. 어셈블리는 중복되는 안전 검사와 최적화되지 않은 명령어 시퀀스를 드러냅니다.
- **디버깅 및 분석**: 프로그램이 예상치 않게 작동할 때, 어셈블리는 근거를 제공합니다. 어떤 명령어가 실행되었는지 정확히 추적하고 실패 지점을 식별할 수 있습니다.

### 아키텍처

sBPF는 10개의 범용 레지스터, 하나의 읽기 전용 스택 포인터를 가지며 복잡한 주소 지정 모드가 없는 로드-스토어 아키텍처를 사용합니다.

이러한 단순성은 의도적입니다: 더 적은 명령어 변형은 더 빠른 검증, 더 빠른 JIT 컴파일 및 더 예측 가능한 성능을 가능하게 합니다.

eBPF 프로그램이 kernel에 로드될 때마다, 바이트코드는 JIT 컴파일러에 의해 호스트 CPU 아키텍처에 특화된 네이티브 머신 명령어로 번역된 다음 VM에 의해 실행됩니다.

### 실행

sBPF 프로그램은 간단한 프로세스를 통해 실행됩니다. 프로그램 카운터(`PC`)는 다음에 실행할 명령어를 추적합니다. 마치 명령어 목록의 북마크처럼 말이죠.

실행 주기는 다음 단계를 따릅니다:
1. **가져오기(Fetch)**: 프로그램 카운터의 명령어 읽기
2. **디코드(Decode)**: 명령어 형식과 operand 해석
3. **실행(Execute)**: 연산 수행 (레지스터 수정, 메모리 접근, 또는 제어 흐름 변경)
4. **진행(Advance)**: 프로그램 카운터를 다음 명령어로 이동 (또는 분기를 위해 점프)
5. **반복(Repeat)**: 프로그램이 종료될 때까지 계속

각 명령어는 산술, 메모리 접근, 비교 또는 함수 호출 중 정확히 하나의 연산을 수행합니다. 이러한 '연산당 하나의 명령어' 설계는 sBPF 프로그램을 예측 가능하고 분석 가능하게 만듭니다.

<ArticleSection name="JIT 컴파일러 파이프라인" id="the-jit-compiler-pipeline" level="h2" />

sBPF 프로그램은 Just-In-Time (JIT) 컴파일을 통해 높은 성능을 달성합니다.

Solana에 프로그램을 배포할 때, 런타임은 두 가지 작업을 수행합니다:
- **검증(Verification)**: 무한 루프, 유효하지 않은 메모리 접근, 잠재적 크래시를 확인하여 프로그램 안전을 보장합니다. 검증기는 모든 가능한 실행 경로를 분석하여 안전한 작동을 보장합니다.
- **컴파일(Compilation)**: sBPF 명령어를 validator의 CPU에서 직접 실행되는 네이티브 머신 코드로 변환합니다. `add64 r1, r2`와 같은 간단한 연산은 단일 네이티브 add 명령어가 되며, 복잡한 연산은 추가 안전 검사를 받지만 여전히 효율적인 네이티브 코드로 컴파일됩니다.

이 접근 방식은 배포 시간을 실행 속도와 교환합니다. 프로그램은 배포 시 한 번 검증되고 컴파일되지만 수천 번 실행되므로, 블록체인 성능을 위한 훌륭한 trade-off입니다.

JIT 검증 프로세스는 가능한 모든 프로그램 경로를 검토하여 메모리 접근이 범위를 벗어나지 않고, 점프가 유효한 주소를 대상으로 하며, 실행이 compute limits 내에서 종료되는지 확인합니다.

JIT 컴파일 프로세스는 각 sBPF 명령어를 동등한 네이티브 CPU 명령어로 번역합니다. 대부분의 실행이 네이티브 코드에서 발생하므로 가상 머신 오버헤드는 최소화됩니다.

> sBPF가 네이티브 코드로 컴파일된다는 것을 이해하면 산술 연산이 빠른 반면 런타임으로 넘어가는 syscall에는 오버헤드가 발생하는 이유를 설명할 수 있습니다. 이러한 지식은 최적화 결정에 도움이 됩니다.

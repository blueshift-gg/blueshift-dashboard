# sBPF Асемблер 101

Щоб зрозуміти sBPF Асемблер та його роль у програмах Solana, нам спочатку потрібно зрозуміти мову асемблера та те, як вона поєднує високорівневий код з машинним виконанням.

<ArticleSection name="Мова асемблера" id="the-assembly-language" level="h2" />

Асемблер — це зрозуміла для людини форма машинного коду: фактичні інструкції виконуються процесорами. Він служить містоком між мовами програмування високого рівня та двійковим кодом, який розуміють комп'ютери.

Коли ви пишете код Rust, наприклад:

```rust
let result = a + b;
```

Компілятор перетворює це через кілька етапів:
1. Вихідний код Rust → розібраний та проаналізований
2. Проміжне представлення → оптимізоване
3. Код асемблера → інструкції, що читаються людиною
4. Машинний код → двійковий файл, який виконує процесор

Асемблер займає етап 3: остаточна форма, що читається людиною, перед перетворенням у двійковий файл. Кожна інструкція асемблера відповідає рівно одній операції процесора: додаванню чисел, завантаженню пам'яті або переходу до різних розділів коду.

<ArticleSection name="Віртуальна Машина sBPF" id="the-sbpf-virtual-machine" level="h2" />

Solana sBPF — це спеціалізований варіант Solana розширеного набору інструкцій Berkeley Packet Filter (eBPF) та віртуальної машини, яка виконує кожну програму в ланцюжку. Він створює спеціалізоване середовище виконання: 64-бітну реєстрову машину, яка знаходиться між вашою програмою та власним процесором валідатора.

Уявіть собі sBPF як спеціально створений комп'ютер, призначений для виконання блокчейну: достатньо швидкий для високопродуктивних транзакцій, але достатньо обмежений, щоб гарантувати безпеку та детермінізм для тисяч валідаторів.

На відміну від власної асемблерної програми, яка працює безпосередньо на вашому процесорі, код sBPF виконується в контрольованому середовищі віртуальної машини. Ця віртуальна машина гарантує безпеку, перевіряючи кожну інструкцію перед виконанням, запобігаючи збоям, нескінченним циклам та несанкціонованому доступу до пам'яті.

Незважаючи на ці обмеження безпеки, sBPF підтримує високу продуктивність завдяки компіляції «точно вчасно», яка досягає швидкості виконання, майже нативної.

Віртуальна машина також забезпечує детерміноване виконання: ідентичні програми з ідентичними вхідними даними дають ідентичні результати для всіх валідаторів по всьому світу. Ця узгодженість є критично важливою для консенсусу блокчейну.

Крім того, sBPF включає системні виклики для доступу до облікових записів, міжпрограмних викликів та взаємодії під час виконання.

### Чому важливе розуміння асемблерного коду sBPF

Хоча компілятор Rust ефективно перетворює високорівневий код на інструкції sBPF, розуміння асемблерного коду надає кілька переваг:
**Розуміння обчислювальних витрат**: Кожна інструкція sBPF споживає обчислювальні одиниці (CU). Один рядок Rust може скомпілюватися в сотні інструкцій — асемблерний код показує, чому певні операції є дорогими.
**Менші розміри програм**: Програми, написані безпосередньо на асемблерному коді sBPF, значно менші за скомпільовані еквіваленти Rust, що зменшує витрати на розгортання та покращує час завантаження.
**Можливості оптимізації**: Компілятор Rust генерує безпечний, правильний код, але не завжди найефективніший. Асемблерний код надає надлишкові перевірки безпеки та неоптимальні послідовності інструкцій.
**Налагодження та аналіз**: Коли програми поводяться несподівано, асемблерний код надає основну інформацію. Ви можете точно відстежити, які інструкції виконувалися, та виявити точки збою.

### Архітектура

sBPF використовує архітектуру завантаження-збереження з 10 регістрами загального призначення, одним покажчиком стека лише для читання та відсутністю складних режимів адресації.

Ця простота навмисна: менше варіантів інструкцій забезпечує швидшу перевірку, швидшу JIT-компіляцію та більш передбачувану продуктивність.

Щоразу, коли програма eBPF завантажується в ядро, її байт-код перетворюється JIT-компілятором на власні машинні інструкції, специфічні для архітектури центрального процесора, а потім виконується віртуальною машиною.

### Виконання

Програми sBPF виконуються за допомогою простого процесу. Лічильник програм (`PC`) відстежує, яку інструкцію виконувати наступною, як закладку у вашому списку інструкцій.

Цикл виконання виконує такі кроки:
1. **Вибірка**: Зчитування інструкції з лічильника програм
2. **Декодування**: Інтерпретація формату інструкції та операндів
3. **Виконання**: Виконання операції (зміна регістрів, доступ до пам'яті або зміна потоку керування)
4. **Перехід**: Переміщення лічильника програм до наступної інструкції (або перехід для переходів)
5. **Повторення**: Продовження до завершення роботи програми

Кожна інструкція виконує рівно одну операцію: арифметичну, доступ до пам'яті, порівняння або виклик функції. Така конструкція з однією інструкцією на операцію робить програми sBPF передбачуваними та аналітичними.

<ArticleSection name="Конвеєр JIT-компілятора" id="the-jit-compiler-pipeline" level="h2" />

Програми sBPF досягають високої продуктивності завдяки компіляції Just-In-Time (JIT).

Коли ви розгортаєте програму в Solana, середовище виконання виконує дві операції:
- **Верифікація**: Забезпечує безпеку програми, перевіряючи наявність нескінченних циклів, недійсного доступу до пам'яті та потенційних збоїв. Верифікатор аналізує кожен можливий шлях виконання, щоб гарантувати безпечну роботу.
- **Компіляція**: Перетворює інструкції sBPF у власний машинний код, який виконується безпосередньо на процесорі валідатора. Прості операції, такі як `add64 r1, r2`, стають окремими власними інструкціями додавання, тоді як складні операції отримують додаткові перевірки безпеки, але все ще компілюються в ефективний власний код.

Цей підхід жертвує часом розгортання заради швидкості виконання. Програми перевіряються та компілюються один раз під час розгортання, але виконуються тисячі разів, що робить це чудовим компромісом для продуктивності блокчейну.

Процес JIT-верифікації проходить через кожен можливий шлях програми, перевіряючи, чи доступ до пам'яті залишається в межах дозволених значень, чи перехід здійснюється за дійсними адресами, а виконання завершується в межах обчислювальних обмежень.

Процес JIT-компіляції перетворює кожну інструкцію sBPF на еквівалентні власні інструкції процесора. Оскільки більшість виконання відбувається в нативному коді, накладні витрати на віртуальну машину мінімальні.

> Розуміння того, що sBPF компілюється в нативний код, пояснює, чому арифметичні операції виконуються швидко, тоді як системні виклики, що перетинаються в середовищі виконання, мають накладні витрати. Ці знання спрямовують рішення щодо оптимізації.

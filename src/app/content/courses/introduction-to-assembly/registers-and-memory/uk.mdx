# Регістри sBPF та модель пам'яті

Коли ваша програма sBPF виконується, вона працює з двома основними механізмами зберігання: 11 високошвидкісними регістрами, вбудованими в процесор, та організованими областями пам'яті, які містять усе інше.

<ArticleSection name="Регістри" id="registers" level="h2" />

Регістри подібні до 11 пронумерованих слотів пам'яті (від `r0` до `r10`), вбудованих безпосередньо в процесор. Кожен з них містить одне 64-бітове значення та забезпечує миттєвий доступ без затримок. Коли ви виконуєте `add64 r1, r2`, процесор негайно отримує значення з обох регістрів та виконує обчислення.

Компроміс простий: ви отримуєте лише 11 полів загалом, тому вам потрібно використовувати їх стратегічно для значень, з якими ви активно працюєте.

sBPF призначає кожному регістру певні ролі:

| Реєстр   | Роль                      | Збережено викликаним? | Нотатки щодо використання                                        |
|----------|---------------------------|-----------------------|------------------------------------------------------------------|
| `r0`     | Значення, що повертається | Ні                    | Результати функції, значення, що повертаються системним викликом |
| `r1`     | Вказівник вхідного буфера | Ні                    | Вказує на 0x400000000 при вході                                  |
| `r2-r5`  | Скретч/аргументи          | Ні                    | Аргументи допоміжних функцій, тимчасові значення                 |
| `r6-r9`  | Загальне призначення      | Так                   | Повинно зберігатися під час викликів                             |
| `r10`    | Вказівник фрейму          | Так, лише для читання | База стеку, не можна змінювати безпосередньо                     |

Регістри з `r6` по `r9` "збережені викликаним користувачем", тобто їхні значення зберігаються під час викликів функцій. Використовуйте їх для важливих даних, які мають пережити виклики функцій.

Решта регістрів (`r0`-`r5`) перезаписуються під час системних викликів та викликів функцій.

Регістр `r10` є "спеціальним", оскільки він служить вказівником фрейму, вказуючи на базу простору стеку та залишаючись доступним лише для читання. Ви отримуєте доступ до змінних стеку, використовуючи від'ємні зміщення, такі як `[r10 - 8]` та `[r10 - 16]`.

<ArticleSection name="Пам'ять" id="memory" level="h2" />

У той час як регістри зберігають активно використовувані значення, пам'ять зберігає все інше. sBPF організовує пам'ять у фіксовані області з однаковим розташуванням елементів у всіх програмах:

| Регіон | Початкова адреса | Призначення                  | Розмір/Примітки         |
|--------|------------------|------------------------------|-------------------------|
| Текст  | 0x100000000      | Код та дані лише для читання | Бінарний файл програми  |
| Стек   | 0x200000000      | Локальні змінні              | 32 КіБ, зростає вниз    |
| Купа   | 0x300000000      | Динамічне розподілення       | Через `sol_alloc_free`  |
| Вхід   | 0x400000000      | Параметри програми           | Серіалізовані аргументи |

- **Текстова область** містить ваш виконуваний код та дані лише для читання, такі як рядкові константи. Дані, визначені за допомогою директив `.quad`, зазвичай знаходяться тут.
- **Регіон стека** містить локальні змінні. Коли `r10` вказує на базу стеку, ви отримуєте доступ до локальних змінних, використовуючи від'ємні зміщення: `[r10 - 16]`, `[r10 - 24]` тощо. Стек обмежений загальним розміром 32 КіБ.
- **Вхідна область** містить параметри вашої програми. При вході `r1` вказує на цю область (`0x400000000`), що дозволяє вам зчитувати серіалізовані дані облікового запису та параметри інструкцій, що передаються вашій програмі.

Це фіксоване розташування забезпечує три ключові переваги: безпеку завдяки ізоляції пам'яті між програмами, детермінізм з ідентичними адресами для всіх валідаторів та продуктивність завдяки оптимізації компілятора для відомих розташувань.

> Спроба доступу до невідображених адрес викликає порушення доступу (AccessViolation), і транзакція завершується невдачею.

<ArticleSection name="Використання Регістрів та Пам'яті" id="using-registers-and-memory" level="h2" />

Ось як регістри та пам'ять працюють разом на практиці:

```sbpf
.globl entrypoint
entrypoint:
    # On entry: r1 points to input data at 0x400000000
    
    ldxdw r0, [r1 + 0]      # Load first 8 bytes from input into r0
    mov64 r2, 42            # Put 42 in register r2
    add64 r0, r2            # Add them: r0 = r0 + r2
    
    stxdw [r10 - 8], r0     # Store result on stack
    mov64 r0, 0             # Return success
    exit
```

Ця програма демонструє типовий шаблон:
- Використовує регістр `r1` (вхідний покажчик) для читання з пам'яті
- Використовує регістри `r0` та `r2` для обчислень
- Використовує регістр `r10` (вказівник кадру) для доступу до стекової пам'яті
- Повертає результат у регістр `r0`

Робочий процес дотримується послідовного шаблону: завантаження даних з пам'яті в регістри, виконання обчислень з регістрами, а потім збереження результатів назад у пам'ять, коли це необхідно.

### Використання Стеку

Стек працює з `r10` як покажчиком кадру, що вказує на основу поточного кадру стеку (найвища адреса). Локальні змінні використовують від'ємні зміщення:

```sbpf
# Store a value on the stack
mov64 r0, 42
stxdw [r10 - 8], r0         ; Store at first stack slot

# Load it back
ldxdw r1, [r10 - 8]         ; Load from first stack slot
```

Слоти стеку зазвичай мають ширину 8 байтів, тому послідовні змінні використовують зміщення, такі як `[r10 - 8]`, `[r10 - 16]`, `[r10 - 24]` тощо.

### Вхід та вихід з програми

Ваша програма починає виконання з символу, позначеного `.globl` (зазвичай точка входу). Початковий стан регістра мінімальний та передбачуваний:

```sbpf
.globl entrypoint
entrypoint:
    # On entry:
    # r1 = 0x400000000 (input buffer pointer)
    # r0, r2-r10 = 0 (all other registers zeroed)

    # Your program logic here

    mov64 r0, 0     # Success code (0 = SUCCESS)
    exit            # Return to runtime
```

Поведінка при виході залежить від глибини виклику:
- На глибині виклику 0, exit завершує програму з кодом результату `r0`.
- На глибших рівнях виклику, exit діє як оператор return, відновлюючи збережені викликаючою стороною регістри (`r6`-`r9`) та вказівник фрейму викликаючої сторони (`r10`) перед продовженням виконання за адресою повернення.

Середовище виконання автоматично обробляє налаштування та завершення роботи за допомогою неявного коду прологу та епілогу, включаючи початкове налаштування стану регістрів та остаточну обробку повернення.

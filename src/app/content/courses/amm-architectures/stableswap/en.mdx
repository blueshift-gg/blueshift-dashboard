# StableSwap

In January 2020, Michael Egorov launched Curve Finance with a [whitepaper](https://berkeley-defi.github.io/assets/material/StableSwap.pdf) that solved a specific problem: constant product AMMs are terrible for stablecoins.

If USDC and USDT should both be worth $1, why is there slippage?

Curve's StableSwap invariant changed everything and today, they handles billions in stablecoin volume.

<ArticleSection name="The Problem with Constant Product" id="the-problem" level="h2" />

### Why `x * y = k` doesn't work for Stablecoins

Consider a USDC/USDT pool with $2M liquidity (1M USDC, 1M USDT):

```
Constant Product: x * y = k
1,000,000 * 1,000,000 = 1,000,000,000,000

Swap 100,000 USDC for USDT:
New USDC: 1,100,000
New USDT: k / 1,100,000 = 909,091
USDT received: 1,000,000 - 909,091 = 90,909

Expected: 100,000 USDT
Actual: 90,909 USDT
Slippage: 9.1%
```

A 9% loss to swap two assets that should be identical in value.

### The Mathematical Reason

Constant product creates a hyperbolic curve where the center (for balanced pool), it's relatively flat. But it curves away quickly:

```
Price impact = (amount_in / reserve_in) * 100%

For 10% of pool size:
- 10% input → ~9% slippage
- Scales roughly linearly
```

The curve treats USDC and USDT as if they could have any price ratio, providing liquidity for scenarios where USDC could be worth 10x USDT or vice versa.

<ArticleSection name="The StableSwap Insight" id="insight" level="h2" />

### Two Extreme Curves

Consider two formulas:

**Constant Sum**: `x + y = k`
- Zero slippage: 1 USDC always equals exactly 1 USDT
- Problem: Pool can be completely drained. If 1M USDC in pool, someone can take all of it for 1M USDT.

**Constant Product**: `x * y = k`
- Infinite liquidity: Pool can never be fully drained
- Problem: High slippage, even for pegged assets

What if there was a way to blend them?

### The StableSwap Invariant

Curve created a formula that behaves like constant sum near the center (low slippage) but like constant product at the extremes (can't be drained).

The invariant for two tokens:

```
A * n^n * (x + y) + D = A * D * n^n + D^(n+1) / (n^n * x * y)

Where:
- x, y = token reserves
- n = number of tokens (2 for pairs)
- D = total value when pool is balanced
- A = amplification parameter (determines curve shape)
```

This looks complex. Let's break it down.

### Understanding the Amplification Parameter (A)

The amplification parameter `A` controls how "stable" the curve is:
- **A = 0**: Pure constant product (x*y=k)
- **A = ∞**: Pure constant sum (x+y=k)
- **A = 100-2000**: Typical range for stablecoin pools

```
Low A (10):
- More curved, approaches constant product
- Higher slippage, but safer during depegs
- Better for loosely pegged assets

High A (2000):
- Very flat, approaches constant sum
- Near-zero slippage within range
- Dangerous if assets depeg significantly
```

### Visualizing the Curve

```
                    Constant Sum (x+y=k)
                    /
                   /
                  /     StableSwap curve
                 /     /   (high A)
                /    /
               /   /
              /  /
             / /
            /------------ Constant Product (x*y=k)
           /
```

When both stable's are in equal liqudiity, the curve StableSwap follows the constant sum formula providing low slippage. 

As imbalance between assets grows, it bends toward the constant product formula so it can't be drained and arbitrageurs are incentivesed to rebalance it.

<ArticleSection name="The Math Deep Dive" id="math" level="h2" />

### Simplified Two-Token Formula

For a two-token pool, the StableSwap invariant simplifies to:

```
A * 4 * (x + y) + D = A * D * 4 + D³ / (4 * x * y)
```

Rearranging to solve for the output amount when swapping:

```
Given: swap dx of token X for token Y
Find: dy (amount of Y received)

1. Calculate new x: x_new = x + dx
2. Solve invariant for y_new (requires iteration)
3. dy = y - y_new
```

### Newton's Method for Solving

Since the invariant can't be solved algebraically for y, the implementations must use Newton's method:

```rust
fn get_y(x_new: u128, d: u128, a: u128) -> u128 {
    // StableSwap invariant rearranged for y
    // A * 4 * (x + y) + D = A * D * 4 + D³ / (4 * x * y)
    
    let ann = a * 4; // A * n^n where n=2
    
    // Initial guess
    let mut y = d;
    
    // Newton's method iteration
    for _ in 0..256 {
        let y_prev = y;
        
        // f(y) and f'(y) for Newton's method
        let numerator = y * y + (ann * x_new + d * d * d / (4 * x_new) - ann * d - y);
        let denominator = 2 * y + ann * x_new / d - d * d / (4 * x_new * y) - 1;
        
        y = y - numerator / denominator;
        
        // Convergence check
        if y.abs_diff(y_prev) <= 1 {
            break;
        }
    }
    
    y
}
```

### Computing D (Invariant Value)

When the pool is balanced (equal values of each token), D equals the total value. Computing D also requires using the Newton method:

```rust
fn get_d(reserves: &[u128], a: u128) -> u128 {
    let n = reserves.len() as u128;
    let sum: u128 = reserves.iter().sum();
    
    if sum == 0 {
        return 0;
    }
    
    let ann = a * n.pow(n as u32);
    let mut d = sum;
    
    for _ in 0..256 {
        let d_prev = d;
        
        // D_P = D^(n+1) / (n^n * prod(reserves))
        let mut d_p = d;
        for reserve in reserves {
            d_p = d_p * d / (reserve * n);
        }
        
        // Newton's method
        let numerator = (ann * sum + d_p * n) * d;
        let denominator = (ann - 1) * d + (n + 1) * d_p;
        d = numerator / denominator;
        
        if d.abs_diff(d_prev) <= 1 {
            break;
        }
    }
    
    d
}
```

### Real Numbers

Same scenario: $2M pool, swap 100,000 USDC for USDT:

**Constant Product (A=0)**:
```
Slippage: 9.1%
Received: 90,909 USDT
```

**StableSwap (A=100)**:
```
Slippage: 0.15%
Received: 99,850 USDT
```

**StableSwap (A=1000)**:
```
Slippage: 0.015%
Received: 99,985 USDT
```

For stablecoin, using the StableSwap formula, swapping is 100-1000x more efficient.

StableSwap maintains low slippage for much larger trades.

<ArticleSection name="The Depeg Problem" id="depeg" level="h2" />

Using an high `A` values helps out with slippage but assume assets stay pegged. When they don't, interesting dynamics emerge.

**March 2023: USDC Depeg**

Silicon Valley Bank collapsed, Circle had $3.3B in deposits there. Market thought there would be some contagions so USDC traded at $0.87 on external markets.

What happened in Curve pools:

```
Pool: 1M USDC, 1M USDT (A=1000)
External price: USDC = $0.87

Arbitrageur buys USDC at $0.87 on Coinbase
Swaps in Curve pool: 100K USDC → ~99.5K USDT (0.5% slippage)
Profit: $12,000 per 100K swapped

Even as pool becomes 1.5M USDC / 0.5M USDT:
- Curve still offers ~0.95 USDT per USDC
- External market: 0.87 USDT per USDC
- Arbitrage remains profitable → dumping continues
```

The flat curve keeps offering near-1:1 rates while external markets price USDC at a discount. Arbitrageurs continued to drain USDT until the curve step enough that pool price matches external price.

### The LP Perspective

The problem was that LPs effectively bought USDC at pool prices (~$0.95-0.99) while it was worth $0.87 externally.

**If the peg recovers** (like USDC did): LPs are fine. They hold USDC that's now worth $1 again and the temporary imbalance reverses.

**If the peg fails permanently** (like UST): LPs are holding a worthless asset they bought at near-par creating a catastrophic loss.

The USDC depeg recovered within days so LPs who didn't panic-withdraw were made whole. But the risk was real, if Circle had been insolvent, those LPs would have been devastated.

### Mitigation Strategies

**1. Lower A Values**

With a lower value of A, the pool would have reached the external market price sooner, limiting LP exposure.

**2. Oracle Integration**

If we had an oracle that monitored external prices, we could have caught the depeg and:
- Pause swaps entirely
- Dynamically lower A
- Adjust virtual price to reflect reality

```rust
fn check_depeg(oracle_price: u64, pool_price: u64, threshold_bps: u64) -> bool {
    let diff = if oracle_price > pool_price {
        oracle_price - pool_price
    } else {
        pool_price - oracle_price
    };
    diff * 10_000 / oracle_price > threshold_bps
}
```

**3. Volume Limits**

With a cap how much can be swapped per block or per time window we could have stopped and protect the LP against the arbitrage drainage.

But this is not a good experience for 99.9% of the time since stables usually do a lot of intraday volume

**4. Circuit Breakers**

By adding a circuit breaker that triggered if imbalance exceeds threshold (e.g., 80/20 ratio), we could have paused swaps or require governance intervention.

This is a good mitigation, but setting a parameter that meaningfully protect LPs while not disrupting normal trading is extremely complex.

<ArticleSection name="Multi-Token Pools" id="multi-token" level="h2" />

The StableSwap invariant can be generalized to n tokens:

```
A * n^n * Σ(x_i) + D = A * D * n^n + D^(n+1) / (n^n * Π(x_i))
```

This means that with this formula we could:
- Trade any stablecoin for any other in one swap
- Create a deeper combined liquidity
- Single LP token for multi-asset exposure

For example, this is extremely useful when launching a new stablecoin. To be usble, it needs deep liquidity against USDC, USDT, and any other stablecoin that has meaningful usage across the ecosystem. 

Creating separate pairs for each, fragments liquidity. Creating a pool that serves all of this helps since it concentrates liquidity while enabling trading against all major stablecoins.

<ArticleSection name="Implementations" id="implementations" level="h2" />

### Implementation Considerations

**Precision**: StableSwap math requires high precision. Use u128 or u256 for intermediate calculations.

**Iteration limits**: Newton's method must converge. Set reasonable iteration limits (256 is common).

**A parameter changes**: Never change A instantly. Ramp over hours/days to prevent manipulation (see Dynamic A in the Depeg section above).

<ArticleSection name="When to Use StableSwap" id="when-to-use" level="h2" />

### Ideal Use Cases

**Stablecoins**: USDC/USDT, DAI/USDC, any dollar-pegged assets
**Wrapped assets**: wBTC variants, bridged tokens that should be 1:1
**Liquid staking tokens**: stETH/ETH, mSOL/SOL, jitoSOL/SOL
**Synthetic assets**: Synths pegged to the same underlying

### The Rule of Thumb

> Use StableSwap when you believe the assets should trade 1:1 (or at a fixed ratio) and will continue to do so.

If there's meaningful probability of permanent depeg, the efficiency gains aren't worth the risk.

<ArticleSection name="Key Takeaways" id="takeaways" level="h2" />

1. **StableSwap blends constant sum and constant product** to optimize for pegged assets
2. **The amplification parameter (A)** controls the tradeoff between efficiency and depeg protection
3. **Higher A = lower slippage** but more risk during depegs
4. **Newton's method** is required to solve the invariant, both for swaps and computing D
5. **Choose A carefully** based on asset stability and risk tolerance
6. **Multi-token pools** concentrate liquidity across many stablecoins

StableSwap solved stablecoin trading. But for volatile assets, we need a different approach: concentrating liquidity where it's actually used.

# Emerging Designs

AMM design hasn't stopped evolving. New architectures are emerging that blend elements from existing models, introduce novel mechanisms, or solve problems we didn't know we had.

This lesson covers the frontier: dynamic fees, proactive market making, intent-based systems, and hybrid designs that blur the line between AMMs and order books.

<ArticleSection name="Dynamic Fee AMMs" id="dynamic-fees" level="h2" />

Traditional AMMs have fixed fees (0.3%, 0.05%, etc.). But optimal fees depend on conditions:

### Volatility-based Fees

Some protocols adjust fees based on recent volatility:

```
Low volatility:
- Arbitrage is cheap
- Lower fees capture more volume
- Optimal: 0.01-0.05%

High volatility:
- Large price swings
- LPs need more compensation for IL
- Optimal: 0.3-1%
```

### Utilization-Based Fees

Some protocols adjust fees based on pool utilization:

```
Pool heavily used (many swaps):
- LPs are valuable, demand is high
- Increase fees

Pool idle:
- Need to attract volume
- Decrease fees
```

### Time-Weighted Dynamic Fees

To prevent fee manipulation, dynamic fees should be implemented by averaging over time:

```rust
struct FeeState {
    accumulated_fee: u128,
    last_update: i64,
    twap_fee: u64,
}

fn update_fee_twap(
    state: &mut FeeState,
    current_fee: u64,
    current_time: i64,
) {
    let time_elapsed = current_time - state.last_update;
    
    state.accumulated_fee += state.twap_fee as u128 * time_elapsed as u128;
    state.accumulated_fee += current_fee as u128;
    
    state.twap_fee = (state.accumulated_fee / (current_time - TWAP_START)) as u64;
    state.last_update = current_time;
}
```

<ArticleSection name="Proactive Market Making (PropAMMs)" id="proactive-mm" level="h2" />

Oracle AMMs solved the stale pricing problem by using external price feeds, but they're still passive: they wait for trades to come.

PropAMMs take this further: they actively manage their positions like a professional market maker would.

### The Problem With Passive LPs

Even in oracle AMMs, LPs are passive:

```
Oracle AMM LP:
  Deposit liquidity
  Wait for trades
  Collect fees
  Hope you don't get rekt by inventory imbalance

Professional market maker:
  Continuously adjust quotes based on:
    - Order flow analysis
    - Inventory position
    - Volatility regime
    - Cross-venue arbitrage opportunities
  Actively hedge exposure
```

### How PropAMMs Work

A PropAMM doesn't just price at oracle ± spread. It actively manages three things:

**1. Predictive Pricing**: Instead of using a fixed spread around the oracle price, PropAMMs analyze recent order flow and market conditions to adjust their quotes. If buy pressure is increasing, they quote slightly higher. If volatility is spiking, they widen the spread. The goal is to anticipate where the market is heading, not just react to where it's been.

**2. Inventory Management**: When a pool accumulates too much of one asset, a passive AMM just waits and hopes someone comes to rebalance it. A PropAMM actively skews its quotes to incentivize the trades it wants. If it's long SOL, it makes SOL cheaper to buy and more expensive to sell. Some PropAMMs even hedge their exposure on external venues like CEXs or perp markets.

**3. Flow Toxicity Detection**: Not all trades are equal. Arbitrage bots and MEV searchers are "informed" traders who extract value. Retail swappers are "uninformed" and represent profitable flow. PropAMMs try to distinguish between them - widening spreads or rejecting toxic flow while offering tight spreads to capture uninformed volume.

### The Technical Implementation

PropAMMs require more infrastructure than passive AMMs:

1. Price feed (Pyth, Switchboard)
2. Order flow analysis (recent trades, pending txs)
3. Volatility model (realized vol, implied vol)
4. Inventory tracker (current vs target allocation)
5. Execution layer (quote engine, hedging)

But most importantly, the key PropAMM technique is to adjust mid price based on inventory:

```
Target: 50% SOL, 50% USDC
Current: 60% SOL, 40% USDC (long SOL)

Standard AMM:
  Mid = oracle price ($100)
  Bid = $99.90, Ask = $100.10

PropAMM with inventory skew:
  Mid = oracle price - skew
  Skew = f(inventory imbalance) = $0.20
  
  Effective mid = $99.80
  Bid = $99.70, Ask = $99.90
  
Result:
  Cheaper for traders to buy SOL (helps you rebalance)
  More expensive to sell SOL (don't want more)
```

<ArticleSection name="Intent-Based Systems" id="intents" level="h2" />

### What Are Intents?

Instead of specifying the exact action to perform, users specify what they want:

```
Traditional:
"Swap 100 USDC for SOL on Raydium..."

Intent:
"I want to trade 100 USDC for SOL, best price within 1 minute"
```

And a network of "solvers" competes to fulfill the intent optimally.

### How Intent Systems Work

```
1. User signs intent: "Swap X for Y, min output Z"
2. Intent goes to solver network
3. Solvers compete to fill:
   - Direct AMM execution
   - Aggregation across AMMs
   - OTC/RFQ matching
   - Any combination
4. Best solution wins
5. User gets result
```

Intents help AMMs because of:
- **MEV protection**: Solvers compete, reducing sandwich attacks
- **Price improvement**: Solvers find best routes across all liquidity
- **Abstraction**: Users don't need to know AMM mechanics

### Request for Quote (RFQ)

Related to intents is RFQ (Request for Quote), where users request quotes from market makers:

```
1. User: "I want to buy 100 SOL"
2. Market makers respond with quotes
3. User accepts best quote
4. Atomic settlement

Benefits:
- Zero slippage (quote is guaranteed)
- MEV protected (private quotes)
- Large trades without moving AMM price
```

<ArticleSection name="Key Takeaways" id="takeaways" level="h2" />

1. **Dynamic fees** adjust to market conditions (volatility, utilization)
2. **Proactive market making** anticipates prices instead of reacting
3. **Intent-based systems** let solvers optimize execution for users
4. **Hybrid designs** combine order books with AMM liquidity

The AMM space continues to evolve. The designs that win will balance capital efficiency, LP returns, trader experience, and MEV resistance. No single design solves everything—every approach has tradeoffs.

# Oracle-Integrated AMMs

Every AMM we've covered has the same problem: toxic flow. 

Since the pool is uninformed, it only knows what its reserves say, arbitrageurs, that are informed trader that know the true market price, can extracts significant value from LPs.

This is because the pricin model for traditional AMMs is reactive since they are based on a simple constante curve, trades move the price. This creates a window where the pool price is stale.

<ArticleSection name="How Oracle AMMs Work" id="how-it-works" level="h2" />

Most price discovery doesn't happen onchain but on centralized exchanges and oracles like Pyth already aggregate those prices.

So why calculate price from reserves when you can just use the oracle?

Lifinity (Solana, 2021) pioneered this approach, but the mechanics apply to any oracle-integrated AMM.

### The Core Idea

An oracle AMM is still an AMM since it does real token swaps, but instead of deriving price from `x * y = k`, it uses the oracle price as its reference point.

```
Traditional AMM:
  Price = f(reserves)
  SOL/USDC pool with 10,000 SOL and 1,000,000 USDC
  Price = 1,000,000 / 10,000 = $100
  
  Problem: This price is stale until arbitrageurs fix it

Lifinity:
  Price = oracle price ± spread
  Pyth says SOL = $120
  Lifinity quotes: Buy at $120.12, Sell at $119.88
  
  Price is always current. No stale window to exploit.
```

To do that, under the hood the Oracle AMM is a CPAMM that concentrates the liquidity around the oracle price.

### The Oracle-Based Curve

Even if the pricing is made by the oracle, you still need a curve. This is because if you just say "everything trades at oracle price" there's no slippage, and no slippage means that large trades would just drain the pool.

The solution to this problem is to just use a constant product curve, but **re-center it around the oracle price**.

```
Traditional CPAMM:
  x * y = k
  Price derived from reserves: P = y/x
  
  If reserves are 1000 SOL and 100,000 USDC:
  Price = 100,000/1000 = $100
  
  Problem: This price is stale until arbs fix it.

Oracle-AMM's approach:
  Still uses x * y = k for slippage calculation
  But the "virtual" reserves are adjusted so the curve's
  price matches the oracle price.
  
  Oracle says: SOL = $120
  Lifinity adjusts virtual reserves so curve price = $120
  Trades execute along this re-centered curve
```

This is easily done by creating "virtual reserves" that would put the CPAMM price at 100$. 

The depth of this "virtual reserves" are created based on the actual spread that the pool wants to use.

```
Oracle price: $100

Shallow virtual reserves:
  100 SOL / 10,000 USDC
  k = 1,000,000
  
Deep virtual reserves:
  10,000 SOL / 1,000,000 USDC
  k = 10,000,000,000
```

Both price are the same, but if we try to buy 10SOL we would have 5% of price impact in the shallow pool against the 0.1% of the deep pool.

> The virtual depth is adjust based on different parameters like oracle confidence or volatilty.

### How Fees Work

Every trade pays a fee. In Oracle AMMs, fees come from two sources:

**1. Base trading fee**: A percentage of each trade (e.g., 0.3%)

**2. Price impact (slippage)**: The difference between oracle price and execution price

```
Trade: Buy 100 SOL

Oracle price: $100
Virtual reserves: 10,000 SOL / 1,000,000 USDC

Execution:
  Average price paid: $100.50
  Price impact: $0.50 per SOL = 0.5%
  
Total cost to trader: $10,050
  Base fee (0.3%): $30
  Price impact: $50
  
LPs receive: The $50 price impact + their share of the $30 fee
```

Since the slippage goes to LPs, deeper virtual reserves mean less slippage revenue but it puts the AMM at more competitive pricing.

### Inventory Risk

Unlike traditional AMMs where arbitrageurs force rebalance the LPs at bad prices, Oracle-AMM LPs face a different dynamic:

```
SOL pumps from $100 to $150:

Traditional AMM:
  Arbs bought your SOL at $100-$140
  You sold all the way up at bad prices
  Pool rebalanced, you have less SOL

Lifinity:
  Oracle updates to $150
  Pool prices at $150 immediately
  Normal traders might buy SOL at $150+slippage
  You sell at fair price, not stale price
```

You still sell SOL as price rises (that's how AMMs work), but you sell at current market price, not stale prices. The toxic flow is eliminated, but the inventory risk remains since you'll end up with less SOL after a pump.

<ArticleSection name="Key Takeaways" id="takeaways" level="h2" />

Oracle AMMs like Lifinity solve a specific problem: toxic flow.

```
The problem:
  Traditional AMMs derive price from reserves
  This creates a lag vs. external markets
  Arbitrageurs exploit the lag
  LPs get extracted in BOTH directions

The solution:
  Use oracle price instead of reserve-derived price
  No lag = no arbitrage opportunity
  LPs keep their fees without extraction
```

The key insights:

1. **Proactive vs Reactive**: Traditional AMMs wait for trades to update price. Oracle AMMs update price proactively from external feeds.

2. **Concentrated + Oracle**: Oracle-AMM combines oracle pricing with concentrated liquidity around the oracle price. Capital efficient AND no stale pricing.

3. **Dynamic Spreads**: Widen spreads during uncertainty (low oracle confidence) and volatility. This is how traditional market makers work.

4. **Oracle Risk**: You're trading toxic flow risk for oracle risk. Manipulation is rare but catastrophic so use multiple oracles, staleness checks, and confidence intervals.

5. **Not for everything**: Oracle AMMs only work for assets with reliable oracle feeds.

Lifinity proved this model works on Solana. By using Pyth for pricing and concentrating liquidity around the oracle price, they eliminated the toxic flow that plagues traditional AMMs.

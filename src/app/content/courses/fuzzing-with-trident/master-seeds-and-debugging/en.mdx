# Master Seeds and Debugging

When your fuzz test finds a crash, you need to reproduce it to understand what happened. This is where **Master Seeds** become essential. This lesson covers the complete debugging workflow: from crash discovery to understanding the root cause to verifying your fix.

<ArticleSection
  name="Understanding Master Seeds"
  id="understanding-master-seeds"
  level="h2"
/>

Every fuzz run ends with output like this:

```
MASTER SEED used: "b6562888e52de3436324c96c76ab8d16a9877af74f3a2fe71dc2d363a2fc6337"
```

### What is the Master Seed?

The Master Seed is a 256-bit value that controls **all randomness** in your fuzz session:

- Every `random_from_range()` call
- Every `random_pubkey()` and `random_keypair()`
- Every `random_string()` and `random_bytes()`
- Which `#[flow]` methods are selected
- The order of flow execution

Everything is deterministically derived from this single seed.

### Why Does This Matter?

**Reproducibility.** Given the same seed, Trident will:

- Generate the exact same random values
- Select the exact same flows
- Execute in the exact same order
- Hit the exact same crash

This transforms debugging from "I got a crash somewhere in 10,000 iterations" to "Here's the exact sequence that caused it."

### How Seeds Work

```
Master Seed
    │
    ├──► Iteration 1 randomness
    │       ├──► Flow selection (flow2, flow1, flow2, ...)
    │       ├──► random_from_range(1..1000) → 742
    │       ├──► random_pubkey() → 5XjU7n...
    │       └──► ...
    │
    ├──► Iteration 2 randomness
    │       └──► ...
    │
    └──► Iteration N randomness
```

Same seed = Same tree = Same behavior.

<ArticleSection name="The Debugging Workflow" id="debugging-workflow" level="h2" />

Here's the complete process when fuzzing finds a bug:

### Step 1: Run Fuzz Test

```bash
cd trident-tests
trident fuzz run fuzz_vulnerable
```

Let it run. If there's a bug, you'll see something like: 1

```text
Assertion failed at fuzz_vulnerable/test_fuzz.rs:158:9: Error, Balance overflowed to
18446744073538639099 (seed: 0d0258fb7dcc05cac0b2d576418a8ebe946deb8bf7d11e10067c4faf4a0f0924)

+----------------------+---------------+------------+-----------+----------------------+
| Instruction          | Invoked Total | Ix Success | Ix Failed | Instruction Panicked |
+----------------------+---------------+------------+-----------+----------------------+
| Initialize Vault     |            48 |         48 |         0 |                    0 |
| Create User Account  |            48 |         48 |         0 |                    0 |
| Withdraw Instruction |            60 |         60 |         0 |                    0 |
+----------------------+---------------+------------+-----------+----------------------+
MASTER SEED used: "06d4d112c9531950152869399f2e888e0425cf8a7bad9e8b672b1a7f61f41b52"
```

**What this tells you:**

- **Instruction Panicked: 0**: No runtime errors occurred on-chain. This is a "Silent Killer" bug.
- **Assertion Failed**: Your test code checked the account data _after_ the transaction and found the balance was impossibly high.
- **Master Seed**: `06d4d112...` (Save this!)

### Step 2: Reproduce the Crash

Since the bug relies on a specific sequence of random numbers, you must use the **Master Seed** to replay it. This allows you to isolate the exact scenario that caused the bug.

```bash
trident fuzz debug fuzz_vulnerable 06d4d112c9531950152869399f2e888e0425cf8a7bad9e8b672b1a7f61f41b52
```

### Step 3: Verify Persistence

The output confirms that the bug is reproducible with 100% accuracy:

```text
Debug mode detected: Running single iteration with provided seed
Using debug seed: 06d4d112c9531950152869399f2e888e0425cf8a7bad9e8b672b1a7f61f41b52
DEBUG_FUZZ: Balance = 18446744073538639099
Assertion failed at fuzz_vulnerable/test_fuzz.rs:158:9: Error, Balance overflowed to 18446744073538639099
```

This confirms:

1. **Determinism**: The same seed produces the exact same random values.
2. **State Corruption**: The balance wraps around to the same massive number every time.

### Step 4: Analyze and Fix

The fact that the balance is `18,446,744...` (u64::MAX) confirms an integer underflow occurred. The user withdrew more than they had, and the program didn't stop them.

**The Fix:**
Open `programs/vulnerable/src/lib.rs` and add a check before subtraction:

```rust
pub fn withdraw(ctx: Context<Withdraw>, amount: u64) -> Result<()> {
    let user_account = &mut ctx.accounts.user_account;

    // FIX: Check if balance is sufficient
    require!(user_account.balance >= amount, ErrorCode::InsufficientFunds);

    // ...
}
```

### Step 5: Verify the Fix

Run the **same seed** again with the fixed code. This proves your fix works for the exact edge case you found.

```bash
trident fuzz debug fuzz_vulnerable 06d4d112c9531950152869399f2e888e0425cf8a7bad9e8b672b1a7f61f41b52
```

**Expected Result:**

- **No Assertion Failure**: The transaction will now fail gracefully (with your error code) OR the condition to withdraw invalid funds will be blocked.
- The test will pass successfully because the "Balance overflow" state is never reached.

### Step 6: Run Full Fuzz Test

Finally, run the fuzzer without a seed to search for _new_ bugs to ensure your fix didn't break anything else.

```bash
trident fuzz run fuzz_vulnerable
```

A clean run ensures your fix didn't break anything else and that no other bypasses exist.

<ArticleSection name="CLI Commands Reference" id="cli-reference" level="h2" />

### Running Fuzz Tests

```bash
# Run with random seed (normal fuzzing)
trident fuzz run fuzz_0

# Run with specific seed (reproduce a session)
trident fuzz run fuzz_0 abc123def456...

# Run with exit code (for CI/CD)
trident fuzz run fuzz_0 --with-exit-code
# Returns non-zero exit code if crashes found
```

### Debugging

```bash
# Debug a specific crashed session
trident fuzz debug fuzz_0 abc123def456...

# With detailed logging
TRIDENT_LOG=1 trident fuzz debug fuzz_0 abc123def456...

# Combine with specific seed for any run
TRIDENT_LOG=1 trident fuzz run fuzz_0 abc123def456...
```

### Adding New Fuzz Tests

```bash
# Add another fuzz test with default naming (fuzz_1, fuzz_2, etc.)
trident fuzz add

# Specify target program and test name
trident fuzz add -p staking -t fuzz_staking
```

The `-p` flag specifies which program to generate the fuzz test for, and `-t` sets a custom name for the test directory. This is useful when your workspace has multiple programs (e.g., a lending program and a staking program).

<ArticleSection name="Reading Fuzz Output" id="reading-output" level="h2" />

### The Statistics Table

```
+-------------+---------------+------------+-----------+----------------------+
| Instruction | Invoked Total | Ix Success | Ix Failed | Instruction Panicked |
+-------------+---------------+------------+-----------+----------------------+
| Initialize  |         1,000 |      1,000 |         0 |                    0 |
| Deposit     |         5,234 |      4,891 |       343 |                    0 |
| Withdraw    |         4,766 |      3,102 |     1,664 |                    0 |
| Trade       |         8,123 |      5,432 |     2,691 |                    3 |
+-------------+---------------+------------+-----------+----------------------+
```

**Interpreting each column:**

| Column               | Meaning                         | Good Sign                              | Bad Sign                      |
| -------------------- | ------------------------------- | -------------------------------------- | ----------------------------- |
| Invoked Total        | Times instruction was attempted | High numbers = good coverage           | Very low = flow issues        |
| Ix Success           | Successful transactions         | Some successes                         | Zero = flows are broken       |
| Ix Failed            | Failed transactions             | Expected - fuzzer tests invalid inputs | Zero = not testing edge cases |
| Instruction Panicked | **BUGS FOUND**                  | Zero                                   | Any non-zero = investigate!   |

**Healthy ratios:**

- Success rate of 60-90% is normal (fuzzer intentionally tests invalid inputs)
- 100% success = you're not testing error paths
- 0% success = your flows are misconfigured
- **Any panics = bugs to investigate**

<ArticleSection name="Regression Testing" id="regression-testing" level="h2" />

Regression testing ensures that code changes don't break existing functionality. Trident supports this by tracking the state of specific accounts across fuzz runs and letting you compare results between program versions.

### Step 1: Enable Regression in Config

In your `Trident.toml`:

```toml
[fuzz.regression]
enable = true
```

When enabled, Trident sets the `FUZZING_REGRESSION` environment variable internally. This tells the fuzzer to generate a regression JSON file containing snapshots of tracked account states.

### Step 2: Track Accounts in Your Fuzz Test

Use `track_account_regression` to mark which accounts should be monitored:

```rust
#[flow_executor]
impl FuzzTest {
    #[init]
    fn start(&mut self) {
        let user = self.fuzz_accounts.user.insert(&mut self.trident, None);
        let vault = self.fuzz_accounts.vault.insert(&mut self.trident, None);

        // ... initialize accounts ...

        // Track these accounts for regression
        self.trident.track_account_regression(&vault, "vault_account");
    }

    #[flow]
    fn deposit_flow(&mut self) {
        let vault = self.fuzz_accounts.vault.get(&mut self.trident);

        // ... execute deposit ...

        // Track state after modification
        self.trident.track_account_regression(&vault, "vault_account");
    }
}
```

You can track accounts in `#[init]`, `#[flow]`, or `#[end]`. Each call captures a snapshot of the account's data at that point.

> **Note:** `track_account_regression` returns nothing (`()`), so calls cannot be chained. Track each account separately.

### Step 3: Run on the Stable Version

Run your fuzz test on the current (working) version of your program:

```bash
trident fuzz run fuzz_0
```

Trident generates a regression JSON file (e.g., `regression_fuzz_0_<timestamp>.json`) in `.fuzz-artifacts/`. This file contains hashes of the tracked account data at each snapshot point, organized by iteration seed.

Note the **Master Seed** from the output - you'll need it to ensure the same sequence runs on the new version.

### Step 4: Run on the New Version

After making your code changes, run the fuzz test again with the **same seed**:

```bash
trident fuzz run fuzz_0 <MASTER_SEED>
```

This generates a second regression JSON file with snapshots from the updated program.

### Step 5: Compare Results

Use `trident compare` to check for differences:

```bash
trident compare <path_to_old_regression.json> <path_to_new_regression.json>
```

This compares the account state hashes between the two runs. If any tracked account's data differs at the same point in the sequence, Trident reports which iteration seeds produced different results.

**Matching hashes** = your changes didn't affect the tracked account states.
**Different hashes** = something changed in how the program modifies those accounts.

### Manual Seed Collection

In addition to automatic regression tracking, keep a record of seeds that found bugs:

```text
# regression_seeds.txt
# Integer overflow in withdraw - fixed 2024-01-15
abc123def456...

# Missing authority check - fixed 2024-01-20
789xyz012abc...
```

Re-run these seeds after changes to confirm fixes still hold:

```bash
# Run each bug-finding seed to verify fixes
trident fuzz run fuzz_0 abc123def456... --with-exit-code
trident fuzz run fuzz_0 789xyz012abc... --with-exit-code
```

Or in CI:

```text
# .github/workflows/fuzz.yml
- name: Run regression seeds
  run: |
    for seed in abc123def456 789xyz012abc; do
      trident fuzz run fuzz_0 $seed --with-exit-code
    done
```

<ArticleSection name="Debugging Tips" id="debugging-tips" level="h2" />

### 1. Start with Fewer Iterations

During debugging, reduce iterations to find the crash faster:

```rust
fn main() {
    // During debugging
    FuzzTest::fuzz(100, 20);

    // For real testing
    // FuzzTest::fuzz(10000, 200);
}
```

### 2. Add Strategic Logging

In your fuzz test, add prints that only show when `TRIDENT_LOG=1` is set:

```rust
#[flow]
fn deposit_flow(&mut self) {
    let amount = self.trident.random_from_range(1..1_000_000u64);

    // This only shows when TRIDENT_LOG=1
    println!("Attempting deposit of {} lamports", amount);

    let result = self.trident.process_transaction(&[ix], Some("Deposit"));

    println!("Deposit result: {:?}", result.is_success());
}
```

### 3. Narrow Down the Failing Flow

If you have many flows, temporarily disable some to isolate the bug:

```rust
#[flow]
fn deposit_flow(&mut self) { /* ... */ }

#[flow]
fn withdraw_flow(&mut self) { /* ... */ }

// Temporarily comment out to isolate
// #[flow]
// fn trade_flow(&mut self) { /* ... */ }

// #[flow]
// fn governance_flow(&mut self) { /* ... */ }
```

### 4. Check Account State at Crash Point

Add explicit state dumps in your invariant checks:

```rust
if result.is_success() {
    let balance_after = self.trident
        .get_account_with_type::<Vault>(&vault, 8)
        .expect("Vault should exist")
        .balance;

    if balance_after != balance_before + amount {
        // Dump state before panicking
        println!("=== INVARIANT VIOLATION ===");
        println!("Before: {}", balance_before);
        println!("After: {}", balance_after);
        println!("Amount: {}", amount);
        println!("Expected: {}", balance_before + amount);
        println!("Difference: {}", (balance_after as i128) - (balance_before as i128) - (amount as i128));

        panic!("Balance invariant violated");
    }
}
```

### 5. Use the Dashboard

For visual debugging, enable the dashboard:

```toml
# Trident.toml
[fuzz.metrics]
enabled = true
dashboard = true
```

After running, open the HTML dashboard in `.fuzz-artifacts/` to see:

- Transaction success/failure rates over time
- Which flows are executing
- Where crashes occurred

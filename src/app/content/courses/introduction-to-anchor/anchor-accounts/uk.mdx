# Акаунти

Ми бачили макрос `#[account]`, але, звичайно, на Solana є різні типи облікових записів. З цієї причини варто приділити хвилинку, щоб побачити, як загалом працюють облікові записи на Solana, а точніше, як вони працюють з Anchor.

<ArticleSection name="Базовий Огляд" id="general-overview" level="h2" />

На Solana кожен фрагмент стану знаходиться в обліковому записі; уявіть собі [реєстр](https://solana.com/docs/references/terminology#ledger) як одну гігантську таблицю, де кожен рядок має однакову базову схему:

```rust
pub struct Account {
    /// кількість лампортів, які належать цьому обліковому запису 
    pub lamports: u64,
    /// дані, які зберігаються в обліковому записі
    #[cfg_attr(feature = "serde", serde(with = "serde_bytes"))]
    pub data: Vec<u8>,
    /// публічний ключ програми, яка володіє цим обліковим записом
    pub owner: Pubkey,
    /// прапорець, який вказує, чи є цей обліковий запис виконуваним
    pub executable: bool,
    /// кількість лампортів, які обліковий запис має на рахунку для покриття оренди
    pub rent_epoch: Epoch,
}
```
Усі облікові записи на Solana мають однакову базову структуру. Що їх відрізняє:

1. Власник: Програма, яка має виключні права на зміну даних та ламппортів облікового запису.

2. Дані: Використовуються програмою-власником для розрізнення різних типів облікових записів.

Коли ми говоримо про облікові записи Програми токенів, ми маємо на увазі обліковий запис, де «власником» є Програма токенів. На відміну від Системного облікового запису, поле даних якого порожнє, обліковий запис Програми токенів може бути як обліковим записом **Mint**, так і обліковим записом **Token**. Ми використовуємо дискримінатори, щоб розрізняти їх.

Так само, як Програма токенів може володіти обліковими записами, так само може володіти будь-яка інша програма, навіть наша власна.

<ArticleSection name="Облікові Записи Програми" id="program-accounts" level="h2" />

Облікові записи програм є основою управління станом в програмах Anchor. Вони дозволяють створювати власні структури даних, що належать вашій програмі. Давайте розглянемо, як ефективно з ними працювати.

### Структура Акаунту та Дискримінатори
Кожен обліковий запис програми в Anchor потребує способу ідентифікації свого типу. Це здійснюється за допомогою дискримінаторів, які можуть бути:

1. **Дискримінатори за замовчуванням**: 8-байтовий префікс, згенерований за допомогою `sha256("account:<StructName>")[0..8]` для облікових записів або `sha256("global:<instruction_name>")[0..8]` для інструкцій. Начальні значення використовують PascalCase для облікових записів та snake_case для інструкцій.

<AnchorDiscriminatorCalculator value={"TestAccount"} displayMode="account" />

2. **Користувацькі дискримінатори**: Починаючи з Anchor `v0.31.0`, ви можете вказати свій власний дискримінатор:

```rust
#[account(discriminator = 1)]              // 1 байт
pub struct Escrow { … }
```

**Важливі примітки щодо дискримінаторів**:
- Вони мають бути унікальними у вашій програмі
- Використання `[1]` запобігає використанню `[1, 2, …]`, оскільки вони також починаються з `1`
- `[0]` не можна використовувати, оскільки це конфліктує з неініціалізованими обліковими записами

### Створення Акаунтів Програми

Щоб створити обліковий запис програми, спочатку визначте структуру даних:

```rust
use anchor_lang::prelude::*;

#[derive(InitSpace)]
#[account(discriminator = 1)]
pub struct CustomAccountType {
    data: u64,
}
```
Ключові моменти щодо облікових записів програми:
- Максимальний розмір становить 10 240 байт (10 КіБ)
- Для більших облікових записів вам знадобиться `zero_copy` та фрагментований запис
- Макрос виведення `InitSpace` автоматично розраховує необхідний простір
- Загальний простір = `INIT_SPACE` + `DISCRIMINATOR.len()`

Загальний простір у байтах, необхідний для облікового запису, дорівнює сумі `INIT_SPACE` (розмір усіх полів разом) та розміру дискримінатора (`DISCRIMINATOR.len()`).

Облікові записи Solana вимагають орендного депозиту в лампортах, який залежить від розміру облікового запису. Знання розміру допомагає нам розрахувати, скільки лампортів нам потрібно внести, щоб відкрити обліковий запис.

Ось як ми збираємося ініціювати обліковий запис у нашій структурі `Account`:

```rust
#[account(
    init,
    payer = <target_account>,
    space = <num_bytes>                 // CustomAccountType::INIT_SPACE + CustomAccountType::DISCRIMINATOR.len(),
)]
pub account: Account<'info, CustomAccountType>,
```
Ось деякі поля, що використовуються в макросі `#[account]`, окрім полів `seeds` та `bump`, які ми вже розглянули, та їх функції:
- `init`: повідомляє Anchor про створення облікового запису
- `payer`: який підписант фінансує орендну плату (тут, мейкер)
- `space`: скільки байтів виділити. Тут також відбувається розрахунок орендної плати

Після створення ви можете змінити дані облікового запису. Якщо вам потрібно змінити його розмір, використовуйте reallocation:

```rust
#[account(
    mut,                       // Позначити як змінне
    realloc = <space>,         // Новий розмір
    realloc::payer = <target>, // Хто платить за зміну
    realloc::zero = <bool>     // Чи обнуляти новий простір
)]
```
**Примітка**: Зменшуючи розмір облікового запису, встановіть `realloc::zero = true`, щоб забезпечити належне очищення старих даних.

Нарешті, коли обліковий запис більше не потрібен, ми можемо закрити його, щоб стягнути орендну плату:

```rust
#[account(
    mut,                       // Позначити як змінне
    close = <target_account>,  // Куди відправити решту ламппортів
)]
pub account: Account<'info, CustomAccountType>,
```
Потім ми можемо додати до цих обмежень PDA, детерміновані адреси, отримані з початкових значень, та ідентифікатор програми, які особливо корисні для створення передбачуваних адрес облікових записів, ось так:

```rust
#[account(
    seeds = <seeds>,            // Сіди для деривіації
    bump                        // Стандартний бамп сід
)]
pub account: Account<'info, CustomAccountType>,
```

**Примітка**: що PDA є детермінованими: однакові початкові значення + програма + bump завжди створюють однакову адресу, і bump гарантує, що адреса знаходиться поза кривою ed25519.

Оскільки обчислення bump може "спалити" багато CU, завжди добре зберегти його в обліковому записі або передати в інструкцію та перевірити його без необхідності обчислювати так:

```rust
#[account(
    seeds = <seeds>,
    bump = <expr>
)]
pub account: Account<'info, CustomAccountType>,
```

І можна отримати КПК, який походить від іншої програми, передавши адресу програми, з якої отримано ось так:

```rust
#[account(
    seeds = <seeds>,
    bump = <expr>,
    seeds::program = <expr>
)]
pub account: Account<'info, CustomAccountType>,
```

<ArticleSection name="Акаунти Токена" id="token-program" level="h2" />

Програма токенів, що є частиною бібліотеки програм Solana (SPL), — це вбудований набір інструментів для створення та переміщення будь-якого активу, який не є рідним для SOL. Він містить інструкції для створення токенів, створення нової пропозиції, переказу балансів, запису, заморожування тощо.

Ця програма має два ключові типи облікових записів:
- **Обліковий запис монетного двору**: зберігає метадані для одного конкретного токена: пропозиція, десяткові знаки, авторизація монетного двору, авторизація заморожування тощо
- **Обліковий запис токенів**: зберігає баланс цієї монети для конкретного власника. Тільки власник може зменшити баланс (переказати, спалити тощо), але будь-хто може надсилати токени на обліковий запис, збільшуючи його баланс.

### Акаунти Токена в Anchor

За своєю природою, основний крейт Anchor містить лише допоміжні функції CPI та Accounts для системної програми. Якщо вам потрібна така ж сама обробка токенів SPL, ви встановлюєте крейт `anchor_spl`.

`anchor_spl` додає:
- Конструктори допоміжних функцій для кожної інструкції в програмах SPL Token та Token-2022
- Обгортки типів, які спрощують перевірку та десеріалізацію облікових записів Mint та Token

Давайте розглянемо, як структуровані облікові записи `Mint` та `Token`:

```rust
#[account(
    mint::decimals     = <expr>,
    mint::authority    = <target_account>,
    mint::freeze_authority = <target_account>
    mint::token_program = <target_account>
)]
pub mint: Account<'info, Mint>,

#[account(
    mut,
    associated_token::mint       = <target_account>,
    associated_token::authority  = <target_account>,
    associated_token::token_program = <target_account>
)]
pub maker_ata_a: Account<'info, TokenAccount>,
```

`Account<'info, Mint>` та `Account<'info, TokenAccount>` повідомляють Anchor про необхідність:
- підтвердити, що обліковий запис дійсно є обліковим записом Mint або Token
- десеріалізувати його дані, щоб ви могли читати поля безпосередньо
- застосувати будь-які додаткові обмеження, які ви вкажете (`authority`, `decimals`, `mint`, `token_program` тощо).

Ці облікові записи, пов'язані з токенами, дотримуються того ж шаблону `init`, який використовувався раніше. Оскільки Anchor знає їхній фіксований розмір у байтах, нам не потрібно вказувати значення `пробілу`, лише платника, який фінансує обліковий запис.

Anchor також пропонує макрос `init_if_needed`: він перевіряє, чи обліковий запис токена вже існує, і якщо ні, створює його. Цей скорочений спосіб не є безпечним для кожного типу облікового запису, але він ідеально підходить для облікових записів токенів, тому ми будемо покладатися на нього тут.

Як згадувалося, `anchor_spl` створює помічники для програм **Token** та **Token2022**, причому остання вводить розширення токенів. Основна проблема полягає в тому, що, хоча ці облікові записи досягають схожих цілей і мають порівнянні структури, їх не можна десеріалізувати та перевіряти однаково, оскільки вони належать двом різним програмам.

Ми могли б створити більш «розширену» логіку для обробки цих різних типів облікових записів, але, на щастя, Anchor підтримує цей сценарій через **InterfaceAccounts**:

```rust
use anchor_spl::token_interface::{Mint, TokenAccount};

#[account(
    mint::decimals     = <expr>,
    mint::authority    = <target_account>,
    mint::freeze_authority = <target_account>
)]
pub mint: InterfaceAccounts<'info, Mint>,

#[account(
    mut,
    associated_token::mint = <target_account>,
    associated_token::authority = <target_account>,
    associated_token::token_program = <target_account>
)]
pub maker_ata_a: InterfaceAccounts<'info, TokenAccount>,
```

Ключова відмінність тут полягає в тому, що ми використовуємо `InterfaceAccounts` замість `Account`. Це дозволяє нашій програмі працювати як з обліковими записами Token, так і з обліковими записами Token2022 без необхідності обробляти відмінності в їхній логіці десеріалізації. Інтерфейс забезпечує спільний спосіб взаємодії з обома типами облікових записів, зберігаючи при цьому безпеку типів та належну валідацію.

Цей підхід особливо корисний, коли ви хочете, щоб ваша програма була сумісною з обома стандартами токенів, оскільки він усуває необхідність писати окрему логіку для кожної програми. Інтерфейс обробляє всю складність роботи з різними структурами облікових записів за лаштунками.

Якщо ви хочете дізнатися більше про те, як використовувати `anchor-spl`, ви можете пройти курси [SPL-Token Program with Anchor](/en/courses/spl-token-with-anchor) або [Token2022 Program with Anchor](/en/courses/token-2022-with-anchor).

<ArticleSection name="Додаткові типи Акаунтів" id="additional-accounts-type" level="h2" />

Звичайно, системні облікові записи, облікові записи програм та облікові записи токенів – це не єдині типи облікових записів, які ми можемо мати в Anchor. Тому ми розглянемо тут інші типи облікових записів, які ми можемо мати:

### Signer

Тип `Signer` використовується, коли потрібно перевірити, чи обліковий запис підписав транзакцію. Це важливо для безпеки, оскільки гарантує, що лише авторизовані облікові записи можуть виконувати певні дії. Ви використовуватимете цей тип щоразу, коли потрібно гарантувати, що певний обліковий запис схвалив транзакцію, наприклад, під час переказу коштів або зміни даних облікового запису, що вимагає явного дозволу. Ось як його можна використовувати:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    #[account(mut)]
    pub signer: Signer<'info>,
}
```

Тип `Signer` автоматично перевіряє, чи обліковий запис підписав транзакцію. Якщо ні, транзакція не буде виконана. Це особливо корисно, коли потрібно переконатися, що лише певні облікові записи можуть виконувати певні операції.

### AccountInfo та UncheckedAccount

`AccountInfo` та `UncheckedAccount` – це низькорівневі типи облікових записів, які надають прямий доступ до даних облікового запису без автоматичної перевірки. Вони ідентичні за функціональністю, але `UncheckedAccount` є кращим вибором, оскільки його назва краще відображає його призначення.

Ці типи корисні у трьох основних сценаріях:

1. Робота з обліковими записами, яким бракує визначеної структури
2. Реалізація власної логіки перевірки
3. Взаємодія з обліковими записами з інших програм, які не мають визначень типів Anchor

Оскільки ці типи обходять перевірки безпеки Anchor, вони за своєю суттю є небезпечними та вимагають явного підтвердження за допомогою коментаря `/// CHECK`. Цей коментар служить документацією того, що ви розумієте ризики та впровадили відповідну перевірку.

Ось приклад того, як їх використовувати:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    /// CHECK: This is an unchecked account
    pub account: UncheckedAccount<'info>,

    /// CHECK: This is an unchecked account
    pub account_info: AccountInfo<'info>,
}
```

### Option

Тип `Option` в Anchor дозволяє зробити облікові записи необов'язковими у вашій інструкції. Коли обліковий запис обгорнуто в `Option`, його можна або надати, або пропустити в транзакції. Це особливо корисно для:
- Створення гнучких інструкцій, які можуть працювати з певними обліковими записами або без них
- Впровадження необов'язкових параметрів, які можуть бути не завжди потрібні
- Створення зворотно сумісних інструкцій, які можуть працювати з новими або старими структурами облікових записів

Коли обліковий запис `Option` встановлено на `None`, Anchor використовуватиме ідентифікатор програми як адресу облікового запису. Цю поведінку важливо розуміти під час роботи з необов'язковими обліковими записами.

Ось як це реалізувати:


```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub optional_account: Option<Account<'info, CustomAccountType>>,
}
```

### Box

Тип `Box` використовується для зберігання облікових записів у купі, а не в стеку. Це необхідно в кількох сценаріях:
- При роботі з великими структурами облікових записів, які було б неефективно зберігати в стеку
- При роботі з рекурсивними структурами даних
- Коли вам потрібно працювати з обліковими записами, розмір яких неможливо визначити під час компіляції

Використання `Box` допомагає ефективніше керувати пам'яттю в цих випадках, розподіляючи дані облікових записів у купі. Ось приклад:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub boxed_account: Box<Account<'info, LargeAccountType>>,
}
```

### Program

Тип `Program` використовується для перевірки та взаємодії з іншими програмами Solana. Anchor може легко ідентифікувати облікові записи програм, оскільки їхній прапорець `executable` встановлено на `true`. Цей тип особливо корисний, коли:

- Вам потрібно виконувати міжпрограмні виклики (CPI)
- Ви хочете переконатися, що взаємодієте з правильною програмою
- Вам потрібно перевірити право власності програми на облікові записи

Існує два основних способи використання типу `Program`:

1. Використання вбудованих типів програм (рекомендовано, якщо доступно):
```rust
use anchor_spl::token::Token;

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub system_program: Program<'info, System>,
    pub token_program: Program<'info, Token>,
}
```

2. Використання власної адреси програми, коли тип програми недоступний:
```rust
// Address of the Program
const PROGRAM_ADDRESS: Pubkey = pubkey!("22222222222222222222222222222222222222222222")

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    #[account(address = PROGRAM_ADDRESS)]
    /// CHECK: this is fine since we're checking the address
    pub program: UncheckedAccount<'info>,
}
```

**Примітка**: Під час роботи з програмами токенів вам може знадобитися підтримка як Legacy Token Program, так і Token-2022 Program. У таких випадках використовуйте тип `Interface` замість `Program`:

```rust
use anchor_spl::token_interface::TokenInterface;

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub program: Interface<'info, TokenInterface>,
}
```

<ArticleSection name="Користувацька Перевірка Акаунтів" id="custom-account-validation" level="h2" />

Anchor надає потужний набір обмежень, які можна застосовувати безпосередньо в атрибуті `#[account]`. Ці обмеження допомагають забезпечити дійсність облікового запису та забезпечити виконання правил програми на рівні облікового запису, перш ніж буде виконано логіку інструкцій. Ось доступні обмеження:

### Обмеження Адреси

Обмеження `address` перевіряє, чи відповідає відкритий ключ облікового запису певному значенню. Це важливо, коли вам потрібно переконатися, що ви взаємодієте з відомим обліковим записом, таким як певний КПК або обліковий запис програми:

```rust
#[account(
    address = <expr>,                    // Базове використання
    address = <expr> @ CustomError       // З користувацькою помилкою
)]
pub account: Account<'info, CustomAccountType>,
```

### Обмеження Власника

Обмеження `owner` гарантує, що обліковий запис належить певній програмі. Це критично важлива перевірка безпеки під час роботи з обліковими записами, що належать програмам, оскільки вона запобігає несанкціонованому доступу до облікових записів, якими має керувати певна програма:

```rust
#[account(
    owner = <expr>,                      // Базове використання
    owner = <expr> @ CustomError         // З користувацькою помилкою
)]
pub account: Account<'info, CustomAccountType>,
```

### Виконуване Обмеження

Обмеження `executable` перевіряє, чи є обліковий запис обліковим записом програми (його прапорець `executable` встановлено на `true`). Це особливо корисно під час міжпрограмних викликів (CPI), щоб переконатися, що ви взаємодієте з програмою, а не з обліковим записом даних:

```rust
#[account(executable)]
pub account: Account<'info, CustomAccountType>,
```

### Змінюване Обмеження

Обмеження `mut` позначає обліковий запис як змінний, дозволяючи змінювати його дані під час виконання інструкції. Це необхідно для будь-якого облікового запису, який буде оновлено, оскільки Anchor за замовчуванням забезпечує незмінність для безпеки:

```rust
#[account(
    mut,                                 // Базове використання
    mut @ CustomError                    // З користувацькою помилкою
)]
pub account: Account<'info, CustomAccountType>,
```

### Обмеження Signer

Обмеження `signer` перевіряє, чи обліковий запис підписав транзакцію. Це критично важливо для безпеки, коли обліковий запис має авторизувати дію, таку як переказ коштів або зміна даних. Це більш чіткий спосіб вимагати підписи порівняно з використанням типу `Підписувач`:

```rust
#[account(
    signer,                              // Базове використання
    signer @ CustomError                 // З користувацькою помилкою
)]
pub account: Account<'info, CustomAccountType>,
```

### Обмеження Has One

Обмеження `has_one` перевіряє, чи певне поле в структурі облікового запису відповідає відкритому ключу іншого облікового запису. Це корисно для підтримки зв'язків між обліковими записами, наприклад, для забезпечення належності облікового запису токена правильному власнику:

```rust
#[account(
    has_one = data @ Error::InvalidField
)]
pub account: Account<'info, CustomAccountType>,
```

### Користувацбкі Обмеження

Коли вбудовані обмеження не відповідають вашим потребам, ви можете написати власний вираз перевірки. Це дозволяє використовувати складну логіку перевірки, яку неможливо виразити за допомогою інших обмежень, таких як довжина даних розрахункового рахунку або перевірка зв'язків між кількома полями:

```rust
#[account(
    constraint = data == account.data @ Error::InvalidField
)]
pub account: Account<'info, CustomAccountType>,
```

Ці обмеження можна поєднати для створення потужних правил перевірки ваших облікових записів. Розміщуючи перевірку на рівні облікового запису, ви забезпечуєте близькість перевірок безпеки до визначень облікових записів та уникаєте розпорошення викликів `require!()` по всій логіці інструкцій.

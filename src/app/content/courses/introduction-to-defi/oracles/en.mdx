# Oracles

October 2022. A trader named Avraham Eisenberg deposited $10 million into Mango Markets, opened massive perpetual positions on both sides, then bought MNGO tokens on illiquid spot markets.

The price spiked 10x in minutes. The oracle dutifully reported this "real" price, so Eisenberg's long position showed $400M in unrealized profit. He borrowed against it and withdrew real assets. The MNGO price collapsed, leaving Mango with $114M in bad debt.

The exploit wasn't a bug in Mango's Rust code. It was a failure to make sure oracles represented the right data.

### The Oracle Problem

Blockchains are isolated systems: a Solana program can't call a web API, scrape a price from Coinbase, or check the weather. Everything on-chain must come from on-chain data.

But DeFi needs real-world prices. How much is SOL worth in USD? What's ETH/BTC? Without external price data, lending protocols can't value collateral, perpetuals can't calculate PnL, and liquidations can't trigger.

Oracles bridge this gap: trusted parties (like Pyth or Switchboard) aggregate prices from multiple sources and publish them to on-chain accounts that your program can read.

This lesson covers what you need from oracles and, critically, how to avoid getting exploited.

> For complete Pyth and Switchboard implementation details, see the dedicated [Oracle Integration](/courses/oracles-on-solana) course. This lesson covers the essentials for understanding oracle security.

<ArticleSection name="What You Need From an Oracle" id="oracle-requirements" level="h2" />

A naive developer might think an oracle just returns a price: "SOL is $100." But that single number hides critical context.

Every oracle price feed provides four fields you must understand:

```rust
pub struct OraclePrice {
    pub price: i64,          // The price value
    pub conf: u64,           // Confidence interval (uncertainty)
    pub expo: i32,           // Decimal exponent
    pub publish_time: i64,   // When this price was published
}
```

**Price** is the actual value, but it's an integer. SOL at $100.50 might be represented as `10050000000` with a separate exponent telling you where the decimal goes.

**Confidence** tells you how certain the oracle is. If the price is $100 with confidence of $5, the real price could be anywhere from $95 to $105. During the Mango exploit, the confidence interval on MNGO was screaming "something is wrong" - but Mango's code didn't check it.

**Exponent** handles decimal scaling. A price of `12345678` with exponent `-8` means $0.12345678. Get this wrong and you'll value assets at millions of times their real worth.

**Publish time** tells you when the data was fetched. A price from 5 minutes ago during a crash is worse than useless - it's actively dangerous.

<ArticleSection name="Price Validation" id="price-validation" level="h2" />

This is where most protocols fail. Reading a price is easy. Validating it properly is what separates secure protocols from hacked ones.

### Staleness Check

The oracle stops updating during a network hiccup. SOL crashes from $100 to $80, but your protocol still sees $100. 

A borrower deposits SOL, gets valued at the stale price, borrows maximum USDC, and disappears. When the price updates, the protocol has bad debt.

Staleness checks prevent this:

```rust
const MAX_PRICE_AGE: i64 = 60;  // 60 seconds

pub fn validate_staleness(price: &OraclePrice, current_time: i64) -> Result<()> {
    let age = current_time - price.publish_time;

    require!(age <= MAX_PRICE_AGE, ErrorCode::StalePriceData);
    require!(age >= 0, ErrorCode::FuturePriceData);  // Sanity check

    Ok(())
}
```

### Confidence Check

The oracle returns a price of $100 with a confidence interval of $10. That means the real price could be anywhere from $90 to $110. 

If your protocol treats $100 as gospel and a liquidation triggers at $95, you might be liquidating a healthy position, or failing to liquidate a dangerous one.

Wide confidence means the oracle isn't sure. Acting on uncertain prices is risky:

```rust
const MAX_CONFIDENCE_BPS: u64 = 200;  // 2% max uncertainty

pub fn validate_confidence(price: &OraclePrice) -> Result<()> {
    // Confidence should be less than X% of price
    // conf / price < MAX_CONFIDENCE_BPS / 10_000

    let price_abs = price.price.unsigned_abs();

    // Avoid division: conf * 10_000 < price * MAX_CONFIDENCE_BPS
    let conf_scaled = price.conf.checked_mul(10_000)
        .ok_or(ErrorCode::MathOverflow)?;
    let price_scaled = price_abs.checked_mul(MAX_CONFIDENCE_BPS)
        .ok_or(ErrorCode::MathOverflow)?;

    require!(conf_scaled < price_scaled, ErrorCode::PriceConfidenceTooWide);

    Ok(())
}
```

> During high volatility, confidence intervals widen. Your protocol should either pause operations or use wider safety margins.

### Sanity Bounds

Prices should fall within reasonable ranges. This catches oracle failures and manipulation:

```rust
pub fn validate_sanity(
    price: &OraclePrice,
    min_price: u64,
    max_price: u64,
) -> Result<()> {
    let price_normalized = normalize_price(price)?;

    require!(price_normalized >= min_price, ErrorCode::PriceTooLow);
    require!(price_normalized <= max_price, ErrorCode::PriceTooHigh);

    Ok(())
}

// For SOL/USD: min might be $1, max might be $1000
// If oracle returns $0.01 or $50,000, something is wrong
```

### Combined Validation

Always validate all aspects together:

```rust
pub fn get_validated_price(
    price_account: &AccountInfo,
    current_time: i64,
    config: &OracleConfig,
) -> Result<u64> {
    let price = get_pyth_price(price_account)?;

    // 1. Staleness
    validate_staleness(&price, current_time)?;

    // 2. Confidence
    validate_confidence(&price)?;

    // 3. Sanity
    validate_sanity(&price, config.min_price, config.max_price)?;

    // 4. Normalize to standard precision
    let normalized = normalize_price(&price)?;

    Ok(normalized)
}
```

<ArticleSection name="Integration Points" id="integration-points" level="h2" />

Different DeFi primitives use oracles in different ways, and each has unique risks.

### AMMs: The Exception

AMMs are unique: they don't *require* oracles for swaps. The pool price emerges from the reserve ratio. Arbitrageurs keep it aligned with market prices.

But oracles are still useful for AMMs as a sanity check or to increase liquidity efficiency while protecting LPs, as we saw with propAMMs.

### Lending: Total Oracle Dependency

Lending protocols live and die by their oracles. Every single operation depends on accurate prices:

- **Deposits**: Need to value collateral
- **Borrows**: Need to check if collateral covers the loan  
- **Liquidations**: Need to know when positions are underwater
- **Interest**: Sometimes adjusts based on asset prices

A lending protocol with bad oracle data will either liquidate healthy positions (users leave) or fail to liquidate underwater positions (protocol accumulates bad debt and dies).

```rust
pub fn check_health_with_oracle(ctx: Context<CheckHealth>) -> Result<()> {
    // Every price must be validated - no shortcuts
    let collateral_price = get_validated_price(&ctx.accounts.collateral_oracle, /* ... */)?;
    let debt_price = get_validated_price(&ctx.accounts.debt_oracle, /* ... */)?;

    let collateral_value = ctx.accounts.position.collateral as u128 
        * collateral_price as u128 / PRECISION;
    let debt_value = ctx.accounts.position.debt as u128 
        * debt_price as u128 / PRECISION;

    let health = (collateral_value * LIQ_THRESHOLD) / debt_value;
    require!(health >= PRECISION, ErrorCode::Undercollateralized);

    Ok(())
}
```

### Perpetuals: Multiple Price Types

Perps need oracles for several distinct purposes, and mixing them up is dangerous:

1. **Index price**: The "true" spot price for funding rate calculations
2. **Mark price**: Used for PnL and liquidations, often smoothed to resist manipulation
3. **Entry/exit pricing**: What traders actually trade at

The mark price typically blends oracle data with on-chain market data. More oracle weight = more manipulation resistant, but also slower to react to real moves:

```rust
pub fn update_perp_prices(market: &mut Market, oracle_price: u64) -> Result<()> {
    market.index_price = oracle_price;

    let perp_price = calculate_perp_market_price(market)?;
    // 80% oracle, 20% market - heavily weighted toward manipulation resistance
    market.mark_price = (oracle_price * 8 + perp_price * 2) / 10;

    Ok(())
}
```

### Liquidations: Highest Stakes

Liquidation triggers are the most sensitive oracle usage in all of DeFi. Get it wrong in either direction and you're in trouble:

- **Too aggressive**: Healthy positions get liquidated during brief price wicks. Users lose money unfairly, leave your protocol, and maybe sue you.
- **Too lenient**: Underwater positions aren't liquidated in time. Bad debt accumulates. Protocol becomes insolvent.

For liquidations, use the strictest validation:

```rust
pub fn can_liquidate(position: &Position, oracle_accounts: &[AccountInfo]) -> Result<bool> {
    let collateral_price = get_validated_price(
        oracle_accounts[0],
        Clock::get()?.unix_timestamp,
        &OracleConfig {
            max_age: 30,              // Must be very fresh
            max_confidence_bps: 100,  // Must be very certain
        },
    )?;

    let health = calculate_health(position, collateral_price)?;
    Ok(health < PRECISION)
}
```

<ArticleSection name="Oracle Attack Patterns" id="attack-patterns" level="h2" />

Understanding how oracles get exploited is essential to defending against attacks. These patterns repeat across DeFi history.

### Flash Loan + Thin Liquidity

The classic oracle attack, responsible for hundreds of millions in losses:

1. Flash loan massive capital ($50M+)
2. Buy obscure token X on thin DEX, spiking price 10x
3. Protocol's oracle reads the manipulated price
4. Deposit small amount of X as "collateral" (valued at 10x real worth)
5. Borrow real assets (USDC, SOL) against the fake collateral value
6. Sell X back, price crashes to normal
7. Repay flash loan, keep the borrowed assets

The attacker walks away with real money. The protocol is left holding worthless collateral.

**Why it works:** The protocol used a spot DEX price that could be moved with enough capital, rather than an aggregated feed that's manipulation-resistant.

**Mitigation:** Use Pyth or Switchboard. Never use a single DEX's spot price as your oracle.

### Stale Price Exploitation

During network congestion or oracle downtime, prices stop updating. The on-chain price says $100, but the real market price is $80.

An attacker deposits collateral at the stale (higher) price, borrows maximum value, and waits. When the oracle updates, their position is underwater. They've already withdrawn the borrowed funds. The protocol eats the loss.

**Mitigation:** Always check `publish_time`. If the price is older than your threshold, reject the operation entirely. Fail closed.

### Oracle Lag Arbitrage

Even working oracles have latency. If the oracle updates every 400ms but you can see the market moving, there's an arbitrage window.

Market price drops to $95. Oracle still shows $100. You deposit collateral valued at $100, borrow against it, and by the time the oracle catches up, you've extracted value.

**Mitigation:** Tight staleness limits. For high-value operations, consider requiring multiple oracle updates or using TWAP.

### The Mango Playbook (Revisited)

The attack we opened with is worth understanding in detail because it exploited multiple oracle weaknesses:

1. **Thin liquidity**: MNGO traded on illiquid markets - easy to move the price
2. **Oracle reflected manipulation**: The oracle correctly reported the manipulated price
3. **No confidence check**: The confidence interval during the spike was enormous, but Mango didn't reject it
4. **Unrealized PnL as collateral**: Mango let users borrow against paper profits that hadn't been realized

The fix isn't any single check - it's defense in depth. Confidence intervals. Position limits. Circuit breakers. Borrowing restrictions on volatile assets.

<ArticleSection name="Security Checklist" id="security-checklist" level="h2" />

### 1. Never Use Raw Price Data

This seems obvious, but it's the most common mistake:

```rust
// NEVER do this - you will get exploited
let price = oracle.price;

// ALWAYS validate everything
let price = get_validated_price(oracle, clock, config)?;
```

Every price read should go through validation. No exceptions. No "just this once." No "we'll add validation later."

### 2. Use Confidence Intervals Defensively

When the oracle isn't sure, be conservative. For collateral valuation, assume the price is at the low end of the confidence interval. For debt valuation, assume the high end:

```rust
// Valuing collateral? Use the pessimistic (lower) price
let conservative_collateral_price = price.price - price.conf as i64;

// Valuing debt? Use the pessimistic (higher) price
let conservative_debt_price = price.price + price.conf as i64;
```

This widens your safety margins during volatile periods when confidence intervals naturally expand.

### 3. Use TWAP for High-Stakes Operations

Time-weighted average prices are harder to manipulate because the attacker would need to sustain the manipulation over time, not just spike it for one block:

```rust
pub fn calculate_twap(price_samples: &[(u64, i64)]) -> u64 {
    let mut weighted_sum: u128 = 0;
    let mut total_time: i64 = 0;

    for i in 1..price_samples.len() {
        let (prev_price, prev_time) = price_samples[i - 1];
        let (_, curr_time) = price_samples[i];
        let duration = curr_time - prev_time;
        weighted_sum += prev_price as u128 * duration as u128;
        total_time += duration;
    }

    (weighted_sum / total_time as u128) as u64
}
```

TWAP is especially important for liquidation triggers and large position changes.

### 4. Have Fallback Strategies

Oracles fail. Networks congest. What does your protocol do when the primary oracle is unavailable?

```rust
pub fn get_price_with_fallback(
    primary_oracle: &AccountInfo,
    backup_oracle: Option<&AccountInfo>,
    config: &OracleConfig,
) -> Result<u64> {
    // Try primary first
    if let Ok(price) = get_validated_price(primary_oracle, config) {
        return Ok(price);
    }

    // Try backup
    if let Some(backup) = backup_oracle {
        if let Ok(price) = get_validated_price(backup, config) {
            return Ok(price);
        }
    }

    // No valid price - fail closed, don't guess
    Err(ErrorCode::NoValidPriceAvailable.into())
}
```

**Fail closed, not open.** If you can't get a valid price, reject the operation. A paused protocol is better than a drained one.

### The Fundamental Rule

> **Assume someone is always trying to manipulate the price against you.**

Because they are. Oracle exploitation is one of the most profitable attack vectors in DeFi. The protocols that survive are the ones that treat every price as suspect until proven otherwise.

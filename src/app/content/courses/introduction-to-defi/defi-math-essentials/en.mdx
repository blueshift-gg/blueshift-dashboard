# DeFi Math Essentials

DeFi protocols perform financial calculations on-chain: interest accrual, swap amounts, collateral ratios, liquidation thresholds. These calculations must be precise, deterministic, and resistant to manipulation through rounding.

Solana programs cannot use floating-point numbers (they're non-deterministic across validators), so all math uses integers with fixed-point scaling. This introduces precision challenges: when do you round up vs down? How do you prevent rounding errors from accumulating? How do you handle tokens with different decimal places? This lesson covers the math patterns that DeFi protocols use to handle these problems safely. 


<ArticleSection name="The Precision Problem" id="precision-problem" level="h2" />

### No Floats On Chain

Solana programs should not use floating-point numbers. No `f32`, no `f64`.

Floating-point arithmetic is non-deterministic across different hardware; this means that the same calculation might produce slightly different results on different validators.

So we must use integers. But how do you represent `0.5 SOL` with integers?

```rust
// This is how tokens work on Solana
let amount_in_lamports: u64 = 500_000_000; // 0.5 SOL
let sol_decimals: u8 = 9;

// To get the "human readable" value:
// 500_000_000 / 10^9 = 0.5 SOL
```

Every token has a decimal count: SOL has 9 decimals (the smallest part called lamport), USDC has 6. When you see "1 USDC" in a wallet, the on-chain value is actually `1_000_000`.

### Fixed Point Arithmetic

Not being able to use floating point creates other problems. 

For example, if you need to calculate a user's 33.33% share of a 1000 token pool:

```rust
let share = 1000 * 33 / 100;  // = 330, not 333.33
```

You will lose 3.33 tokens to truncation; that's 0.33% of the pool gone in a single calculation. 

At $10M TVL, that's $33,000 vanishing that multiplied by thousands of daily transactions means you've just built a protocol that bleeds value.

By using fixed-point arithmetic we can solve this by scaling up before operations, preserving the decimals that integer division would destroy:

```rust
const PRECISION: u128 = 1_000_000_000; // 10^9

// Calculate 33.33% of 1000 with precision
let percentage = 333_333_333u128; // 0.3333... * PRECISION
let amount = 1000u128;

let result = (amount * percentage) / PRECISION;
// result = 333 (we preserved the decimal places)
```

The pattern: multiply by `PRECISION` to work in "decimal space," then divide at the end to return to normal integers.

Common precision constants you'll see in DeFi:

| **Constant** | **Value** | **Use Case** |
|----------|-------|----------|
| `BPS` | 10,000 | Fee percentages (1 BPS = 0.01%) |
| `PRECISION` | 10^9 or 10^18 | General calculations |
| Token decimals | 6-9 | Token amounts |

> When mixing tokens with different decimals (like SOL and USDC), normalize to a common precision first. Forgetting this is a classic exploit vector.

<ArticleSection name="The Golden Rule of Rounding" id="golden-rule" level="h2" />

Even with the right precision, rounding errors are unavoidable. Integer division always truncates.

The question isn't whether to round, it's who absorbs the loss: the protocol or the user?

Consider this deposit function that rounds in the user's favor:

```rust
pub fn deposit(amount: u64, total_shares: u64, total_assets: u64) -> u64 {
    // Round UP - user gets more shares than they mathematically deserve
    let shares = (amount * total_shares + total_assets - 1) / total_assets;
    shares
}
```

Here's how an attacker exploits this:

```
Pool state: 100 shares, 1000 USDC
Fair price: 1 share = 10 USDC

Step 1: Deposit 5 USDC
  Fair shares: 5 × 100 / 1000 = 0.5 → should round to 0
  With round UP: (5 × 100 + 999) / 1000 = 1 share ← extra share!

Step 2: Withdraw that 1 share
  Assets out: 1 × 1000 / 100 = 10 USDC

Result: Put in 5 USDC, got back 10 USDC.
```

The attacker doubled their money. Repeat in a loop, and the pool drains as other depositors' value is extracted one rounding error at a time.

> Always round so the protocol keeps more value, never less.

As much as this could appear as greediness, it's just about making attacks unprofitable. 

When rounding favors the protocol, the attacker loses gas fees on each iteration while gaining nothing.

### Rounding Direction by Operation

| Operation | Direction | Why |
|-----------|-----------|-----|
| Mint LP tokens/shares | DOWN | Give user fewer shares |
| Burn LP for assets | DOWN | Give user fewer assets |
| Swap output | DOWN | Give user fewer tokens |
| Fees charged | UP | Take more from user |
| Debt on borrow | UP | User owes more |
| Repayment required | UP | User pays more |
| Interest accrued | UP | Protocol earns more |
| Collateral value | DOWN | Less borrowing power |
| Health factor | DOWN | Liquidation triggers sooner |

### Implementation

The base formula for calculating shares from a deposit:

```
shares = (deposit × total_shares) / total_assets
```

**Round DOWN** (default in Rust, integer division truncates):

```rust
// User deposits, protocol mints shares - round DOWN to protect protocol
let shares = (deposit * total_shares) / total_assets;
```

**Round UP** (add `divisor - 1` to numerator):

```rust
// User deposits, protocol mints shares - round UP favors user (dangerous!)
let shares = (deposit * total_shares + total_assets - 1) / total_assets;
```

Why does adding `divisor - 1` round up? It ensures any remainder pushes to the next integer:

```
Without trick: 7 / 3 = 2  (truncates the 0.33 remainder)
With trick:    (7 + 2) / 3 = 9 / 3 = 3  (remainder captured)

Without trick: 6 / 3 = 2  (no remainder)
With trick:    (6 + 2) / 3 = 8 / 3 = 2  (still 2, no false rounding)
```

For this reason, here are some helper functions you'll use constantly:

```rust
/// Round down
pub fn div_floor(numerator: u128, denominator: u128) -> u128 {
    numerator / denominator
}

/// Round up
pub fn div_ceil(numerator: u128, denominator: u128) -> u128 {
    (numerator + denominator - 1) / denominator
}
```

<ArticleSection name="Safe Math" id="safe-math" level="h2" />

DeFi deals with large numbers. When using multiplication inside a pool with $100M in TVL, the math can overflow a `u64` easily. 

For this reason you should always use `checked_*` operations:

```rust
// Bad: can overflow silently in release builds
let result = a * b / c;

// Good: explicit overflow handling
let result = a
    .checked_mul(b)?
    .checked_div(c)?;
```

And for intermediate calculations, you should transform them into a `u128` before normalizing it to u64 after divisions:

```rust
// Token amounts are u64, but intermediate math needs u128
let shares: u64 = ((deposit as u128)
    .checked_mul(total_shares as u128)?
    .checked_div(total_assets as u128)?) as u64;
```

The main reason to use `*_checked` is that Rust's standard arithmetic operators overflow silently during release builds; this means that even if your tests pass, your mainnet deployment wraps `u64::MAX + 1` to `0`. 

> Always use `checked_*` operations in production code.

### Order of Operations

Using the right mental models and safe math isn't everything; ordering is key as well.

Watch what happens with different ordering:

```rust
// Division first
let result = (7 / 3) * 100;  // = 2 * 100 = 200

// Multiplication first
let result = (7 * 100) / 3;  // = 700 / 3 = 233
```

Same inputs but 16% difference in output. The division-first approach destroyed precision before multiplication could preserve it.

> Every division truncates your number; you should delay them till you finished all other operations first.

# Lending & Borrowing

How do you lend money to someone you don't know, can't identify, and can't sue?

You demand collateral worth more than the loan. If they don't repay, you keep it.

This is **overcollateralized lending**: deposit $10,000 in SOL, borrow $7,500 in USDC. If SOL crashes and you don't repay, the protocol sells your SOL to cover the debt. No courts, no collections, just code.

The math handles everything banks use lawyers for: When is collateral worth too little? Who triggers the liquidation? How do interest rates balance supply and demand?

<ArticleSection name="Core Mechanics" id="core-mechanics" level="h2" />

### Why Shares Instead of Balances?

Imagine tracking each depositor's balance individually. Alice deposits 1000 USDC. Bob deposits 500. Interest accrues. Now you need to update Alice's balance, Bob's balance, and everyone else's. Every second. Forever.

That's expensive. Instead, we use **shares**.

You deposit USDC, you get shares. Those shares represent your *percentage* of the pool, not a fixed amount. When interest accrues, the pool grows, but the share count stays the same. Your shares are now worth more.

```
Day 1: Pool has 10,000 USDC, 10,000 shares
       You deposit 1,000 USDC → receive 1,000 shares (10% of pool)

Day 30: Interest accrues, pool now has 11,000 USDC, still 10,000 shares
        Your 1,000 shares = 10% of 11,000 = 1,100 USDC
```

One global update (the pool total) instead of thousands of individual updates. The share-to-asset ratio is all you need:

```rust
// What your shares are worth
let your_value = your_shares * pool.total_assets / pool.total_shares;
```

### The Pool State

A minimal lending pool state to allow for every basic action securely should have the following fields:

```rust
#[account]
pub struct LendingPool {
    pub total_deposits: u64,     // Actual tokens in pool
    pub total_shares: u64,       // Receipt tokens minted
    pub total_borrows: u64,      // Tokens borrowed out
    pub borrow_index: u128,      // Accumulated interest multiplier
    pub last_update: i64,        // Last interest accrual
}
```

After this we can finally explore the 3 main actions that we should plan for in a lending market.

### Deposit Flow

Give assets, receive shares. The protocol mints shares proportional to your deposit relative to the pool.

```rust
pub fn deposit(ctx: Context<Deposit>, amount: u64) -> Result<()> {
    let pool = &mut ctx.accounts.pool;

    // Calculate shares to mint (round DOWN - protocol keeps dust)
    let shares = if pool.total_shares == 0 {
        amount  // First deposit: 1:1
    } else {
        (amount as u128 * pool.total_shares as u128 / pool.total_deposits as u128) as u64
    };

    transfer(/* user -> pool vault */, amount)?;
    mint_to(/* -> user */, shares)?;

    pool.total_deposits += amount;
    pool.total_shares += shares;

    Ok(())
}
```

### Borrow Flow

Lock collateral, take assets. You can only borrow up to a percentage of your collateral's value.

```rust
pub fn borrow(ctx: Context<Borrow>, amount: u64) -> Result<()> {
    let pool = &mut ctx.accounts.pool;
    let position = &mut ctx.accounts.user_position;

    // Check collateral covers this borrow
    let max_borrow = calculate_max_borrow(position.collateral_value, pool.ltv_bps);
    require!(position.borrowed + amount <= max_borrow, ErrorCode::InsufficientCollateral);

    transfer(/* pool vault -> user */, amount)?;

    // Track debt (round UP - user owes more)
    position.borrowed += amount;
    pool.total_borrows += amount;

    Ok(())
}
```

### Repay Flow

Return assets plus interest, unlock collateral. Interest is calculated from a global index.

```rust
pub fn repay(ctx: Context<Repay>, amount: u64) -> Result<()> {
    let pool = &mut ctx.accounts.pool;
    let position = &mut ctx.accounts.user_position;

    // Can't repay more than owed
    let debt = get_current_debt(position, pool);
    let repay_amount = std::cmp::min(amount, debt);

    transfer(/* user -> pool vault */, repay_amount)?;

    position.borrowed = debt - repay_amount;
    pool.total_borrows -= repay_amount;

    Ok(())
}
```

<ArticleSection name="Collateralization" id="collateralization" level="h2" />

Before moving on, we should learn more about the most important part about a lending market. How does the collateral interact with all actions to remain safe:

### The Buffer Zone

Two numbers control the risk:

- **LTV (Loan-to-Value)**: Maximum you can borrow. 75% LTV = $100 collateral lets you borrow $75.
- **Liquidation Threshold**: When you get liquidated. 80% threshold = if debt reaches 80% of collateral, you're in trouble.

This two concept are the essential step to manage risk and avoid bad debt.

```
You deposit $10,000 SOL
At 75% LTV, you can borrow up to $7,500 USDC
At 80% liquidation threshold, you're liquidated when debt = 80% of collateral

The 5% gap gives you room to breathe. If SOL drops a bit, you're not immediately liquidated.
```

### Health factor

The previously mentioned concept, are used in a lending market to calculate the health factor of each position:

```
health = (collateral_value × liquidation_threshold) / debt_value
```

- Health > 1.0: You're safe
- Health < 1.0: You can be liquidated

Let's walk through a scenario:

```
Start:
  Collateral: $10,000 SOL
  Debt: $7,500 USDC
  Liquidation threshold: 80%
  
  Health = ($10,000 × 0.80) / $7,500 = 1.067 ✓ Safe

SOL drops 10%:
  Collateral: $9,000 SOL
  Debt: $7,500 USDC (unchanged)
  
  Health = ($9,000 × 0.80) / $7,500 = 0.96 ✗ Liquidatable
```

Just a 10% price drop took you from safe to liquidated. That's why the buffer matters, and why volatile assets get lower LTV limits.

```rust
pub fn calculate_health_factor(
    collateral_value: u128,
    debt_value: u128,
    liq_threshold_bps: u64,
) -> u128 {
    if debt_value == 0 {
        return u128::MAX;  // No debt = infinite health
    }
    // Round DOWN - triggers liquidation sooner (protocol protection)
    (collateral_value * liq_threshold_bps as u128) / (debt_value * 10_000)
}
```

### Per-Asset Risk

Not all collateral is equal. SOL has deep liquidity and can be sold quickly. A random memecoin might crash 50% before you can liquidate it.

Protocols assign different parameters per asset:

| Asset | LTV | Liquidation Threshold | Why |
|-------|-----|----------------------|-----|
| SOL | 75% | 80% | Liquid, stable-ish |
| ETH | 80% | 85% | Very liquid |
| Memecoin | 50% | 60% | Volatile, thin liquidity |

When you have mixed collateral, each asset contributes to health factor weighted by its own threshold:

```rust
#[account]
pub struct AssetConfig {
    pub mint: Pubkey,
    pub ltv_bps: u16,           // Max borrow ratio
    pub liq_threshold_bps: u16, // Liquidation trigger
    pub liq_bonus_bps: u16,     // Liquidator incentive
    pub oracle: Pubkey,         // Price feed
}

pub fn calculate_position_health(
    collaterals: &[(u64, AssetConfig, u64)],  // (amount, config, price)
    debts: &[(u64, u64)],                      // (amount, price)
) -> u128 {
    let mut weighted_collateral: u128 = 0;
    let mut total_debt: u128 = 0;

    for (amount, config, price) in collaterals {
        let value = (*amount as u128) * (*price as u128) / PRICE_PRECISION;
        weighted_collateral += value * config.liq_threshold_bps as u128 / 10_000;
    }

    for (amount, price) in debts {
        total_debt += (*amount as u128) * (*price as u128) / PRICE_PRECISION;
    }

    if total_debt == 0 { return u128::MAX; }
    (weighted_collateral * PRECISION) / total_debt
}
```

<ArticleSection name="Interest Rates" id="interest-rates" level="h2" />

### The Balancing Act

Interest rates have to solve a paradox: lenders want high yields, borrowers want low rates. Make lenders happy and no one borrows. Make borrowers happy and no one deposits.

The solution: let **utilization** set the rate.

```
Utilization = Total Borrowed / Total Deposited
```

- Low utilization (20%): Most deposits sit idle. Low rates to attract borrowers.
- High utilization (95%): Almost everything is borrowed. High rates to attract deposits and discourage borrowing.

This creates a self-balancing market. No governance vote needed, the math does it.

### The Kinked Curve

Linear rates have a problem: at 95% utilization, depositors can't withdraw. There's no liquidity left.

The fix is a **kinked curve**: gentle slope up to 80% utilization, then a steep cliff.

```
0-80% utilization:   2% → 6% (gentle)
80-100% utilization: 6% → 80% (steep)
```

That cliff creates urgency. At 90% utilization, borrowers face 40% rates. They rush to repay. Meanwhile, lenders see great yields and rush to deposit. The protocol self-corrects without intervention.

```rust
pub fn calculate_borrow_rate(utilization: u64) -> u64 {
    if utilization <= OPTIMAL_UTILIZATION {
        BASE_RATE + (utilization * SLOPE_1 / OPTIMAL_UTILIZATION)
    } else {
        let base_at_kink = BASE_RATE + SLOPE_1;
        let excess = utilization - OPTIMAL_UTILIZATION;
        base_at_kink + (excess * SLOPE_2 / (PRECISION - OPTIMAL_UTILIZATION))
    }
}
```

### Tracking Interest Without Per-User Updates

Interest accrues continuously. Updating every user's debt every block is impossible. Instead, protocols use an **index**.

The borrow index starts at 1.0 and grows over time as interest accrues. When you borrow, the protocol records the current index. Your debt is always:

```
current_debt = original_borrow × (current_index / index_at_borrow)
```

If the index was 1.0 when you borrowed 1000 USDC, and it's now 1.1, you owe 1100 USDC. One global index serves all borrowers.

```rust
#[account]
pub struct UserPosition {
    pub borrowed_shares: u64,        // Not raw amount, but indexed shares
    pub borrow_index_at_open: u128,  // Index when borrowed
}

pub fn accrue_interest(pool: &mut LendingPool, current_time: i64) {
    let time_elapsed = current_time - pool.last_update;
    if time_elapsed <= 0 { return; }

    let utilization = (pool.total_borrows as u128 * PRECISION / pool.total_deposits as u128) as u64;
    let rate = calculate_borrow_rate(utilization);

    // Compound interest: index *= (1 + rate * time / year)
    let interest_factor = PRECISION + (rate * time_elapsed as u64 / SECONDS_PER_YEAR);
    pool.borrow_index = pool.borrow_index * interest_factor as u128 / PRECISION as u128;
    pool.total_borrows = (pool.total_borrows as u128 * interest_factor as u128 / PRECISION as u128) as u64;
    pool.last_update = current_time;
}

pub fn get_current_debt(position: &UserPosition, pool: &LendingPool) -> u64 {
    (position.borrowed_shares as u128 
        * pool.borrow_index 
        / position.borrow_index_at_open) as u64
}
```

<ArticleSection name="Liquidations" id="liquidations" level="h2" />

### The Cleanup Crew

When health drops below 1.0, anyone can liquidate you. The liquidator:

1. Pays off part of your debt
2. Takes your collateral at a discount (the **liquidation bonus**)

Why would anyone do this? Profit. 

If the bonus is 5%, they pay $100 of your debt and receive $105 of your collateral.

```
Your position:
  Collateral: $9,000 SOL
  Debt: $7,500 USDC
  Health: 0.96 (liquidatable)

Liquidator:
  Pays: $3,750 USDC (50% of debt - the close factor)
  Receives: $3,937.50 worth of SOL (5% bonus)
  Profit: $187.50
```

This is how a liquidation function looks like:

```rust
pub fn liquidate(ctx: Context<Liquidate>, debt_to_repay: u64) -> Result<()> {
    let position = &mut ctx.accounts.borrower_position;
    let pool = &ctx.accounts.pool;

    // Verify position is liquidatable
    let health = calculate_health_factor(position, pool);
    require!(health < PRECISION, ErrorCode::PositionHealthy);

    // Apply close factor (can't liquidate 100% at once)
    let max_repay = position.debt * pool.close_factor_bps / 10_000;
    let repay_amount = std::cmp::min(debt_to_repay, max_repay);

    // Calculate collateral to seize (including bonus)
    let collateral_value = repay_amount * (10_000 + pool.liq_bonus_bps) / 10_000;
    let collateral_amount = collateral_value * PRICE_PRECISION / collateral_price;

    transfer(/* liquidator pays debt */)?;
    transfer(/* borrower's collateral to liquidator */)?;

    position.debt -= repay_amount;
    position.collateral -= collateral_amount;

    Ok(())
}
```

### Why Not Liquidate Everything?

The **close factor** (typically 50%) limits how much can be liquidated at once:

```rust
const CLOSE_FACTOR_BPS: u64 = 5000;  // 50%
let max_liquidatable = total_debt * CLOSE_FACTOR_BPS / 10_000;
```

Why this limit?

1. **Protects borrowers**: If price briefly dips then recovers, you're not fully wiped out
2. **Reduces cascade risk**: Selling huge amounts of collateral crashes the price, triggering more liquidations
3. **Distributes opportunity**: Multiple liquidators can participate

### When Liquidations Fail: Bad Debt

Sometimes prices move too fast. By the time liquidators act, the collateral is worth less than the debt.

```
Collateral: $95
Debt: $100
Liquidation bonus: 5%

Liquidator needs: $100 × 1.05 = $105 of collateral
Available: $95

Nobody will liquidate at a loss.
```

This is **bad debt**. The protocol must absorb it somehow:
- Insurance fund pays it off
- Losses spread across all depositors
- Protocol token holders take the hit

<ArticleSection name="Attack Vectors" id="vulnerabilities" level="h2" />

### Oracle Manipulation

The classic attack:

1. Flash loan a huge amount
2. Buy some illiquid token on a thin DEX, spiking its price
3. Deposit that token as collateral (the protocol thinks it's valuable)
4. Borrow real assets against the fake value
5. Don't repay. Keep the borrowed assets. Let the inflated collateral get liquidated.

**Defense**: Never trust spot prices. Use Pyth/Switchboard with confidence intervals. Require TWAP for large positions. Set sanity bounds on price changes.

### Liquidation Cascades

One liquidation dumps collateral on the market. Price drops. More positions become liquidatable. More liquidations. More dumping. Cascade.

This is what happened during the March 2020 crash. Ethereum dropped 50% in hours. Liquidators couldn't keep up. Bad debt piled up.

**Defense**: Conservative LTV ratios. Gradual liquidation (close factors). Circuit breakers that pause during extreme volatility.

### Interest Rounding

Small rounding errors compound. If you round interest down (user-favorable), you lose value over millions of operations.

```rust
// Bad: rounds down
interest = principal * rate / PRECISION;

// Good: rounds up (protocol keeps the dust)
interest = (principal * rate + PRECISION - 1) / PRECISION;
```

Always round in the protocol's favor. Users pay slightly more, but the protocol stays solvent.

# 데이터 읽기 및 쓰기

최적화된 Solana 프로그램을 구축할 때 효율적인 데이터 serialization 및 deserialization은 성능에 큰 영향을 미칠 수 있습니다.

Pinocchio는 low-level memory operations을 요구하지 않지만, account 데이터를 효율적으로 읽고 쓰는 방법을 이해하면 더 빠른 프로그램을 구축하는 데 도움이 될 수 있습니다.

이 가이드의 기술은 Pinocchio, Anchor 또는 native SDK를 사용하든 관계없이 모든 Solana 개발 framework에서 작동합니다. 핵심은 데이터 structures를 신중하게 설계하고 serialization을 안전하게 처리하는 것입니다.

### Unsafe Code를 사용해야 할 때

unsafe code는 다음 경우에만 사용하십시오:
- 최대 성능이 필요하고 안전한 대안이 너무 느리다고 측정했을 때
- 모든 safety invariants를 엄격하게 검증할 수 있을 때
- safety requirements를 명확하게 문서화할 때

> 가능하면 안전한 대안을 선호하십시오.

<ArticleSection name="Safety Principles" id="safety-principles" level="h2" />

raw byte arrays 및 memory operations을 다룰 때는 undefined behavior를 피하기 위해 주의해야 합니다. 이러한 원칙을 이해하는 것은 정확하고 신뢰할 수 있는 code를 작성하는 데 매우 중요합니다.

### Buffer Bounds Checking

읽기 또는 쓰기 operation을 수행하기 전에 항상 buffer가 충분히 큰지 확인하십시오. 할당된 memory를 넘어 읽거나 쓰는 것은 undefined behavior입니다.

```rust
// Good: Check bounds first
if data.len() < size_of::<u64>() {
    return Err(ProgramError::InvalidInstructionData);
}
let value = u64::from_le_bytes(data[0..8].try_into().unwrap());

// Bad: No bounds checking - could panic or cause UB
let value = u64::from_le_bytes(data[0..8].try_into().unwrap());
```

### Alignment Requirements

Rust의 모든 type은 memory에 배치될 위치를 결정하는 alignment requirement를 가집니다. 적절하게 정렬되지 않은 memory에서 type을 읽는 것은 undefined behavior를 초래합니다. 대부분의 primitive types은 자신의 size와 동일한 alignment를 요구합니다:
- `u8`: 1-byte alignment
- `u16`: 2-byte alignment
- `u32`: 4-byte alignment
- `u64`: 8-byte alignment

이는 `u64`가 8로 나누어지는 memory addresses에 저장되어야 하며, `u16`은 짝수 addresses에서 시작해야 함을 의미합니다.

이를 준수하지 않으면 compiler는 각 field가 alignment requirements를 충족하도록 struct fields 사이에 보이지 않는 "padding" bytes를 자동으로 삽입합니다.

> 또한 struct의 총 size는 가장 큰 field의 alignment requirement의 배수여야 합니다.

정렬이 좋지 않은 struct의 예시는 다음과 같습니다:

```rust
#[repr(C)]
struct BadOrder {
    small: u8,    // 1 byte
    // padding: [u8; 7] since `big` needs to be aligned at 8 bytes.
    big: u64,     // 8 bytes  
    medium: u16,  // 2 bytes
    // padding: [u8; 6] since the struct size needs to be aligned to 8 bytes.
}
```

compiler는 `big`이 8-byte alignment를 요구하기 때문에 `small` 뒤에 7개의 padding bytes를 삽입합니다. 그런 다음 총 size(24 bytes)를 8의 배수로 만들기 위해 끝에 6 bytes를 더 추가하여 13 bytes를 낭비합니다.

더 나은 방법은 struct의 field를 다음과 같이 정렬하는 것입니다:

```rust
#[repr(C)]
struct GoodOrder {
    big: u64,     // 8 bytes
    medium: u16,  // 2 bytes  
    small: u8,    // 1 byte
    // padding: [u8; 5] since the struct size needs to be aligned to 8 bytes.
}
```

더 큰 field를 먼저 배치함으로써 padding을 13 bytes에서 5 bytes로 줄일 수 있습니다.

> 황금률은 padding을 최소화하고 memory 사용량을 줄이기 위해 struct fields를 가장 큰 alignment requirements부터 가장 작은 순서로 정렬하는 것입니다.

최대 공간 효율성을 위해 데이터를 serialization 및 deserialization하는 또 다른 고급 방법이 있습니다. alignment requirements가 완전히 제거된 Zero-Padding Structs를 만들 수 있습니다:

```rust
#[repr(C)]
struct ByteArrayStruct {
    big: [u8; 8],    // represents u64
    medium: [u8; 2], // represents u16  
    small: u8,
}
```

이 경우 모든 것이 1 byte aligned이므로 size는 정확히 11 bytes입니다.

### 유효한 Bit Patterns

모든 bit pattern이 모든 type에 대해 유효한 것은 아닙니다. `bool`, `char`, `enums`와 같은 type은 유효한 값이 제한되어 있습니다. 유효하지 않은 bit pattern을 이러한 type으로 읽는 것은 undefined behavior입니다.

<ArticleSection name="Reading Data" id="reading-data" level="h2" />

account buffer에서 데이터를 읽는 몇 가지 접근 방식이 있으며, 각각 다른 trade-offs가 있습니다:

### Field-by-Field Deserialization (권장)

가장 안전한 접근 방식은 각 field를 개별적으로 deserialize하는 것입니다. 이는 byte arrays로 작업하므로 모든 alignment 문제를 피할 수 있습니다:

```rust
pub struct DepositInstructionData {
    pub amount: u64,
    pub recipient: Pubkey,
}

impl<'a> TryFrom<&'a [u8]> for DepositInstructionData {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        if data.len() < (size_of::<u64>() + size_of::<Pubkey>()) {
            return Err(ProgramError::InvalidInstructionData);
        }

        // No alignment issues: we're reading bytes and converting
        let amount = u64::from_le_bytes(
            data[0..8].try_into()
                .map_err(|_| ProgramError::InvalidInstructionData)?
        );
        
        let recipient = Pubkey::try_from(&data[8..40])
            .map_err(|_| ProgramError::InvalidInstructionData)?;

        Ok(Self { amount, recipient })
    }
}
```

### Zero-Copy Deserialization

이것은 적절하게 정렬된 structs를 사용하여 최대 성능을 달성하는 데 사용될 수 있지만, 신중한 alignment checking이 필요합니다:

```rust
#[repr(C)]
pub struct Config {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    pub seed: u64,        // This field requires 8-byte alignment
    pub fee: u16,         // This field requires 2-byte alignment  
    pub state: u8,
    pub config_bump: u8,
}

impl Config {
    pub const LEN: usize = size_of::<Self>();
    
    pub fn from_bytes(data: &[u8]) -> Result<&Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        // Critical: Check alignment for the most restrictive field (u64 in this case)
        if (data.as_ptr() as usize) % core::mem::align_of::<Self>() != 0 {
            return Err(ProgramError::InvalidAccountData);
        }

        // SAFETY: We've verified length and alignment
        Ok(unsafe { &*(data.as_ptr() as *const Self) })
    }
}

// Alternative: Avoid alignment issues entirely by using byte arrays for types with
// alignment requirement greater than 1 and provide accessor methods
#[repr(C)]
pub struct ConfigSafe {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    seed: [u8; 8],      // Convert with u64::from_le_bytes when needed
    fee: [u8; 2],       // Convert with u16::from_le_bytes when needed
    pub state: u8,
    pub config_bump: u8,
}

impl ConfigSafe {
    pub fn from_bytes(data: &[u8]) -> Result<&Self, ProgramError> {
        if data.len() != size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // SAFETY: No alignment check needed - everything is u8 aligned
        Ok(unsafe { &*(data.as_ptr() as *const Self) })
    }
    
    pub fn seed(&self) -> u64 {
        u64::from_le_bytes(self.seed)
    }
    
    pub fn fee(&self) -> u16 {
        u16::from_le_bytes(self.fee)
    }
}
```

보시다시피 `seed` 및 `fee` field는 모두 private입니다. 이는 해당 값들이 byte arrays로 표현되므로 데이터를 읽을 때 항상 accessor methods를 사용해야 하기 때문입니다.

field에 직접 접근할 때 (`config.seed`), compiler는 해당 field의 memory 위치에 대한 reference를 일시적으로라도 생성해야 할 수 있습니다. 해당 field가 적절하게 정렬되지 않은 경우, reference를 명시적으로 사용하지 않더라도 reference를 생성하는 것은 undefined behavior입니다!

Accessor methods는 method scope 내에서 읽기 operation을 수행함으로써 이를 방지합니다. 이 경우 compiler는 중간 reference를 최적화하여 제거할 수 있습니다.

```rust
#[repr(C, packed)]  // This can cause unaligned fields!
pub struct PackedConfig {
    pub state: u8,
    pub seed: u64,    // This u64 might not be 8-byte aligned due to packing
}

impl PackedConfig {
    pub fn seed(&self) -> u64 {
        self.seed  // Safe: Direct value copy, no reference created
    }
}

// Usage:
let config = PackedConfig::load(account)?;

// ❌ UNDEFINED BEHAVIOR: Creates a reference to potentially unaligned field
let seed_ref = &config.seed; // Compiler must create a reference here!

// ❌ UNDEFINED BEHAVIOR: Even this can be problematic
let seed_value = config.seed; // May create temporary reference internally

// ✅ SAFE: Accessor method reads value without creating reference
let seed_value = config.seed(); // No intermediate reference
```

> `u8` field는 alignment가 1이고 항상 정렬되어 있으므로 `self.state`를 직접 사용할 수 있어 항상 안전하게 직접 접근할 수 있습니다.

이 경우 "special types"은 없지만, 일부 type은 유효하지 않은 bit patterns으로 인해 추가적인 주의가 필요하다는 점을 항상 기억하십시오:

```rust
pub struct StateAccount {
    pub is_active: bool,
    pub state_type: StateType,
    pub data: [u8; 32],
}

#[repr(u8)]
pub enum StateType {
    Inactive = 0,
    Active = 1,
    Paused = 2,
}

impl StateAccount {
    pub fn from_bytes(data: &[u8]) -> Result<Self, ProgramError> {
        if data.len() < size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // Safely handle bool (only 0 or 1 are valid)
        let is_active = match data[0] {
            0 => false,
            1 => true,
            _ => return Err(ProgramError::InvalidAccountData),
        };

        // Safely handle enum
        let state_type = match data[1] {
            0 => StateType::Inactive,
            1 => StateType::Active, 
            2 => StateType::Paused,
            _ => return Err(ProgramError::InvalidAccountData),
        };

        let mut data_array = [0u8; 32];
        data_array.copy_from_slice(&data[2..34]);

        Ok(Self {
            is_active,
            state_type,
            data: data_array,
        })
    }
}
```

### 피해야 할 위험한 패턴

다음은 undefined behavior로 이어질 수 있으므로 피해야 할 일반적인 패턴입니다:

1. `transmute()`와 함께 Unaligned Data 사용

```rust
// ❌ UNDEFINED BEHAVIOR: transmute requires proper alignment
let value: u64 = unsafe { core::mem::transmute(bytes_slice) };
```

`transmute()`는 source 데이터가 target type에 대해 적절하게 정렬되어 있다고 가정합니다. 임의의 byte slices를 다루는 경우, 이러한 가정은 종종 위반됩니다.

2. Packed Structs로 Pointer Casting

```rust
#[repr(C, packed)]
pub struct PackedConfig {
    pub state: u8,
    pub seed: u64,     // This u64 is only 1-byte aligned!
    pub authority: Pubkey,
}

// ❌ UNDEFINED BEHAVIOR: Creates references to unaligned fields
let config = unsafe { &*(data.as_ptr() as *const PackedConfig) };
let seed_value = config.seed; // UB: May create reference to unaligned u64
```

struct가 memory에 맞더라도 multi-byte field에 접근하면 unaligned references가 생성될 수 있습니다.

3. Packed Structs에 대한 Direct Field Access

```rust
#[repr(C, packed)]
pub struct PackedStruct {
    pub a: u8,
    pub b: u64,
}

let packed = /* ... */;
// ❌ UNDEFINED BEHAVIOR: Creates reference to unaligned field
let b_ref = &packed.b;
// ❌ UNDEFINED BEHAVIOR: May create temporary reference
let b_value = packed.b;
```

4. 검증 없는 Alignment 가정

```rust
// ❌ UNDEFINED BEHAVIOR: No alignment check
let config = unsafe { &*(data.as_ptr() as *const Config) };
```

데이터가 맞는다고 해서 제대로 정렬되었다는 의미는 아닙니다.

5. `read_unaligned()` 잘못 사용하기

```rust
// ❌ WRONG: read_unaligned needs proper layout, not just size
#[repr(Rust)]  // Default layout - not guaranteed!
pub struct BadStruct {
    pub field: u64,
}

let value = unsafe { (data.as_ptr() as *const BadStruct).read_unaligned() };
```

`read_unaligned()`는 struct가 여전히 예측 가능한 layout (`#[repr(C)]`)을 가져야 합니다.

<ArticleSection name="Writing Data" id="writing-data" level="h2" />

데이터를 안전하게 쓰는 것은 읽기와 유사한 원칙을 따릅니다:

### Field-by-Field Serialization (권장)

```rust
impl Config {
    pub fn write_to_buffer(&self, data: &mut [u8]) -> Result<(), ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        let mut offset = 0;
        
        // Write authority
        data[offset..offset + 32].copy_from_slice(self.authority.as_ref());
        offset += 32;
        
        // Write mint_x  
        data[offset..offset + 32].copy_from_slice(self.mint_x.as_ref());
        offset += 32;
        
        // Write mint_y
        data[offset..offset + 32].copy_from_slice(self.mint_y.as_ref());
        offset += 32;
        
        // Write seed
        data[offset..offset + 8].copy_from_slice(&self.seed.to_le_bytes());
        offset += 8;
        
        // Write fee
        data[offset..offset + 2].copy_from_slice(&self.fee.to_le_bytes());
        offset += 2;
        
        // Write state
        data[offset] = self.state;
        offset += 1;
        
        // Write config_bump
        data[offset] = self.config_bump;

        Ok(())
    }
}
```

이 접근 방식은 각 field를 byte buffer에 명시적으로 serialize하기 때문에 가장 안전한 방법입니다:
- alignment 걱정 없음: byte array에 쓰고 있습니다.
- 명시적 endianness: `to_le_bytes()`로 byte order를 제어합니다.
- 명확한 memory layout: 디버깅 및 이해 용이
- undefined behavior 없음: 모든 operation은 byte arrays에서 이루어집니다.

### Direct Mutation (Zero-Copy)

최대 성능을 위해 byte buffer를 struct로 casting하고 field를 직접 변경할 수 있습니다. 이를 위해서는 struct가 적절하게 정렬되어야 합니다:

```rust
impl Config {
    pub fn from_bytes_mut(data: &mut [u8]) -> Result<&mut Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        // Check alignment
        if (data.as_ptr() as usize) % core::mem::align_of::<Self>() != 0 {
            return Err(ProgramError::InvalidAccountData);
        }

        // SAFETY: We've verified length and alignment
        Ok(unsafe { &mut *(data.as_mut_ptr() as *mut Self) })
    }
}
```

alignment가 확인되고 struct가 `#[repr(C)]`를 사용하는 경우, direct field mutation은 unaligned references를 생성하지 않습니다.

### Setters를 사용한 Byte Array 접근 방식 (가장 안전 + 빠름)

두 가지 장점을 모두 가집니다: 내부적으로 byte arrays를 사용하지만, 인체 공학적인 setters를 제공합니다:

```rust
#[repr(C)]
pub struct ConfigSafe {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    seed: [u8; 8],
    fee: [u8; 2],
    pub state: u8,
    pub config_bump: u8,
}

impl ConfigSafe {
    pub fn from_bytes_mut(data: &mut [u8]) -> Result<&mut Self, ProgramError> {
        if data.len() != size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // No alignment check needed - everything is u8 aligned
        Ok(unsafe { &mut *(data.as_mut_ptr() as *mut Self) })
    }
    
    pub fn seed(&self) -> u64 {
        u64::from_le_bytes(self.seed)
    }
    
    pub fn fee(&self) -> u16 {
        u16::from_le_bytes(self.fee)
    }

    // Setters that handle endianness correctly

    pub fn set_seed(&mut self, seed: u64) {
        self.seed = seed.to_le_bytes();
    }
    
    pub fn set_fee(&mut self, fee: u16) {
        self.fee = fee.to_le_bytes();
    }
}
```

이는 다음과 같은 이유로 이상적입니다:
- alignment 문제 없음: 모든 field는 byte-aligned입니다.
- 빠른 direct mutation: 초기 설정 후 serialization overhead 없음
- 일관된 endianness: setters가 byte order 변환을 처리합니다.
- Type safety: setters는 byte arrays가 아닌 예상되는 type을 받습니다.

<ArticleSection name="Dynamically Sized Data" id="dynamically-sized-data" level="h2" />

가능한 한, dynamically sized data를 account에 직접 저장하는 것을 피하십시오. 하지만 일부 사용 사례에서는 필요합니다.

account에 dynamic data가 포함되어 있다면, 항상 모든 statically sized field를 struct의 시작 부분에 배치하고, dynamic data는 끝에 추가하십시오.

### 단일 Dynamic Field

이것은 가장 간단한 경우입니다: account의 끝에 하나의 가변 길이 section이 있습니다:

```rust
#[repr(C)]
pub struct DynamicAccount {
    pub fixed_data: [u8; 32],
    pub counter: u64,
    // Dynamic data follows after the struct in memory
    // Layout: [fixed_data][counter][dynamic_data...]
}

impl DynamicAccount {
    pub const FIXED_SIZE: usize = size_of::<Self>();
    
    /// Safely parse account with dynamic data
    pub fn from_bytes_with_dynamic(data: &[u8]) -> Result<(&Self, &[u8]), ProgramError> {
        if data.len() < Self::FIXED_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }

        // SAFETY: We've verified the buffer is large enough for the fixed part
        // The fixed part only contains [u8; 32] and u64, which have predictable layout
        let fixed_part = unsafe { &*(data.as_ptr() as *const Self) };
        
        // Everything after the fixed part is dynamic data
        let dynamic_part = &data[Self::FIXED_SIZE..];
        
        Ok((fixed_part, dynamic_part))
    }
    
    /// Get mutable references to both parts
    pub fn from_bytes_mut_with_dynamic(data: &mut [u8]) -> Result<(&mut Self, &mut [u8]), ProgramError> {
        if data.len() < Self::FIXED_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }

        // Split the buffer to avoid borrowing issues
        let (fixed_bytes, dynamic_bytes) = data.split_at_mut(Self::FIXED_SIZE);
        
        // SAFETY: We've verified the size and split safely
        let fixed_part = unsafe { &mut *(fixed_bytes.as_mut_ptr() as *mut Self) };
        
        Ok((fixed_part, dynamic_bytes))
    }
}

/// Writing single dynamic field
impl DynamicAccount {
    pub fn write_with_dynamic(
        data: &mut [u8], 
        fixed_data: &[u8; 32], 
        counter: u64,
        dynamic_data: &[u8]
    ) -> Result<(), ProgramError> {
        let total_size = Self::FIXED_SIZE + dynamic_data.len();
        
        if data.len() != total_size {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // Write fixed part field by field (safest approach)
        data[0..32].copy_from_slice(fixed_data);
        data[32..40].copy_from_slice(&counter.to_le_bytes());
        
        // Write dynamic part
        data[Self::FIXED_SIZE..].copy_from_slice(dynamic_data);
        
        Ok(())
    }
    
    /// Update just the dynamic portion
    pub fn update_dynamic_data(&mut self, account_data: &mut [u8], new_data: &[u8]) -> Result<(), ProgramError> {
        if account_data.len() < Self::FIXED_SIZE + new_data.len() {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // Write new dynamic data
        account_data[Self::FIXED_SIZE..Self::FIXED_SIZE + new_data.len()].copy_from_slice(new_data);
        
        Ok(())
    }
}
```

undefined behavior를 피하려면, 항상 account data buffer가 statically sized 부분만큼 크거나 큰지 확인하십시오. dynamic section은 비어 있을 수 있으므로 이 확인은 필수적입니다.

이 layout은 dynamic data의 길이에 관계없이 fixed-size field의 offset이 항상 알려지도록 보장합니다.

dynamically sized data를 읽을 때 두 가지 주요 시나리오가 있습니다:

- 끝에 단일 dynamic field: 다음과 같이 runtime에 dynamic data의 size와 offset을 쉽게 결정할 수 있습니다:

```rust
const DYNAMIC_DATA_START_OFFSET: usize = size_of::<[u8; 32]>();

#[repr(C)]
pub struct DynamicallySizedAccount {
    pub sized_data: [u8; 32],
    // pub dynamic_data: &'info [u8], // Not part of the struct, but follows in the buffer
}

impl DynamicallySizedAccount {
    /// Returns the length of the dynamic data section.
    #[inline(always)]
    pub fn get_dynamic_data_len(data: &[u8]) -> Result<usize, ProgramError> {
        if data.len().le(&DYNAMIC_DATA_START_OFFSET) {
            return Err(ProgramError::InvalidAccountData);
        }

        Ok(data.len() - DYNAMIC_DATA_START_OFFSET)
    }

    /// Returns a slice of the dynamic data.
    #[inline(always)]
    pub fn read_dynamic_data(data: &[u8]) -> Result<&[u8], ProgramError> {
        if data.len().le(&DYNAMIC_DATA_START_OFFSET) {
            return Err(ProgramError::InvalidAccountData);
        }

        Ok(&data[DYNAMIC_DATA_START_OFFSET..])
    }
}
```

### 다중 Dynamic Fields

이 접근 방식은 마지막 dynamic field를 제외한 각 dynamic field의 길이를 결정하는 방법이 필요하므로 더 복잡합니다. 가장 일반적인 접근 방식은 각 dynamic field (마지막 필드 제외) 앞에 길이를 접두사로 붙여 buffer를 올바르게 parse할 수 있도록 하는 것입니다.

여기에 간단하고 강력한 패턴이 있습니다: 첫 번째 dynamic field의 길이를 u8 (또는 더 큰 크기가 필요한 경우 u16 등)로 statically sized data 바로 뒤에 저장합니다. 첫 번째 dynamic field가 뒤따르고, 두 번째 dynamic field는 buffer의 나머지 부분을 차지합니다.

```rust
#[repr(C)]  
pub struct MultiDynamicAccount {
    pub fixed_data: [u8; 32],
    pub timestamp: u64,
    // Layout: [fixed_data][timestamp][len1: u8][data1][data2: remainder]
}

impl MultiDynamicAccount {
    pub const FIXED_SIZE: usize = size_of::<Self>();
    pub const LEN_PREFIX_SIZE: usize = size_of::<u8>();
    pub const MIN_SIZE: usize = Self::FIXED_SIZE + Self::LEN_PREFIX_SIZE;
    
    /// Parse account with two dynamic sections
    pub fn parse_dynamic_fields(data: &[u8]) -> Result<(&[u8; 32], u64, &[u8], &[u8]), ProgramError> {
        if data.len() < Self::MIN_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // Extract fixed data safely
        let fixed_data = data[..32].try_into()
            .map_err(|_| ProgramError::InvalidAccountData)?;
            
        let timestamp = u64::from_le_bytes(
            data[32..40].try_into()
                .map_err(|_| ProgramError::InvalidAccountData)?
        );
            
        // Read length of first dynamic field (single byte)
        let len = data[Self::FIXED_SIZE] as usize;
        
        // Validate we have enough data
        if data.len() <  Self::MIN_SIZE + len {
            return Err(ProgramError::InvalidAccountData);
        }
        
        let data_1 = &data[Self::MIN_SIZE..Self::MIN_SIZE + len];
        let data_2 = &data[Self::MIN_SIZE + len..]; // Remainder
        
        Ok((fixed_data, timestamp, data_1, data_2))
    }
    
    /// Write account with two dynamic sections
    pub fn write_with_multiple_dynamic(
        buffer: &mut [u8],
        fixed_data: &[u8; 32],
        timestamp: u64,
        data_1: &[u8],
        data_2: &[u8]
    ) -> Result<(), ProgramError> {
        let total_size = Self::MIN_SIZE + data_1.len() + data_2.len();
        
        if buffer.len() != total_size {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // Validate data_1 length fits in u8
        if data_1.len() > u8::MAX as usize {
            return Err(ProgramError::InvalidInstructionData);
        }
        
        let mut offset = 0;
        
        // Write fixed data
        buffer[offset..offset + 32].copy_from_slice(fixed_data);
        offset += 32;
        
        buffer[offset..offset + 8].copy_from_slice(&timestamp.to_le_bytes());
        offset += 8;
        
        // Write length prefix for data1 (single byte)
        buffer[offset] = data_1.len() as u8;
        offset += 1;
        
        // Write data1
        buffer[offset..offset + data_1.len()].copy_from_slice(data_1);
        offset += data_1.len();
        
        // Write data2 (remainder - no length prefix needed)
        buffer[offset..].copy_from_slice(data_2);
        
        Ok(())
    }
}
```

### account 크기 조정

dynamic field를 업데이트할 때마다 size가 변경되면 account 크기를 조정해야 합니다. 다음은 account 크기를 조정하는 일반적인 목적의 function입니다:

```rust
pub fn resize_account(
    account: &AccountInfo,
    payer: &AccountInfo,
    new_size: usize,
    zero_out: bool,
) -> ProgramResult {
    // If the account is already the correct size, return early
    if new_size == account.data_len() {
        return Ok(());
    }

    // Calculate rent requirements
    let rent = Rent::get()?;
    let new_minimum_balance = rent.minimum_balance(new_size);

    // Adjust lamports to meet rent-exemption requirements
    match new_minimum_balance.cmp(&account.lamports()) {
        core::cmp::Ordering::Greater => {
            // Need more lamports for rent exemption
            let lamports_diff = new_minimum_balance.saturating_sub(account.lamports());
            **payer.try_borrow_mut_lamports()? -= lamports_diff;
            **account.try_borrow_mut_lamports()? += lamports_diff;
        }
        core::cmp::Ordering::Less => {
            // Return excess lamports to payer
            let lamports_diff = account.lamports().saturating_sub(new_minimum_balance);
            **account.try_borrow_mut_lamports()? -= lamports_diff;
            **payer.try_borrow_mut_lamports()? += lamports_diff;
        }
        core::cmp::Ordering::Equal => {
            // No lamport transfer needed
        }
    }

    // Reallocate the account
    account.resize(new_size)?;

    Ok(())
}
```

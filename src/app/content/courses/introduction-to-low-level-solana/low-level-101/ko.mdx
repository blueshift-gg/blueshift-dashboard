# Low-level 101

![Image Test](/graphics/banners/research-crateless-program.png)

Solana program을 작성해 보셨다면, Entrypoint, CPIs, account 관리와 같은 프로그램의 기본적인 요구사항들이 일반적으로 solana_program 및 pinocchio와 같은 crates에 의해 처리된다는 것을 잘 아실 겁니다. 이 crates들은 anchor, steel 등과 같은 프레임워크에 의해 내부적으로 사용됩니다.

하지만 Solana 스택을 진정으로 이해하고 최적화하려면, 이러한 모든 abstraction 뒤에 숨겨진 것들을 들여다보고 내부에서 무슨 일이 일어나는지 파악해야 합니다. 이 과정에서는 완전히 수작업으로 만들어진, 의존성 없는 Solana program을 처음부터 만들 것입니다.

다양한 수작업 구성 요소를 살펴보기 전에, Solana program이 작동하게 하는 근본적인 빌딩 블록들을 이해해야 합니다.

<ArticleSection name="eBPF" id="eBPF" level="h2" />

Solana program은 네이티브 머신 코드가 아닌 eBPF (extended Berkeley Packet Filter) 바이트코드로 컴파일됩니다. 이러한 아키텍처적 선택은 Solana의 여러 특징을 설명합니다:
- **Compute unit 제한**: eBPF의 안전 모델은 명령어 수를 세어 무한 루프를 방지합니다.
- **힙 할당 없음**: eBPF program은 malloc/free 없이 샌드박스 환경에서 실행됩니다.
- **제한된 스택**: 4KB의 스택 공간만으로 신중한 메모리 관리가 필요합니다.
- **결정론적 실행**: 동일한 입력은 모든 validator에서 항상 동일한 출력을 생성합니다.

이는 특정 Rust 기능이 Solana program에서 작동하지 않는 이유를 설명합니다. 런타임이 해당 기능을 문자 그대로 실행할 수 없기 때문입니다.

<ArticleSection name="#[repr(C)] & extern `C`" id="repr-c-and-extern-c" level="h2" />

어떤 저수준 Solana 예제를 보더라도, 두 가지 패턴이 어디에나 나타납니다:

```rust
#[repr(C)]              
pub struct MyState { … }

pub unsafe extern "C" fn entrypoint(ptr: *mut u8) -> u64 { … }
```

**`extern "C"`**

Rust 컴파일러에게 C ABI (Application Binary Interface)를 사용하여 함수를 노출하도록 지시합니다. C ABI는 어떤 eBPF 레지스터가 인수를 전달하고, 스택이 어떻게 배치되며, 어떤 레지스터가 값을 반환하는지 정의하는 호출 규칙입니다.

C ABI는 LLVM의 eBPF 백엔드가 지원하는 모든 언어(Rust, C, Zig, 또는 심지어 수작업으로 작성된 어셈블리)에서 가장 낮은 공통 분모이기 때문에 선택됩니다. Solana 런타임은 프로그램의 entrypoint를 원시 이름으로 호출하고 특정 레지스터를 통해 매개변수를 전달해야 합니다. C ABI는 어떤 언어로 바이트코드가 컴파일되었는지에 관계없이 이것이 작동하도록 보장합니다.

**`#[repr(C)]`** 

Rust가 C 컴파일러와 동일하게 struct 필드를 정렬하도록 강제하여, 필드 순서와 padding을 고정하여 바이트 레이아웃이 절대 변하지 않도록 합니다:

```rust
// #[repr(C)] 없이 - Rust는 최적화를 위해 이 필드들의 순서를 재정렬할 수 있습니다!
struct UnpredictableState {
    amount: u64,     // offset 0, 8, 또는 16에 있을 수 있음
    owner: [u8; 32], // 위치는 컴파일러에 따라 달라짐
    bump: u8,        // 어디든 압축되거나 padding될 수 있음
}

// #[repr(C)] 사용 시 - 레이아웃이 보장되고 예측 가능함
#[repr(C)]
struct PredictableState {
    amount: u64,     // 항상 offset 0
    owner: [u8; 32], // 항상 offset 8  
    bump: u8,        // 항상 offset 40
    // 암시적 padding: 8바이트 경계에 정렬하기 위한 7바이트
}
```

이는 account data가 프로그램 호출 사이에 유지되기 때문에 중요합니다. Rust가 컴파일 간에 필드 순서를 재정렬하면, 프로그램은 이전에 작성한 데이터를 읽을 수 없게 됩니다.

<ArticleSection name="Memory Layout Management" id="memory-layout-management" level="h2" />

고수준 프레임워크에서는 메모리 정렬이 자동으로 처리됩니다. 저수준에서는 모든 바이트가 중요합니다:

```rust
rust#[repr(C)]
struct BadAlignment {
    flag: u8,        // 1 바이트
    // 컴파일러가 여기에 7바이트의 padding을 삽입
    amount: u64,     // 8 바이트 - 8바이트 정렬 필요!
    owner: [u8; 32], // 32 바이트
} // 총: 48 바이트 (41 바이트가 아님!)

#[repr(C)]  
struct GoodAlignment {
    amount: u64,     // 8 바이트 - 자연 정렬됨
    owner: [u8; 32], // 32 바이트  
    flag: u8,        // 1 바이트
    // 끝에 7바이트의 padding만 존재
} // 총: 48 바이트, 하지만 padding은 예측 가능
```

메모리 관리 규칙은 각 필드가 자신의 크기로 나눌 수 있는 offset에서 시작해야 한다는 것입니다:
- `u8`: 아무 offset (1로 나눌 수 있음)
- `u16`: offset은 2로 나눌 수 있어야 함 (0, 2, 4...)
- `u32`: offset은 4로 나눌 수 있어야 함 (0, 4, 8...)
- `u64`: offset은 8로 나눌 수 있어야 함 (0, 8, 16...)

메모리 관리를 잘못하면 정렬되지 않은 메모리 접근으로 이어져 프로그램이 예측할 수 없게 실패할 수 있기 때문에 이는 매우 중요합니다. 

account data serialization을 수동으로 관리할 때, padding과 alignment를 이해하는 것은 cross-program 호환성을 위해 매우 중요합니다.

#### Syscalls 

**시스템 콜**(syscall)은 권한 없는 코드가 호스트로부터 특권 서비스를 요청하는 통로입니다. syscall이 발생하면, CPU는 사용자 모드에서 신뢰할 수 있는 특권 모드로 전환됩니다. 그 후 런타임은 요청된 작업을 수행하고, 상태 코드를 가지고 제어권을 반환합니다. 이러한 간접성은 샌드박스화된 코드가 호스트 메모리나 I/O를 직접 건드리지 못하게 하여 안전성과 결정론적 실행을 유지합니다.

Solana에서 BPF 바이트코드는 자체적으로 해싱, 로깅 또는 cross-program invocation (CPI)을 수행할 수 없습니다. 대신, `sol_log`, `sol_sha256`, `sol_invoke_signed`와 같은 명명된 syscall을 호출합니다.

각 syscall 번호는 로더의 dispatch table에 있는 단순한 인덱스입니다. 로더는 요청된 작업을 실행하고 `u64` status word를 반환합니다 (성공 시 0, 실패 시 0이 아닌 값).

예를 들어, `sol_invoke_signed`는 instruction, 해당 account list, 그리고 모든 PDA signer seeds를 묶어 로더에게 전달하고, 로더는 다음과 같이 적절한 권한 하에 CPI를 수행합니다:

```rust
/// Solana BPF syscall for invoking a signed instruction.
fn sol_invoke_signed_c(
    instruction_addr: *const u8,
    account_infos_addr: *const u8,
    account_infos_len: u64,
    signers_seeds_addr: *const u8,
    signers_seeds_len: u64,
) -> u64;
```

<ArticleSection name="The Vault Code" id="the-vault-code" level="h2" />

이제 "crate-less" Solana program의 모든 빌딩 블록을 풀어보았으니, vault 자체를 설명할 수 있습니다. 기억하십시오, vault는 정확히 두 가지를 수행합니다:
- **Deposit** (예금): 소유자의 public key에서 파생된 PDA에 lamports를 예금합니다.
- **Withdraw** (인출): 나중에 해당 lamports를 인출합니다. 오직 소유자만이 가능합니다.

따라서 각 instruction은 세 개의 account를 포함할 것입니다:
- **Owner** (signer, writable): 자금을 예금하거나 인출하는 사용자.
- **Vault** (writable): 모든 lamports가 담겨 있는 PDA.
- **System Program**: lamport transfer를 수행하는 데 필요한 account.

시작하기 전에 새 프로젝트를 생성해야 합니다. 터미널에서 다음 명령을 실행하십시오:

```
# 워크스페이스 생성
cargo new blueshift_vault --lib --edition 2021
cd blueshift_vault
```

`Cargo.toml`에 다음을 추가하십시오:

```
[lib]
crate-type = ["lib", "cdylib"]
```

#### Account Checks

`deposit` 또는 `withdraw`를 실행하기 전에, entrypoint는 transaction이 정확히 올바른 account를 제공했으며 각 account에 예상된 flag가 있는지 확인해야 합니다.

우리는 원시 포인터 수준에서 작업하고 있기 때문에, 모든 검사는 간단한 포인터 산술과 직접 로드를 통해 이루어집니다.

input 레코드의 처음 8바이트는 account_len을 담고 있습니다. 이 vault의 경우 owner, vault PDA, 그리고 System Program의 세 가지 account를 예상합니다:

```rust
// 3개의 account가 있는지 확인: Signer, Vault, Program
if *(input as *const u64) != 3 {
    sol_log_("Invalid number of accounts".as_ptr(), 26);
    return 1010; // NotEnoughAccountKeys Error
}
```

각 account를 계속해서 확인합니다. 이전에 정의한 layout offsets는 전체 struct를 역직렬화하지 않고도 모든 flag를 건전성 검사할 수 있게 해줍니다.

첫 번째 account인 signer에 대해 수행하는 검사는 다음과 같습니다: 
- 고유해야 함 (is_duplicate == 0xff)
- 쓰기 가능 (lamports를 변경할 것이기 때문)
- Signer
- 실행 가능하지 않음
- 데이터가 없어야 함 

```rust
if *(input.add(ACCOUNT_OFFSET) as *const u32) != 0x0101ff {
    sol_log_("Invalid Account 1 Data: Non-Duplicate, Writable, Signer, Non-Executable Check Failed".as_ptr(), 58);
    return 1003; // InvalidAccountData Error
}
if *(input.add(ACCOUNT_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 1 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

나중에 PDA 검사를 위해 owner의 public key도 저장합니다:

```rust
let signer_key = *(input.add(ACCOUNT_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

두 번째 account인 vault에 대해 수행하는 검사는 다음과 같습니다:
- 쓰기 가능 (lamports를 변경할 것이기 때문)
- System Program이 소유함
- Data length는 0이어야 함 (여기에 state를 저장하지 않음)

```rust
const ACCOUNT_2_OFFSET: usize = ACCOUNT_OFFSET + ACCOUNT_RAW_LEN;

if *(input.add(ACCOUNT_2_OFFSET + IS_WRITABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 2 Data: Writable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != pinocchio_system::ID {
    sol_log_("Invalid Account 2 Data: Owner is not the System Program".as_ptr(), 48);
    return 1022; // InvalidAccountOwner Error
}

if *(input.add(ACCOUNT_2_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 2 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

나중에 PDA 검사를 위해 vault의 public key도 가져옵니다:

```rust
let vault_key = *(input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

마지막 account인 system program에 대해 수행하는 검사는 다음과 같습니다: 
- 실행 가능해야 함
- 그 key는 SYSTEM_PROGRAM_ID와 같아야 함

```rust
const ACCOUNT_3_OFFSET: usize = ACCOUNT_2_OFFSET + ACCOUNT_RAW_LEN;
const SYSTEM_PROGRAM_DATA_LENGTH: usize = 14 + 2;

if *(input.add(ACCOUNT_3_OFFSET + EXECUTABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 3 Data: Executable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != SYSTEM_PROGRAM_ID {
    sol_log_("Invalid Account 3 Data: Owner is not the System Program".as_ptr(), 48);
    return 1003; // InvalidAccountData Error
}
```

#### Instruction checks

account 유효성 검사 후, 마침내 instruction payload를 파싱할 수 있습니다. 그리고 첫 번째 바이트를 discriminator로 사용하여 native program과 동일한 접근 방식을 취합니다:

```rust
const INSTRUCTION_OFFSET: usize = ACCOUNT_3_OFFSET + ACCOUNT_RAW_LEN + SYSTEM_PROGRAM_DATA_LENGTH + INSTRUCTION_LEN_LEN;

let discriminator = *(input.add(INSTRUCTION_OFFSET) as *const u8);
match discriminator {
    0 => {
        sol_log_("Deposit".as_ptr(), 7);

        // deposit 로직 …

        return 0; // 성공
    }
    1 => {
        sol_log_("Withdraw".as_ptr(), 8);

        // withdraw 로직 …

        return 0; // 성공
    }
    _ => {
        sol_log_("Invalid Instruction".as_ptr(), 20);
        return 1002; // InvalidInstructionData Error
    }
}
```

여기서부터 우리는 deposit 또는 withdraw 핸들러로 분기하며, 모든 account와 flag가 vault가 예상하는 것과 정확히 일치한다고 확신합니다.

#### Deposit Logic

이제 deposit instruction에 대해 좀 더 자세히 살펴보겠습니다. 모든 검사는 처음에 이루어지며, 검사가 통과되면 System-Program transfer를 만들고 호출합니다.

이 instruction의 instruction data는 다음과 같습니다:
- 바이트 0은 discriminator (`deposit`의 경우 `0x00`)입니다.
- 바이트 1은 PDA 검사에 재사용할 bump입니다.
- 바이트 2-9는 little-endian으로 lamport amount를 담고 있으며, 값이 0이면 확인되어 거부됩니다.

```rust
let amount = *(input.add(INSTRUCTION_OFFSET + 2) as *const u64);
if amount == 0 {
    return 1002; // InvalidInstructionData Error
}
```

그 후 `sol_sha256` syscall을 사용하여 owner key를 해싱합니다. 이때 bump, program ID 및 고유 문자열 "ProgramDerivedAddress"를 사용합니다. 

결과를 account 검사 중에 저장한 vault key와 비교합니다. 만약 다르면 `InvalidSeeds`를 반환합니다.

만약 다르면 `InvalidSeeds`를 반환합니다.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

마지막으로 System-Program transfer를 만들 수 있습니다. 

System Program은 4바이트 discriminator (transfer의 경우 값은 2)를 사용하며, `from_account`에서 `to_account`로 전송할 양을 나타내는 추가 8바이트가 필요합니다.

다음으로 두 개의 SolAccountMeta 값으로 구성된 작은 배열을 만들어야 합니다: from = owner (signer, writable), to = vault (writable). 이를 `instruction_data`와 결합하여 `SolInstruction` struct를 생성합니다:

```rust
let mut instruction_data = [0; 12];
instruction_data[0] = 2; // discriminator
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes()); // amount

let accounts_addr: [SolAccountMeta; 2] = [
    // from_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    // to_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];

// instruction 생성
let instruction = SolInstruction {
    program_id_addr: input.add(ACCOUNT_3_OFFSET + KEY_OFFSET) as u64,
    accounts_addr: accounts_addr.as_ptr() as u64,
    accounts_len: 2,
    data_addr: instruction_data.as_ptr() as u64,
    data_len: 12,
};
```

하지만 `sol_invoke_signed_c` syscall을 호출하기 전에, owner와 vault를 위한 두 개의 `SolAccountInfo` struct를 만들어야 합니다. 이 struct들은 로더가 메모리에 남겨둔 위치에서 lamport 잔액과 data slices에 대한 포인터를 제공합니다.

그 후 instruction 포인터, 두 요소 `SolAccountInfo` 배열에 대한 포인터, 그리고 account 개수 (2)를 전달하여 syscall을 호출할 수 있습니다. 외부 transaction은 이미 owner에 의해 서명되었으므로, 여기서는 PDA seeds가 필요하지 않으며, 따라서 `signers_seeds_addr` 인수는 NULL입니다.

```rust
let account_infos_addr: [SolAccountInfo; 2] = [
    SolAccountInfo {
        is_signer: true,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
    SolAccountInfo {
        is_signer: false,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_2_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
];

// signer seeds로 instruction 호출
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // account 개수
    core::ptr::null(),
    0,
);
```

#### Withdraw Logic

withdraw instruction은 deposit과 유사하지만, 몇 가지 주요 차이점이 있습니다. instruction data는 더 간단합니다:
- 바이트 0은 discriminator (`withdraw`의 경우 `0x01`)입니다.
- 바이트 1은 PDA 검사에 재사용할 bump입니다.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
```

deposit에서와 동일한 PDA 검사를 수행하며, owner의 public key, bump, program ID 및 고유 문자열 "ProgramDerivedAddress"를 사용합니다:

```rust
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

withdraw의 주요 차이점은 PDA 자체로 transaction에 서명해야 한다는 것입니다. 이를 위해 PDA를 파생하는 데 사용된 seeds를 제공해야 합니다. 두 개의 요소로 구성된 `SolSignerSeedsC` 배열을 생성합니다:
- owner의 public key (32바이트)
- bump (1바이트)

```rust
let seeds: [SolSignerSeedsC; 2] = [
    SolSignerSeedsC {
        addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        len: 32,
    },
    SolSignerSeedsC {
        addr: input.add(INSTRUCTION_OFFSET + 1) as u64,
        len: 1,
    },
];

let signer_seeds_addr: [SolSignerSeedsC; 1] = [
    SolSignerSeedsC {
        addr: seeds.as_ptr() as u64,
        len: 2,
    },
];
```

다음으로 System Program transfer instruction을 만들지만, 이번에는 vault에서 owner로 전송합니다. instruction data는 deposit과 동일합니다:
- 4바이트 discriminator (transfer의 경우 값 2)
- amount를 위한 8바이트 (vault의 lamports에서 가져옴)

```rust
let amount = *(input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as *const u64);

let mut instruction_data = [0; 12];
instruction_data[0] = 2;
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes());
```

account meta는 deposit과 비교하여 역순입니다:
- 첫 번째 account는 vault (writable, signer)
- 두 번째 account는 owner (writable)

```rust
let account_addr: [SolAccountMeta; 2] = [
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];
```

마지막으로 instruction, account infos 및 이전에 생성한 signer seeds와 함께 `sol_invoke_signed_c`를 호출합니다:

```rust
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // account 개수
    signer_seeds_addr.as_ptr() as *const u8,
    1,
);
```

<ArticleSection name="Closing Remarks" id="closing-remarks" level="h2" />

Solana program을 작성하는 이러한 저수준 접근 방식이 극단적으로 보일 수 있지만, 이는 중요한 교육적 목적을 가집니다. 이러한 방식으로 프로그램을 작성하라고 권장하는 것이 아닙니다. 사실, 이러한 복잡성을 추상화하는 기존 프레임워크와 crates를 사용하는 것을 강력히 권장합니다. 하지만, 근본적인 메커니즘을 이해하는 것은 매우 중요합니다.

우리가 Solana 개발에서 사용하는 모든 abstraction, 즉 `solana_program`, `anchor`, 또는 다른 어떤 프레임워크든, 이 기본적인 빌딩 블록들 위에 구축됩니다. 레이어를 벗겨내고 원시 메커니즘을 검토함으로써, 우리는 다음 사항에 대해 더 깊이 이해하게 됩니다:

1. Solana 런타임이 우리 프로그램과 어떻게 상호작용하는지
2. 고수준 프레임워크에서 특정 설계 결정이 왜 이루어졌는지
3. 잠재적인 최적화가 어디에 존재할 수 있는지
4. 문제가 발생했을 때 어떻게 더 잘 디버그할 수 있는지

이 지식은 단순히 학문적인 것이 아니라 실용적입니다. 기초를 이해하면 다음을 할 수 있습니다:
- 데이터 구조 및 메모리 사용에 대해 정보에 입각한 결정을 내려 더 효율적인 프로그램을 작성합니다.
- 문제가 발생했을 때 더 잘 진단하고 해결합니다.
- 우리 모두가 사용하는 도구를 개선하여 생태계에 기여합니다.
- 특정 abstraction을 언제 사용하고 언제 더 낮은 수준에서 작업할지에 대해 정보에 입각한 결정을 내립니다.

기억하십시오, 이 연습의 목표는 crates 없이 프로그램을 작성하는 방법을 가르치는 것이 아니라, 해당 crates가 내부적으로 무엇을 하고 있는지 이해하도록 돕는 것이었습니다. 이러한 이해는 어떤 도구를 사용하든 더 좋고 효율적인 Solana program을 작성하기 위한 첫걸음입니다.

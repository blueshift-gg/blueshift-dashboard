# 블록체인 개요

![블록체인 개요](/graphics/course-banners/introduction-to-blockchain-and-solana.png)

아마도 블록체인에 대해 "디지털 화폐" 또는 "인터넷의 미래"로 묘사되는 것을 들어보셨을 겁니다. 이러한 설명들은 핵심을 완전히 놓치고 있습니다.

블록체인은 분산 시스템입니다. 즉, 서로를 신뢰하지 않으면서 공유 데이터에 합의해야 하는 컴퓨터 네트워크입니다. 이 코스는 블록체인을 기본 원칙부터 가르칩니다. 블록체인이 해결하는 분산 시스템 문제, 그 문제들을 어떻게 해결하는지, 그리고 트레이드오프가 왜 중요한지를 다룹니다.

분산 시스템을 구축하는 것이 컴퓨터 과학에서 가장 어려운 문제 중 하나인 이유를 이해하는 것부터 시작하겠습니다.

<ArticleSection name="분산 시스템" id="distributed-systems" level="h2" />

대부분의 사람들은 하나의 컴퓨터에서 여러 컴퓨터로 확장하는 것을 단순히 '더 많은 것'과 같다고 생각합니다. 이는 한 사람을 조정하는 것과, 서로 다른 시간대에 있고 항상 연락이 닿지 않을 수도 있는 천 명의 사람들을 조정하는 것이 같다고 생각하는 것과 같습니다.

하나의 컴퓨터에서 코드를 작성할 때, 당신은 예측 가능한 세상에 살고 있습니다:
- 작업이 즉시 성공하거나 실패합니다.
- 데이터가 읽기 사이에 알 수 없게 변경되지 않습니다.
- 시간이 일관되게 앞으로 나아갑니다.
- 무언가를 저장하면 실제로 저장됩니다.

간단한 뱅킹 시스템을 예로 들어봅시다. 이 경우 앨리스(Alice)로부터 밥(Bob)에게 $100를 이체하는 것은 매우 쉽습니다:

```python
def transfer(from_account, to_account, amount):
    if from_account.balance >= amount:
        from_account.balance -= amount
        to_account.balance += amount
        return "Transfer successful"
    return "Insufficient funds"
```

이것은 완벽하게 작동합니다... 확장해야 할 때까지는 말이죠.

은행이 하나의 컴퓨터가 처리할 수 있는 범위를 넘어서 성장하여, 이제 계정을 여러 데이터베이스에 균등하게 분할합니다:
- Server A: 계정 1부터 1,000,000
- Server B: 계정 1,000,001부터 2,000,000
- Server C: 계정 2,000,001부터 3,000,000

이제 앨리스(Alice)(Server A에 있음)가 밥(Bob)(Server B에 있음)에게 $100를 보내려고 합니다. 그 간단한 이체는 다음과 같이 바뀝니다:

```python
def distributed_transfer(alice_server, bob_server, amount):
    # Server A에서 앨리스의 잔액 확인
    if alice_server.get_balance("alice") >= amount:
        alice_server.deduct("alice", amount)    # 1단계
        bob_server.add("bob", amount)           # 2단계
        return "Transfer successful"
    return "Insufficient funds"
```
여전히 간단해 보이나요? 다음은 발생할 수 있는 문제입니다:
- 네트워크 분할 (Network Partition): 1단계 직후, 2단계 이전에 서버 간 연결이 끊깁니다. 앨리스의 $100는 디지털 허공으로 사라집니다.
- 서버 충돌 (Server Crash): Server B가 "입금" 명령을 받은 후, 처리 확인을 보내기 전에 충돌합니다. 밥이 돈을 받았을까요? 아무도 모릅니다.
- 경쟁 상태 (Race Conditions): 앨리스의 두 가지 이체가 동시에 발생합니다. 둘 다 앨리스의 $100 잔액을 확인하고, 충분한 자금이 있음을 확인한 후 두 이체 모두 진행됩니다. 앨리스는 이제 자신이 가지고 있지 않던 $100를 사용한 셈이 됩니다.

### CAP 이론

1999년, 컴퓨터 과학자 에릭 브루어(Eric Brewer)는 CAP 이론을 공식화했습니다. 이는 모든 분산 시스템이 다음 세 가지 속성 중 최대 두 가지만 보장할 수 있다고 말합니다:
- 일관성 (Consistency, C): 모든 서버가 항상 동일한 데이터를 보여줍니다. Server A에서 앨리스의 잔액이 변경되면, 다른 모든 서버가 즉시 이를 반영합니다.
- 가용성 (Availability, A): 서버가 충돌하더라도 시스템은 계속 작동합니다. Server A가 다운되면, 사용자들은 Server B와 C를 통해 계정에 계속 접근할 수 있습니다.
- 분할 내성 (Partition Tolerance, P): 서버를 고립된 그룹으로 분할하는 네트워크 오류에도 시스템이 살아남습니다.

네트워크 분할은 피할 수 없기 때문에 (케이블이 끊어지거나, 라우터가 고장 나거나, 데이터 센터의 전원이 나가는 등) 우리는 분할 내성을 보장해야 합니다. 이는 우리에게 일관성(Consistency) 또는 가용성(Availability) 중 하나를 선택하도록 강요합니다.

전통적인 뱅킹 시스템은 일관성 + 분할 내성 (CP 시스템)을 주로 선택합니다. 이들은 잘못된 계정 잔액을 보여주기보다는 시스템을 종료하는 것을 선호합니다.

소셜 미디어 플랫폼은 가용성 + 분할 내성 (AP 시스템)을 자주 선택합니다. 이들은 친구들이 즉시 게시물을 볼 수 없더라도 게시물을 올리는 것을 완전히 막는 것보다는 허용하는 것을 선호합니다.

### 비잔틴 장군 문제 (The Byzantine Generals Problem)

CAP 이론 외에도 대부분의 분산 시스템은 참여자들이 정직하다고 가정합니다. 즉, 참여자들이 실패하거나 연결이 끊어질 수는 있지만, 서로를 적극적으로 속이지는 않는다는 것입니다. 이러한 가정은 참여자들이 악의적일 수 있을 때 무너집니다.

1982년에 컴퓨터 과학자들이 정립한 비잔틴 장군 문제는 이러한 어려움을 보여줍니다:

당신은 요새화된 도시를 공격할 계획을 세우는 비잔틴 장군입니다. 당신은 도시 주변에 배치된 여러 동맹 장군들을 거느리고 있으며, 각 장군은 자신의 군대를 지휘합니다. 성공하려면 동시 공격을 조율해야 합니다. 일부가 공격하고 다른 일부가 후퇴한다면, 공격하는 병력은 전멸할 것입니다.

당신은 오직 전령을 통해서만 소통하며, 일부 장군들은 공격이 실패하기를 바라는 배신자일 수 있습니다. 배신자들은 다음을 할 수 있습니다:
- 일부 장군들에게는 "공격" 메시지를 보내고 다른 장군들에게는 "후퇴" 메시지를 보냅니다.
- 충성스러운 장군들의 메시지가 전달되는 동안 이를 변경합니다.
- 다른 배신자들과 협력하여 혼란을 극대화합니다.

충성스러운 장군과 배신자를 구별할 수 없고, 통신 채널을 신뢰할 수 없을 때 어떻게 "공격" 또는 "후퇴"에 대한 합의에 도달할 수 있을까요?

이것은 불가능해 보였습니다. 수십 년 동안 컴퓨터 과학자들은 다음을 동시에 만족하는 시스템을 구축할 수 없다고 믿었습니다:
- 비잔틴 장애 허용 (Byzantine fault tolerant) (악의적인 참여자가 있어도 작동함)
- 무허가 (Permissionless) (누구나 승인 없이 참여할 수 있음)
- 탈중앙화 (Decentralized) (중앙 권한 없음)

그러다 2008년, 사토시 나카모토(Satoshi Nakamoto)라는 이름의 누군가가 그들의 생각이 틀렸음을 증명했습니다.

### 비트코인: 최초의 블록체인

비트코인은 블록체인 기술의 최초의 실질적인 구현체였습니다. 개별 구성 요소들(암호화 해싱, 디지털 서명, P2P 네트워크)은 이전에 존재했지만, 사토시는 디지털 화폐의 이중 지불(double-spending) 문제를 해결하기 위해 이들을 결합한 최초의 인물이었습니다.

블록체인, 또는 원래 비트코인 [백서](https://bitcoin.org/bitcoin.pdf)에서 "블록의 사슬(chain of blocks)"이라고 불렸던 기술은 마침내 분산되고, 비잔틴 장애 허용적이며, 무허가(permissionless)인 시스템을 동시에 만들었습니다.

돌파구는 누구를 신뢰해야 하는지를 식별하는 것이 아니었습니다. 그것은 거짓말을 하는 것을 진실을 말하는 것보다 경제적으로 더 비싸게 만드는 것이었습니다. 작업 증명(Proof of Work)은 참여자들이 변경 사항을 제안하기 위해 실제 계산 에너지를 소모하도록 요구함으로써 이를 달성합니다. 공격자는 공격을 통해 얻을 수 있는 것보다 더 많은 전기료를 지출해야 할 것입니다.

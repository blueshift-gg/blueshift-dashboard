# Solana 소개

Solana에서 구축하기 전에, Solana를 독특하게 만드는 몇 가지 기본 개념을 이해해야 합니다. 이 가이드는 account, transaction, program 및 이들 간의 상호작용을 다룹니다.

<ArticleSection name="Accounts on Solana" id="accounts-on-solana" level="h2" />

Solana의 아키텍처는 blockchain에 정보를 저장하는 데이터 컨테이너인 account를 중심으로 합니다. account를 파일 시스템의 개별 파일이라고 생각해보십시오. 각 파일은 특정 속성과 이를 제어하는 owner를 가집니다.

모든 Solana account는 동일한 기본 구조를 가집니다:

```rust
pub struct Account {
    /// lamports in the account
    pub lamports: u64,
    /// data held in this account
    #[cfg_attr(feature = "serde", serde(with = "serde_bytes"))]
    pub data: Vec<u8>,
    /// the program that owns this account. If executable, the program that loads this account.
    pub owner: Pubkey,
    /// this account's data contains a loaded program (and is now read-only)
    pub executable: bool,
    /// the epoch at which this account will next owe rent
    pub rent_epoch: Epoch,
}
```

모든 account는 고유한 32바이트 주소를 가지며, 이는 base58로 인코딩된 문자열(예: `14grJpemFaf88c8tiVb77W7TYg2W3ir6pfkKz3YjhhZ5`)로 표시됩니다. 이 주소는 blockchain에서 account의 식별자 역할을 하며, 특정 데이터를 찾는 방법입니다.

account는 최대 10 MiB의 데이터를 저장할 수 있으며, 여기에는 실행 가능한 program 코드 또는 program별 데이터가 포함될 수 있습니다.

모든 account는 데이터 크기에 비례하는 lamport를 예치하여 "rent-exempt" 상태가 되어야 합니다. "rent"라는 용어는 역사적인 것으로, 원래는 각 epoch마다 account에서 lamport가 차감되었으나 이 기능은 현재 비활성화되었습니다. 오늘날, 이 예치금은 환불 가능한 예치금과 유사하게 작동합니다. account가 데이터 크기에 대한 최소 잔액을 유지하는 한, rent-exempt 상태를 유지하며 영구적으로 지속됩니다. 더 이상 account가 필요하지 않으면, 이를 닫고 예치금을 전액 회수할 수 있습니다.

모든 account는 program에 의해 소유되며, 해당 소유 program만이 account의 데이터를 수정하거나 lamport를 인출할 수 있습니다. 그러나 누구든지 account의 lamport 잔액을 늘릴 수 있으며, 이는 program 자체를 호출하지 않고도 작업 자금을 조달하거나 rent를 지불하는 데 유용합니다.

서명 권한은 소유권에 따라 다르게 작동합니다. System Program이 소유한 account는 transaction에 서명하여 자신의 데이터를 수정하고, 소유권을 이전하거나, 저장된 lamport를 회수할 수 있습니다. 소유권이 다른 program으로 이전되면, 해당 program은 private key를 여전히 소유하고 있는지 여부와 관계없이 account에 대한 완전한 제어권을 얻습니다. 이 제어권 이전은 영구적이며 되돌릴 수 없습니다.

### Account 유형

가장 일반적인 account 유형은 System Account이며, 이는 lamport (SOL의 가장 작은 단위)를 저장하고 System Program에 의해 소유됩니다. 이들은 사용자가 SOL을 송수신하기 위해 직접 상호작용하는 기본적인 wallet account 역할을 합니다.

Token Account는 소유권 및 token metadata를 포함한 SPL token 정보를 저장하는 특수 목적을 가집니다. Token Program은 이 account를 소유하며 Solana ecosystem 전반의 모든 token 관련 작업을 관리합니다. Token Account는 _Data Account_입니다.

Data Account는 애플리케이션별 정보를 저장하며 사용자 정의 program에 의해 소유됩니다. 이 account는 애플리케이션의 state를 보유하며, 간단한 사용자 프로필부터 복잡한 금융 데이터까지 program이 요구하는 대로 구조화될 수 있습니다.

마지막으로, Program Account는 Solana에서 실행되는 실행 가능한 코드를 포함하며, 이곳에 smart contract가 존재합니다. 이 account는 `executable: true`로 표시되며 instruction을 처리하고 state를 관리하는 program의 로직을 저장합니다.

### Account 데이터 작업

program이 account 데이터와 상호작용하는 방법은 다음과 같습니다:

```rust
#[derive(BorshSerialize, BorshDeserialize)]
pub struct UserAccount {
    pub name: String,
    pub balance: u64,
    pub posts: Vec<u32>,
}

pub fn update_user_data(accounts: &[AccountInfo], new_name: String) -> ProgramResult {
    let user_account = &accounts[0];
    
    // Deserialize existing data
    let mut user_data = UserAccount::try_from_slice(&user_account.data.borrow())?;
    
    // Modify the data
    user_data.name = new_name;
    
    // Serialize back to account
    user_data.serialize(&mut &mut user_account.data.borrow_mut()[..])?;
    
    Ok(())
}
```

단순히 레코드를 삽입하는 데이터베이스와 달리, Solana account는 사용 전에 명시적으로 생성되고 자금이 예치되어야 합니다.

<ArticleSection name="Transactions on Solana" id="transactions-on-solana" level="h2" />

Solana transaction은 여러 instruction을 포함할 수 있는 atomic operation입니다. transaction 내의 모든 instruction은 함께 성공하거나 함께 실패합니다. 부분적인 실행은 없습니다.

transaction은 다음으로 구성됩니다:
- Instructions: 수행할 개별 operation
- Accounts: 각 instruction이 읽거나 쓸 특정 account
- Signers: transaction을 승인하는 account

```rust
Transaction {
    instructions: [
        // Instruction 1: Transfer SOL
        system_program::transfer(from_wallet, to_wallet, amount),
        
        // Instruction 2: Update user profile  
        my_program::update_profile(user_account, new_name),
        
        // Instruction 3: Log activity
        my_program::log_activity(activity_account, "transfer", amount),
    ],
    accounts: [from_wallet, to_wallet, user_account, activity_account]
    signers: [user_keypair],
}
```

### Transaction 요구사항 및 수수료

transaction은 총 1,232바이트로 제한되며, 이는 포함할 수 있는 instruction 및 account의 수를 제약합니다.

transaction 내의 각 instruction은 세 가지 필수 구성 요소를 필요로 합니다: 호출할 program address, instruction이 읽거나 쓸 모든 account, 그리고 함수 인자(arguments)와 같은 추가 데이터입니다.

instruction은 transaction 내에서 지정한 순서대로 순차적으로 실행됩니다.

모든 transaction은 transaction 처리에 대한 validator의 보상으로 서명당 5,000 lamport의 기본 수수료가 발생합니다.

또한, 현재 leader가 transaction을 더 빠르게 처리할 가능성을 높이기 위해 선택적 우선순위 수수료(prioritization fee)를 지불할 수 있습니다. 이 prioritization fee는 compute unit limit에 compute unit price(micro-lamport 단위로 측정됨)를 곱하여 계산됩니다.

```
prioritization_fee = compute_unit_limit × compute_unit_price
```

> transaction 수수료를 지불하는 account는 System Program에 의해 소유되어야 하며, 이는 지불을 적절하게 승인할 수 있도록 보장합니다.

<ArticleSection name="Programs on Solana" id="programs-on-solana" level="h2" />

Solana의 program은 근본적으로 stateless입니다. 즉, 함수 호출 사이에 내부 상태를 유지하지 않습니다. 대신, account를 입력으로 받아 해당 account 내의 데이터를 처리하고 수정된 결과를 반환합니다.

이러한 stateless 디자인은 예측 가능한 동작을 보장하고 강력한 composability 패턴을 가능하게 합니다.

program 자체는 `executable: true`로 표시된 특수 account에 저장되며, 호출될 때 실행되는 컴파일된 바이너리 코드를 포함합니다.

사용자는 필요한 account 데이터 및 매개변수와 함께 특정 program 함수를 대상으로 하는 특정 instruction을 포함하는 transaction을 전송하여 이 program과 상호작용합니다.

```rust
use solana_program::prelude::*;

#[derive(BorshSerialize, BorshDeserialize)]
pub struct User {
    pub name: String,
    pub created_at: i64,
}

pub fn create_user(
    accounts: &[AccountInfo],
    name: String,
) -> ProgramResult {
    let user_account = &accounts[0];
    
    let user = User {
        name,
        created_at: Clock::get()?.unix_timestamp,
    };
    
    user.serialize(&mut &mut user_account.data.borrow_mut()[..])?;
    Ok(())
}
```

program은 지정된 upgrade authority에 의해 업데이트될 수 있으며, 이를 통해 개발자는 배포 후 버그를 수정하고 기능을 추가할 수 있습니다. 그러나 이 upgrade authority를 제거하면 program은 영구적으로 불변(immutable)하게 되어, 사용자에게 코드가 절대 변경되지 않을 것이라는 보장을 제공합니다.

투명성과 보안을 위해, 사용자는 검증 가능한 빌드(verifiable builds)를 통해 on-chain program이 공개된 소스 코드와 일치하는지 확인할 수 있으며, 배포된 bytecode가 게시된 소스와 정확히 일치함을 보장합니다.

<ArticleSection name="Program Derived Addresses (PDAs)" id="program-derived-addresses" level="h2" />

PDA는 강력한 프로그래밍 패턴을 가능하게 하는 결정론적으로 생성된 address입니다. 이는 seeds와 program ID를 사용하여 생성되며, 해당 private key가 없는 address를 생성합니다.

PDA는 사용자 정의 seeds, 결과가 off-curve임을 보장하는 bump 값, PDA를 소유할 program ID, 그리고 상수 marker를 포함한 특정 입력을 사용하여 `SHA-256` 해싱을 사용합니다.

해시가 on-curve address를 생성할 때(이는 약 50%의 확률로 발생함), 시스템은 bump 255에서 254, 253 등으로 반복하여 off-curve 결과를 찾을 때까지 반복합니다.

```rust
use solana_nostd_sha256::hashv;

const PDA_MARKER: &[u8; 21] = b"ProgramDerivedAddress";

let pda = hashv(&[
    seed_data.as_ref(),    // Your custom seeds
    &[bump],               // Bump to ensure off-curve
    program_id.as_ref(),   // Program that owns this PDA
    PDA_MARKER,
]);
```

### 이점

PDA의 결정론적 특성 덕분에 address를 저장할 필요가 없습니다. 필요할 때마다 동일한 seeds로부터 재생성할 수 있습니다.

이는 on-chain에서 hashmap 구조처럼 작동하는 예측 가능한 address 지정 체계를 만듭니다. 더 중요하게는, program이 자체 PDA에 서명할 수 있어 private key를 노출하지 않고도 자율적인 자산 관리가 가능합니다.

```rust
let seeds = &[b"vault", user.as_ref(), &[bump]];

invoke_signed(
    &transfer_instruction,
    &[from_pda, to_account, token_program],
    &[&seeds[..]], // Program proves PDA control
)?;
```

<ArticleSection name="Cross Program Invocation (CPI)" id="cross-program-invocation" level="h2" />

CPI는 program이 동일한 transaction 내에서 다른 program을 호출할 수 있도록 하여, 여러 program이 외부 조정 없이 atomic하게 상호작용할 수 있는 진정한 composability를 생성합니다.

이를 통해 개발자는 기능을 처음부터 다시 구축하는 대신 기존 program을 결합하여 복잡한 애플리케이션을 구축할 수 있습니다.

CPI는 일반 instruction과 동일한 패턴을 따르며, 대상 program, 필요한 account, 그리고 instruction 데이터를 지정해야 합니다. 주요 차이점은 다른 program 내부에서 수행될 수 있다는 점입니다.

호출하는 program은 흐름을 제어하면서 특정 작업을 전문화된 program에 위임합니다.

```rust
let cpi_accounts = TransferAccounts {
    from: source_account.clone(),
    to: destination_account.clone(), 
    authority: authority_account.clone(),
};

let cpi_ctx = CpiContext::new(token_program.clone(), cpi_accounts);
token_program::cpi::transfer(cpi_ctx, amount)?;
```

### 제약 및 기능

원래 transaction signers는 CPI 체인 전반에 걸쳐 권한을 유지하므로, program이 사용자를 대신하여 원활하게 작동할 수 있습니다.

그러나 program은 무한 재귀를 방지하기 위해 최대 4단계(`A → B → C → D`)까지만 CPI를 수행할 수 있습니다. program은 또한 `CpiContext::new_with_signer`를 사용하여 CPI에서 자체 PDA에 서명할 수 있어 정교한 자율 operation을 가능하게 합니다.

이러한 composability는 단일 atomic transaction 내에서 여러 program에 걸쳐 복잡한 operation을 가능하게 하여, Solana 애플리케이션을 고도로 모듈화되고 상호 운용 가능하게 만듭니다.

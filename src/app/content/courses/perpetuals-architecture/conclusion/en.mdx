### Everything Connects

A perpetual protocol is a stack of interdependent systems:

```
┌─────────────────────────────────────────┐
│           User Interface                │
│   (Open, close, add margin, monitor)    │
├─────────────────────────────────────────┤
│         Position Management             │
│   (Size, entry price, PnL tracking)     │
├─────────────────────────────────────────┤
│          Margin System                  │
│   (Collateral, leverage, health)        │
├─────────────────────────────────────────┤
│    Funding & Liquidation Engine         │
│   (Rate calculation, position closure)  │
├─────────────────────────────────────────┤
│        Pricing & Oracle Layer           │
│   (Mark price, index price, staleness)  │
├─────────────────────────────────────────┤
│        Risk Management                  │
│   (Insurance, limits, circuit breakers) │
├─────────────────────────────────────────┤
│          Solana Runtime                 │
│   (Accounts, compute, parallelization)  │
└─────────────────────────────────────────┘
```

Each layer depends on the ones below. A bug in oracle integration breaks liquidations. A flaw in margin calculation exposes the insurance fund. Everything is connected.

### The Core Loop

Every perp protocol runs a continuous loop:

```rust
// The perpetual heartbeat (conceptual)
loop {
    // 1. Update prices
    let oracle_price = fetch_oracle_price();
    let mark_price = calculate_mark_price(oracle_price, premium_twap);

    // 2. Update funding
    let funding_rate = calculate_funding_rate(mark_price, oracle_price);
    apply_funding_to_positions(funding_rate);

    // 3. Check positions
    for position in all_positions {
        let health = calculate_margin_ratio(position, mark_price);

        if health < liquidation_threshold {
            liquidate(position);
        }
    }

    // 4. Settle bad debt
    if bad_debt > 0 {
        cover_from_insurance_fund(bad_debt);
    }

    sleep(block_time);
}
```

In reality, these operations trigger on-demand through user transactions and keeper bots. But conceptually, this loop never stops.

<ArticleSection name="Design Principles" id="design-principles" level="h2" />

### Principle 1: Defense in Depth

No single mechanism should be the last line of defense:

```
Position goes bad:
  → Margin absorbs first losses
    → Liquidation closes before bankruptcy
      → Liquidation penalty incentivizes keepers
        → Partial liquidation limits impact
          → Insurance fund covers slippage
            → ADL socializes extreme losses
```

Six layers. Each catches what the previous missed.

### Principle 2: Fail Safe, Not Fail Deadly

When something breaks, the protocol should protect capital, not destroy it:

```rust
// Wrong: Continue with stale oracle
if oracle.is_stale() {
    use_last_known_price() // Attackers exploit this
}

// Right: Restrict operations
if oracle.is_stale() {
    market.status = MarketStatus::ReduceOnly; // Users can exit, can't enter
}
```

Freeze before failure. Reduce-only before liquidation cascades.

### Principle 3: Incentive Alignment

Every participant should profit from keeping the system healthy:

| Participant | Incentive | Mechanism |
|-------------|-----------|-----------|
| Traders | Fair execution | Competitive pricing, low fees |
| Liquidators | Profit from cleanup | Liquidation penalties |
| LPs | Yield from fees | Fee share, trader losses |
| Protocol | Sustainable revenue | Trading fees, insurance fund |

When incentives align, the protocol runs itself. When they don't, attackers find the gaps.

### Principle 4: Simplicity Over Cleverness

The Mango exploit wasn't clever. It was obvious in hindsight. The protocol's complexity created blind spots.

Every additional mechanism is another attack surface. Every clever optimization is another edge case. The best protocols are simple enough to reason about.

<ArticleSection name="Common Failure Modes" id="failure-modes" level="h2" />

### Oracle Exploitation

**Pattern**: Manipulate thin spot markets to affect oracle prices, profit on perp positions.

**Mitigation**:
- Multiple oracle sources
- Confidence interval checks
- Price bands limiting sudden moves
- Position limits based on oracle quality

### Liquidation Cascades

**Pattern**: Large liquidation moves price, triggers more liquidations, spirals.

**Mitigation**:
- Partial liquidations
- Gradual deleveraging
- Spread liquidations over time
- Circuit breakers on extreme moves

### Funding Rate Attacks

**Pattern**: Dominate one side to extract extreme funding from trapped positions.

**Mitigation**:
- Funding rate caps
- Velocity-based dampening
- Open interest imbalance limits
- Insurance fund for extreme conditions

### LP Extraction

**Pattern**: Skilled traders systematically profit against LP pools.

**Mitigation**:
- Price impact fees
- Borrowing fees
- Position limits
- Dynamic fee adjustment based on profitability

<ArticleSection name="Solana-Specific Considerations" id="solana-specific" level="h2" />

### Leverage Solana's Strengths

**400ms blocks**: Enable responsive liquidations. Higher leverage becomes viable.

**Parallel execution**: Design accounts so different positions process independently.

**Low fees**: Allow frequent funding updates and granular liquidations.

```rust
// Solana-optimized position account
#[account]
pub struct Position {
    pub owner: Pubkey,
    pub market: Pubkey,  // Different markets = parallel processing
    // ... position data
}

// Seeds ensure one position per user per market
// Different users' positions never contend
seeds = [b"position", market.key().as_ref(), user.key().as_ref()]
```

### Manage Solana's Constraints

**Compute limits**: Complex calculations may need multiple transactions or pre-computation.

**Account rent**: Every position costs ~0.002 SOL. Consider account recycling.

**State size**: Large arrays hit limits. Use multiple accounts or off-chain indexing.

```rust
// Pattern: Chunked processing for large operations
pub fn process_liquidations_batch(
    ctx: Context<BatchLiquidate>,
    max_positions: u8,  // Process up to N per transaction
) -> Result<()> {
    let mut processed = 0;

    for position in ctx.remaining_accounts.iter().take(max_positions as usize) {
        if should_liquidate(position)? {
            execute_liquidation(position)?;
            processed += 1;
        }
    }

    emit!(BatchLiquidationEvent { count: processed });
    Ok(())
}
```

<ArticleSection name="What Makes a Great Perp Protocol" id="great-protocol" level="h2" />

### For Traders

- **Tight spreads**: Minimal cost to enter and exit
- **Deep liquidity**: Large positions don't move the market
- **Fast execution**: Prices don't slip while waiting
- **Fair liquidations**: Reasonable margins, no hunting
- **Reliable uptime**: Available during volatility

### For LPs

- **Sustainable yield**: Fees exceed adverse selection
- **Limited downside**: Risk is bounded and predictable
- **Transparent exposure**: Clear view of pool risk
- **Easy entry/exit**: Liquid LP tokens

### For the Ecosystem

- **Composability**: Other protocols can build on top
- **Transparency**: All positions and liquidations visible
- **Resilience**: Survives black swan events
- **Decentralization**: No single point of failure

<ArticleSection name="The Road Ahead" id="road-ahead" level="h2" />

### Current Limitations

**Oracle dependency**: Every major perp protocol relies on external price feeds. True decentralization remains elusive.

**Capital efficiency**: LPs lock billions in pools. Better capital utilization is possible.

**Cross-margin complexity**: Managing risk across multiple positions is hard.

**MEV and front-running**: Bots extract value from traders. Mitigation is imperfect.

### Emerging Innovations

**Intent-based trading**: Users express what they want; solvers compete to fill.

**Concentrated liquidity**: LPs provide liquidity at specific price ranges for better efficiency.

**Cross-chain positions**: Positions that span multiple chains with unified margin.

**AI-driven market making**: Machine learning for dynamic parameter adjustment.

### What Will Matter

The protocols that survive will be the ones that:

1. **Understand their trade-offs** and build systems to manage them
2. **Align incentives** so participants profit from system health
3. **Fail gracefully** when assumptions break
4. **Evolve carefully** without introducing new attack vectors
5. **Stay simple** enough to audit and reason about

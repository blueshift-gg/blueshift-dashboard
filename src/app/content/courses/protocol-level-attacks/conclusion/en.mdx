# Conclusion

You have now worked through six categories of protocol-level attacks: oracle manipulation, share inflation, flash loan amplification, state and timing vulnerabilities, denial of service, and MEV extraction. Each category represents a distinct way that protocols fail not because of a single buggy instruction, but because of flawed assumptions about how their systems interact with the broader Solana ecosystem.

<ArticleSection name="The Pattern Behind the Patterns" id="the-pattern-behind-the-patterns" level="h2" />

Every protocol-level attack in this course follows the same underlying structure: the protocol assumes something about its environment that an adversary can violate. Oracle manipulation exploits trust in price feeds, share inflation exploits small-value arithmetic, flash loans exploit capital constraints, TOCTOU exploits state stability, DoS exploits execution paths, and MEV exploits ordering fairness. When you review a protocol, the question is always: "What does this code assume about the world, and can that assumption be broken?"

<ArticleSection name="From Finding to Proving" id="from-finding-to-proving" level="h2" />

Finding bugs is step one. Proving them, classifying them, and communicating them is the craft.

A vulnerability report that says "the oracle could be stale" is not actionable. A report that says "the Pyth SOL/USD feed is consumed with a 600-second staleness window; during the March 2024 volatility event, the feed was 45 seconds stale, which would have allowed an attacker to deposit collateral overvalued by 8%, extracting approximately $2.3M from the lending pool" gives the development team everything they need to prioritize and fix the issue.

The difference between a good security researcher and a great one is not the ability to find more bugs. It is the ability to construct clear, reproducible proof-of-concept exploits and communicate their impact in precise economic terms.

Security is not a feature you add at the end. It is a design discipline that starts with the protocol's first line of code and continues through every upgrade, integration, and market condition the protocol will ever face.

# Інструкція Самоаналізу

Самоаналіз інструкцій — це потужна можливість Solana, яка дозволяє програмі аналізувати інші інструкції в межах тієї ж транзакції, включаючи ті, що ще не виконані.
Це дозволяє динамічно реагувати на ці інструкції або доповнювати їх, наприклад, шляхом впровадження захисних заходів, перевірки поведінки або інтеграції інструкцій із зовнішніх програм у власну логіку.

Це стало можливим завдяки спеціальному системному обліковому запису під назвою системна змінна `Instructions`.
Системні змінні — це облікові записи лише для читання, що підтримуються середовищем виконання Solana та надають внутрішній стан програмам (наприклад, годинник, оренда, розклад епох тощо).
Системна змінна інструкцій надає повний список інструкцій у поточній транзакції разом з їхніми метаданими та серіалізованими даними.

Ось як Solana серіалізує цю інформацію під час виконання:

```rust
// Спочатку зашифруйте кількість інструкцій:
//  0..2 - num_instructions
//
// Потім таблиця зміщень, де їх знайти в даних
//  3..2 * num_instructions таблиця зміщень інструкцій
//
// Потім кожна інструкція кодується так:
//   0..2 - num_accounts
//   2 - meta_byte -> (біт 0 signer, біт 1 is_writable)
//   3..35 - pubkey - 32 bytes
//   35..67 - program_id
//   67..69 - data len - u16
//   69..data_len - data
#[cfg(not(target_os = "solana"))]
fn serialize_instructions(instructions: &[BorrowedInstruction]) -> Vec<u8> {
    // 64 байти – це адекватне припущення, точний розрахунок у бенчмарках відбувається повільніше.
    let mut data = Vec::with_capacity(instructions.len() * (32 * 2));
    append_u16(&mut data, instructions.len() as u16);
    for _ in 0..instructions.len() {
        append_u16(&mut data, 0);
    }

    for (i, instruction) in instructions.iter().enumerate() {
        let start_instruction_offset = data.len() as u16;
        let start = 2 + (2 * i);
        data[start..start + 2].copy_from_slice(&start_instruction_offset.to_le_bytes());
        append_u16(&mut data, instruction.accounts.len() as u16);
        for account_meta in &instruction.accounts {
            let mut account_meta_flags = InstructionsSysvarAccountMeta::empty();
            if account_meta.is_signer {
                account_meta_flags |= InstructionsSysvarAccountMeta::IS_SIGNER;
            }
            if account_meta.is_writable {
                account_meta_flags |= InstructionsSysvarAccountMeta::IS_WRITABLE;
            }
            append_u8(&mut data, account_meta_flags.bits());
            append_slice(&mut data, account_meta.pubkey.as_ref());
        }

        append_slice(&mut data, instruction.program_id.as_ref());
        append_u16(&mut data, instruction.data.len() as u16);
        append_slice(&mut data, instruction.data);
    }
    data
}
```

Це означає, що, зчитуючи обліковий запис sysvar `Instructions` у вашій програмі, ви можете отримати доступ до всіх інструкцій, включених до поточної транзакції.

Вам не потрібно вручну розбирати необроблені байти. Solana надає допоміжні функції:
- `load_current_index_checked`: повертає індекс інструкції, що виконується на даний момент.
- `load_instruction_at_checked`: дозволяє завантажити певну інструкцію за її індексом у розібраному, десеріалізованому форматі.

<ArticleSection name="Як це працює?" id="how-does-it-work" level="h2" />

Кожна інструкція Solana містить:
- ідентифікатор програми, на яку вона орієнтована,
- облікові записи, з якими вона взаємодіє (включаючи метадані, такі як підписувач/доступ для запису),
- та корисне навантаження даних (зазвичай дискримінатор + аргументи).

І саме це надає функція `load_instruction_at_checked` з системної змінної Instructions:
- program_id: програма, яку викликає ця інструкція.
- accounts: список задіяних облікових записів з метаданими.
- data: необроблене вхідне корисне навантаження (якщо ми аналізуємо інструкцію-прив'язку, вона часто починається з 8-байтового дискримінатора, за яким йдуть параметри).

Щоб безпечно та ефективно аналізувати інші інструкції, виконайте такі дії:
- Визначте індекс поточної інструкції: Використовуйте `load_current_index_checked`, щоб знайти індекс інструкції, що виконується на даний момент.
> Майте на увазі: ваша інструкція може бути не першою (індекс 0) у транзакції.

- Завантаження цільової інструкції для аналізу: Маючи індекс, використовуйте `load_instruction_at_checked(index)` для завантаження іншої інструкції в тій самій транзакції — або ту, що була до, після або в певній позиції.
> Це корисно для перевірки поведінки, забезпечення очікуваних вхідних даних або безпечного складання коду в різних програмах.

- Створення обмежень для запобігання шкідливій поведінці: самоаналіз інструкцій є потужним інструментом, але він створює нові поверхні для атаки. Переконайтеся, що ви: перевірили, чи спрямована інтроспективна інструкція на очікувану програму, підтвердили, що адреси облікових записів та дані відповідають очікуваним шаблонам, та уникали припущень щодо порядку інструкцій, якщо це не передбачено чітко.

Вживаючи цих запобіжних заходів, ви можете безпечно використовувати інтроспекцію інструкцій для створення потужних, компонованих та безпечних програм Solana.

<ArticleSection name="Загальні обмеження для самоаналізу" id="common-constraints-for-introspection" level="h2" />

Під час використання інтроспекції інструкцій важливо запроваджувати суворі обмеження, щоб запобігти зловмисній або неочікуваній поведінці. Найпоширеніші запобіжні заходи включають:
- Перевірка інструкції: Перевірте ідентифікатор програми та дискримінатор інструкції, щоб переконатися, що вони правильні. Дискримінатор (зазвичай перші 1, 4 або 8 байтів даних інструкції) однозначно ідентифікує, яка функція викликається.
> Цей крок гарантує, що ви перевіряєте саме ту інструкцію, яку потрібно перевірити, а не підроблену або неправильно сформовану.

- Перевірка змінних: Після дискримінатора проаналізуйте та перевірте критичні змінні, що використовуються інструкцією. Вони можуть включати суми, напрямки (наприклад, довгі/короткі) або ідентифікатори, і ви завжди повинні підтверджувати, що ці поля відповідають очікуваній логіці вашої інтеграції або захисту.
- Перевірка облікового запису: Перевірте структуру та ідентичність облікових записів інструкції. Перевірте, чи очікувані облікові записи відображаються в певних позиціях (наприклад, підписувач, сховище, забезпечення), і переконайтеся, що такі ролі, як підписувач/статус придатності для запису, відповідають вашим припущенням.

Застосовуючи ці обмеження, ви гарантуєте, що ваша програма реагує лише на дійсні та надійні інструкції, роблячи вашу логіку більш надійною, компонуємою та безпечною.

Разом з атомарністю транзакцій ці перевірки дозволяють вам створювати надійну, компонуєму логіку, яка може безпечно взаємодіяти з іншими програмами та інструкціями в межах однієї транзакції.

> Пам'ятайте, що транзакції в Solana є атомарними. Якщо будь-яка інструкція завершується невдачею, вся транзакція відкатується.

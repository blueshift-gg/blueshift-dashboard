# Swap

Інструкція `swap` як і раніше виконує дві основні задачі:

- Обчислює, скільки токена з протилежного боку користувач має отримати з урахуванням комісії.
- Переміщує токени в пул і з пулу.

Змінюється те, як ми взаємодіємо з token program. Звичайний AMM swap зазвичай робить два CPI до token program, тобто двічі платить базову ціну CPI. З `p-token` ми зберігаємо той самий program ID і той самий клієнтський потік, але можемо загорнути кілька token instructions в одну instruction `batch`.

> Один із найкраще прихованих секретів `p-token` це batching. Кілька операцій із токенами можна виконати в одному CPI за допомогою discriminator `255`, і це дуже добре підходить для AMM swap.

<ArticleSection name="Потрібні Акаунти" id="required-accounts" level="h2" />

Ось акаунти, які потрібні в цьому контексті:

- `user`: користувач, який робить swap в AMM. Має бути `signer`.
- `user_x_ata`: associated token account користувача для токена X. Має передаватися як `mutable`.
- `user_y_ata`: associated token account користувача для токена Y. Має передаватися як `mutable`.
- `vault_x`: token account, що зберігає токен X пулу. Має передаватися як `mutable`.
- `vault_y`: token account, що зберігає токен Y пулу. Має передаватися як `mutable`.
- `config`: акаунт конфігурації AMM. Зберігає стан пулу та параметри.
- `token_program`: акаунт token program. `p-token` уже працює в mainnet, зберігає той самий program ID SPL Token і той самий клієнтський інтерфейс та надає batch instruction, яку ми хочемо використати для цього swap. Має бути `executable`.

Парсер акаунтів не змінюється:

```rust
pub struct SwapAccounts<'a> {
    pub user: &'a AccountInfo,
    pub user_x_ata: &'a AccountInfo,
    pub user_y_ata: &'a AccountInfo,
    pub vault_x: &'a AccountInfo,
    pub vault_y: &'a AccountInfo,
    pub config: &'a AccountInfo,
    pub token_program: &'a AccountInfo,
}

impl<'a> TryFrom<&'a [AccountInfo]> for SwapAccounts<'a> {
    type Error = ProgramError;

    fn try_from(accounts: &'a [AccountInfo]) -> Result<Self, Self::Error> {
        //..
    }
}
```

<ArticleSection name="Дані Інструкції" id="instruction-data" level="h2" />

Дані інструкції також не змінюються:

- `is_x`: чи міняє користувач X на Y або Y на X. Має бути `[u8]`.
- `amount`: сума, яку користувач хоче відправити. Має бути `[u64]`.
- `min`: мінімальна сума, яку користувач хоче отримати. Має бути `[u64]`.
- `expiration`: часовий штамп, після якого ордер стає невалідним. Має бути `[i64]`.

Можна зберегти ту саму структуру:

```rust
pub struct SwapInstructionData {
    pub is_x: bool,
    pub amount: u64,
    pub min: u64,
    pub expiration: i64,
}

impl<'a> TryFrom<&'a [u8]> for SwapInstructionData {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        //..
    }
}
```

> Переконайся, що `amount` і `min` більші за нуль, і відхиляй прострочені ордери через sysvar `Clock`.

<ArticleSection name="Чому Batch Важливий" id="why-batch-matters" level="h2" />

Кожен CPI має базову вартість 1 000 compute units. Звичайний swap виконує два token transfers:

1. token account користувача -> vault
2. vault -> token account користувача

Без batching це означає два окремі token CPI. З `p-token` обидва трансфери можна загорнути в один зовнішній token CPI за допомогою batch instruction з discriminator `u8::MAX` (`255`).

Кожна внутрішня instruction всередині batch кодується так:

- `account_count: u8`
- `data_len: u8`
- `instruction_data: [u8; data_len]`

Потім token program проходить по payload і послідовно виконує кожну внутрішню instruction. Batch instruction не може містити іншу batch instruction.

<ArticleSection name="Логіка Інструкції" id="instruction-logic" level="h2" />

Ми починаємо з десеріалізації `instruction_data` та `accounts`.

Потім потрібно:

- завантажити акаунт `Config` через `Config::load()`,
- перевірити, що стан пулу дорівнює `AmmState::Initialized`,
- перевірити, що `vault_x` і `vault_y` це очікувані associated token accounts,
- десеріалізувати vault token accounts і порахувати результат swap за допомогою `constant-product-curve`.

Сам розрахунок лишається таким:

```rust
let vault_x = unsafe { TokenAccount::from_account_info_unchecked(self.accounts.vault_x)? };
let vault_y = unsafe { TokenAccount::from_account_info_unchecked(self.accounts.vault_y)? };

let mut curve = ConstantProduct::init(
    vault_x.amount(),
    vault_y.amount(),
    vault_x.amount(),
    config.fee(),
    None,
)
.map_err(|_| ProgramError::Custom(1))?;

let p = match self.instruction_data.is_x {
    true => LiquidityPair::X,
    false => LiquidityPair::Y,
};

let swap_result = curve
    .swap(p, self.instruction_data.amount, self.instruction_data.min)
    .map_err(|_| ProgramError::Custom(1))?;

if swap_result.deposit == 0 || swap_result.withdraw == 0 {
    return Err(ProgramError::InvalidArgument);
}
```

Важлива зміна стосується етапу transfer. Ми все ще хочемо використовувати token helpers із `pinocchio_token`, але замість того, щоб двічі викликати `Transfer::invoke()`, ми покладемо обидва transfer в одну `Batch` і викличемо token program лише один раз.

Імпорт може виглядати так:

```rust
use pinocchio_token::{
    instructions::{Batch, Transfer},
    state::TokenAccount,
};
```

А сам крок transfer має виглядати так:

```rust
let mut batch = Batch::default();

if self.instruction_data.is_x {
    Transfer::new(
        self.accounts.user_x_ata,
        self.accounts.vault_x,
        self.accounts.user,
        self.instruction_data.amount,
    )
    .into_batch(&mut batch)?;

    Transfer::new(
        self.accounts.vault_y,
        self.accounts.user_y_ata,
        self.accounts.config,
        swap_result.withdraw,
    )
    .into_batch(&mut batch)?;
} else {
    Transfer::new(
        self.accounts.user_y_ata,
        self.accounts.vault_y,
        self.accounts.user,
        self.instruction_data.amount,
    )
    .into_batch(&mut batch)?;

    Transfer::new(
        self.accounts.vault_x,
        self.accounts.user_x_ata,
        self.accounts.config,
        swap_result.withdraw,
    )
    .into_batch(&mut batch)?;
}

batch.invoke_signed(&[signer])?;
```

Ключовий момент у тому, що ми все ще використовуємо `Transfer`, просто в batch-формі. `Transfer` реалізує `IntoBatch`, тож нам не потрібно вручну серіалізувати внутрішні instruction. Якщо у твоєму flow не потрібні PDA signer seeds, це може завершуватися простим `batch.invoke()?;` точно як у прикладах `p-token`. У цьому AMM swap нам потрібна PDA `config`, щоб підписати transfer із vault, тому ми використовуємо `batch.invoke_signed(&[signer])?;`.

> Тобто: кілька token instructions, один CPI. Саме тому batch настільки добре підходить для swap, LP deposit та подібних DeFi-потоків.

Тепер тобі потрібно оновити фінальну логіку `process()` так, щоб:

- спочатку виконувалися перевірки та обчислення,
- обидві інструкції `Transfer` додавалися в batch,
- а в кінці batch один раз викликалася до token program.

Зовнішня форма instruction не змінюється:

```rust
pub struct Swap<'a> {
    pub accounts: SwapAccounts<'a>,
    pub instruction_data: SwapInstructionData,
}

impl<'a> TryFrom<(&'a [u8], &'a [AccountInfo])> for Swap<'a> {
    type Error = ProgramError;

    fn try_from((data, accounts): (&'a [u8], &'a [AccountInfo])) -> Result<Self, Self::Error> {
        let accounts = SwapAccounts::try_from(accounts)?;
        let instruction_data = SwapInstructionData::try_from(data)?;

        Ok(Self {
            accounts,
            instruction_data,
        })
    }
}

impl<'a> Swap<'a> {
    pub const DISCRIMINATOR: &'a u8 = &3;

    pub fn process(&mut self) -> ProgramResult {
        //..

        Ok(())
    }
}
```

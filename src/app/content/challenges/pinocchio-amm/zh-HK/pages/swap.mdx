# 交換

`swap` 指令仍然執行相同的兩個高層任務：

- 計算用戶在扣除手續費後應該收到多少另一側的代幣。
- 將代幣轉入池中並從池中轉出。

改變的是我們與代幣程式互動的方式。一般的 AMM swap 通常會對代幣程式執行兩次 CPI，也就是要支付兩次 CPI 基礎成本。使用 `p-token` 時，我們仍然保留相同的程式 ID 與客戶端流程，但可以把多條代幣指令封裝進單一 `batch` 指令。

> `p-token` 最值得關注的能力之一就是 batching。透過 discriminator `255`，你可以在一次 CPI 中執行多個代幣操作，這對 AMM swap 非常合適。

<ArticleSection name="所需帳戶" id="required-accounts" level="h2" />

此情境需要以下帳戶：

- `user`：在 AMM 中進行交換的用戶。必須是 `signer`。
- `user_x_ata`：用戶的 token X 關聯代幣帳戶。必須作為 `mutable` 傳入。
- `user_y_ata`：用戶的 token Y 關聯代幣帳戶。必須作為 `mutable` 傳入。
- `vault_x`：池子持有 token X 的代幣帳戶。必須作為 `mutable` 傳入。
- `vault_y`：池子持有 token Y 的代幣帳戶。必須作為 `mutable` 傳入。
- `config`：AMM 配置帳戶。儲存池子的狀態與參數。
- `token_program`：代幣程式帳戶。`p-token` 已經在主網上線，保留相同的 SPL Token 程式 ID 與客戶端介面，並提供我們要在這次 swap 中使用的 batch 指令。必須是 `executable`。

帳戶解析邏輯保持不變：

```rust
pub struct SwapAccounts<'a> {

    }
```

<ArticleSection name="指令資料" id="instruction-data" level="h2" />

指令資料同樣保持不變：

- `is_x`：表示用戶是從 X 換到 Y，還是從 Y 換到 X。必須是 `[u8]`。
- `amount`：用戶願意送出的數量。必須是 `[u64]`。
- `min`：用戶願意接受的最小數量。必須是 `[u64]`。
- `expiration`：訂單失效的時間戳。必須是 `[i64]`。

我們可以保留相同的資料結構：

```rust
pub struct SwapInstructionData {
    pub is_x: bool,
    pub amount: u64,
    pub min: u64,
    pub expiration: i64,
}

impl<'a> TryFrom<&'a [u8]> for SwapInstructionData {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        //..
    }
}
```

> 請確保 `amount` 和 `min` 都大於零，並使用 `Clock` sysvar 拒絕已經過期的訂單。

<ArticleSection name="為什麼 Batch 很重要" id="why-batch-matters" level="h2" />

每次 CPI 都有 1,000 compute units 的基礎成本。一次普通 swap 會執行兩次代幣轉帳：

1. 用戶代幣帳戶 -> vault
2. vault -> 用戶代幣帳戶

如果不使用 batching，這就是兩次獨立的代幣 CPI。使用 `p-token` 時，可以透過 discriminator 為 `u8::MAX`（`255`）的 batch 指令，把這兩次轉帳包進一次外層代幣 CPI。

batch 內每條內部指令的編碼格式如下：

- `account_count: u8`
- `data_len: u8`
- `instruction_data: [u8; data_len]`

代幣程式之後會遍歷整個 payload，並依序執行每條內部指令。batch 指令本身不能再巢狀另一條 batch 指令。

<ArticleSection name="指令邏輯" id="instruction-logic" level="h2" />

我們首先要反序列化 `instruction_data` 和 `accounts`。

接著需要：

- 使用 `Config::load()` 載入 `Config` 帳戶，
- 驗證池子的狀態為 `AmmState::Initialized`，
- 驗證 `vault_x` 與 `vault_y` 是預期的關聯代幣帳戶，
- 反序列化 vault 的代幣帳戶，並使用 `constant-product-curve` 計算交換結果。

這部分計算仍然如下：

```rust
let vault_x = unsafe { TokenAccount::from_account_info_unchecked(self.accounts.vault_x)? };
let vault_y = unsafe { TokenAccount::from_account_info_unchecked(self.accounts.vault_y)? };

let mut curve = ConstantProduct::init(
    vault_x.amount(),
    vault_y.amount(),
    vault_x.amount(),
    config.fee(),
    None,
)
.map_err(|_| ProgramError::Custom(1))?;

let p = match self.instruction_data.is_x {
    true => LiquidityPair::X,
    false => LiquidityPair::Y,
};

let swap_result = curve
    .swap(p, self.instruction_data.amount, self.instruction_data.min)
    .map_err(|_| ProgramError::Custom(1))?;

if swap_result.deposit == 0 || swap_result.withdraw == 0 {
    return Err(ProgramError::InvalidArgument);
}
```

真正重要的改變發生在轉帳步驟。我們仍然想繼續使用 `pinocchio_token` 的代幣 helper，但不是再呼叫兩次 `Transfer::invoke()`，而是把兩筆轉帳都加入同一個 `Batch`，然後只呼叫一次代幣程式。

匯入可以寫成這樣：

```rust
use pinocchio_token::{
    instructions::{Batch, Transfer},
    state::TokenAccount,
};
```

轉帳步驟應該像這樣：

```rust
let mut batch = Batch::default();

if self.instruction_data.is_x {
    Transfer::new(
        self.accounts.user_x_ata,
        self.accounts.vault_x,
        self.accounts.user,
        self.instruction_data.amount,
    )
    .into_batch(&mut batch)?;

    Transfer::new(
        self.accounts.vault_y,
        self.accounts.user_y_ata,
        self.accounts.config,
        swap_result.withdraw,
    )
    .into_batch(&mut batch)?;
} else {
    Transfer::new(
        self.accounts.user_y_ata,
        self.accounts.vault_y,
        self.accounts.user,
        self.instruction_data.amount,
    )
    .into_batch(&mut batch)?;

    Transfer::new(
        self.accounts.vault_x,
        self.accounts.user_x_ata,
        self.accounts.config,
        swap_result.withdraw,
    )
    .into_batch(&mut batch)?;
}

batch.invoke_signed(&[signer])?;
```

這裡最重要的是：我們仍然在使用 `Transfer`，只是改成 batched 的用法。`Transfer` 已經實作了 `IntoBatch`，所以不需要再手動序列化內部指令。如果你的流程不需要 PDA signer seeds，這裡可以像 `p-token` 範例一樣直接 `batch.invoke()?;`。而在這個 AMM swap 中，我們需要 `config` 這個 PDA 為 vault 向外轉帳簽名，所以這裡應該使用 `batch.invoke_signed(&[signer])?;`。

> 換句話說：多條代幣指令，一次 CPI。這正是 batch 特別適合 swap、LP 存款以及類似 DeFi 流程的原因。

現在你應該把最終的 `process()` 邏輯更新為：

- 先完成驗證與計算，
- 再把兩條 `Transfer` 指令加入 batch，
- 最後只呼叫一次 batch，把它送給代幣程式執行。

外層指令的結構保持不變：

```rust
pub struct Swap<'a> {
    pub accounts: SwapAccounts<'a>,
    pub instruction_data: SwapInstructionData,
}

impl<'a> TryFrom<(&'a [u8], &'a [AccountInfo])> for Swap<'a> {
    type Error = ProgramError;

    fn try_from((data, accounts): (&'a [u8], &'a [AccountInfo])) -> Result<Self, Self::Error> {
        let accounts = SwapAccounts::try_from(accounts)?;
        let instruction_data = SwapInstructionData::try_from(data)?;

        Ok(Self {
            accounts,
            instruction_data,
        })
    }
}

impl<'a> Swap<'a> {
    pub const DISCRIMINATOR: &'a u8 = &3;

    pub fn process(&mut self) -> ProgramResult {
        //..

        Ok(())
    }
}
```
